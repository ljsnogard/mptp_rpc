## 0. 这份文档要解决什么

前面几轮把 Phase 2 实现过两遍，两遍都跑偏，而且偏的是**同一个地方**：把「报文头（prefix）」
与「报文体（body）」当成了一次性一起发出去的整体。这一轮的实现甚至更进一步，为了在 prefix
里写出 `Body_Size`，先在发送前把体编了一遍来量长度——这等于要求体是**可重放**的。

本文把三件事定下来，供后续实现照着做：

1. 体的两种传输机制（定长 / 分块）以及它们在头部如何**被判别**；
2. HTTP 对这两件事的成熟约定，作为协议设计的参考；
3. `prefix` 与 `body` 为什么必须是**两个独立的收发单元**——这是前两遍实现跑偏的根因。

---

## 1. 两种传输机制

体的内容来源决定了它属于哪一类：

| 机制 | 适用场景 | 头部表达 | 发送方代价 |
| --- | --- | --- | --- |
| **定长** | 体在发送前就已经完整存在（内存里的值、已落盘的文件），长度**已知** | 声明总长度 | 零额外代价：长度直接写进头 |
| **分块** | 体在发送时才产生（流式、消费型、长度不可预知）；或者虽然能算但要算一遍才能知道 | 声明「本体的长度是分块给出的」 | 每块自带长度，边产生边发，**不需要预先知道总长** |

**判别必须在头部显式声明**：接收方拿到 prefix 之后，必须能从头部**唯一地**判断出「这是定长
还是分块」，然后选择对应的解读方式。这一条是硬要求——它是本文第 3 节「接收方先读 prefix」
能成立的前提：接收方要先知道对方打算怎么发，才能决定要不要接、怎么接。

> 参考 HTTP 的做法：`Content-Length` 与 `Transfer-Encoding: chunked` 是**互斥**的两种声明，
> 且前者的优先级更低（见 §2.2）。HTTP 用「哪个头在场」来判别，而不是靠猜。

## 2. HTTP 的参考

HTTP 在这两件事上有二十年积累，值得逐条对照。

### 2.1 chunked 的报文格式（[RFC 7230 §4.1](https://datatracker.ietf.org/doc/html/rfc7230#section-4.1)）

```text
chunked-body = *chunk last-chunk trailer-part CRLF

chunk        = chunk-size [ chunk-ext ] CRLF chunk-data CRLF
chunk-size   = 1*HEXDIG                 ; 每个块自带长度，十六进制
last-chunk   = 1*("0") [ chunk-ext ] CRLF
```

要点：

- **每个块自带长度**，写在块前面。接收方不需要预先知道总长，可以边收边处理
  （这正是 HTTP 能流式转发大响应的原因）；
- **结束标记是显式的**：长度为 `0` 的块就是「体到此为止」。没有它就不知道体何时结束
  （因为长度没写在头部）；
- 长度用十六进制文本，那是 HTTP 文本协议的妥协。MPTP 是二进制优先，长度应当用**二进制**
  编码（MessagePack 整数，或定长 `u32`），不必照搬 hex + CRLF;
- trailer 是可选的尾部头。MPTP 是否需要类似物，见 §5。

### 2.2 模式判别与优先级（[RFC 7230 §3.3.3](https://datatracker.ietf.org/doc/html/rfc7230#section-3.3.3)）

HTTP 判别「体有多长」的规则，按优先级：

1. 对响应而言，`HEAD` 请求的回复、`1xx` / `204` / `304` 的回复**一律无体**，
   即便头里出现了 `Content-Length`——**方法/状态本身就能否决体的存在**；
2. 有 `Transfer-Encoding` 且最终编码是 `chunked` → 按 chunked 读；
3. 否则有 `Content-Length` → 按该长度读；
4. 都没有 → 对响应是「读到连接关闭为止」，对请求则是错误。

值得借鉴的两点：

- **「没有体」是一个独立于「体有多长」的结论**，而且可以由方法/状态直接推出（第 1 条）。
  MPTP 的 `Head` / `Drop` 正好对应这一条语义；
- **判别是「看哪几个头在场」的组合判断**，不是单看一个头。

不必照搬的两点：

- HTTP 的 `Transfer-Encoding` 是**逐跳**（hop-by-hop）语义，中间代理可以重新编码。MPTP 一条
  channel 就是端到端，只有一跳，不存在「中途换编码」的问题；
- 第 4 条「读到连接关闭」在 MPTP 里不该有地位：一条 channel 上可能还有 suffix stream，
  「靠关闭定界」会把后续数据一起吞掉。

### 2.3 multipart 的分界（[RFC 7578](https://datatracker.ietf.org/doc/html/rfc7578)）

`multipart/form-data` 解决的是「多个部分」而不是「一个体的分块」，但它的定界方式很值得对照：

```text
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryXXXX

------WebKitFormBoundaryXXXX CRLF
Content-Disposition: form-data; name="field1" CRLF
CRLF
<field1 的内容>
------WebKitFormBoundaryXXXX CRLF
...
------WebKitFormBoundaryXXXX--  CRLF      ; 结束边界以 -- 收尾
```

要点：

- **分界符（boundary）在头部声明**，接收方据此切开各个部分——与 chunked 一样，
  「怎么分」这件事必须先由头部交代清楚；
- **每个部分可以有自己的头**（这里是 `Content-Disposition`），于是每个部分可以独立声明
  自己的长度/类型；这与 §1 的两种机制正交，可以与 chunked 组合；
- **结束有显式标记**（末尾的 `--`）。

**对 MPTP 的启示**：chunk 头不必只是「长度」一个字段。既然每个 chunk 都是协议实现自己写的，
它完全可以是一个小的 MessagePack map（长度 + 可选的类型/序号/标志），代价是每个 chunk 多
几个字节。是否需要，见 §5。

## 3. prefix / body 为什么必须分离（核心设计意图）

这一节是本文的重点，也是前两遍实现跑偏的根因。以下先把结论按原样记下：

> 对于发送方和接收方来说，header 部分的内容是由协议实现（即这个库的代码）来决定的，所以
> 可以先发送一波，但是 body 的内容通常变化很大，可能是定长的也可能是长度未定的，不太可能
> 一次性发送。
>
> 所以之前的设计就是，先把确定的部分（即所谓的 prefix）先发了，腾出来 ring 的空间边序列化
> 边发。对于接收方也是一样的，先把 prefix 部分解析出来，看看对方到底要发什么东西，给上层
> 调用者一个判断要不要接收的机会，而不是要求接收方一定要一次过接收完可能不想要的内容。

拆开看，这是**两侧各一条独立的理由**：

### 3.1 发送方：prefix 先走，是为了腾出 ring 的空间

`prefix` 的内容（method / path / headers）是**协议实现自己决定的**：它知道要写哪些字段、
每个字段多大，总量小且**在构造请求时就完全确定**。所以它可以先写进 ring、先发出去。

体则相反：它可能几 KiB，也可能几百 MiB；可能是内存里的值，也可能是「要发的时候才产生」的流。
如果坚持「先把体准备好再一起发」，只有两条路：

- 把体整个攒进一块缓冲（**违反 README §7 第 1 条纪律**：IO 路径上不许用 `Vec` 绕开 ring）；
- 或者先把体编一遍量出长度（**要求体可重放**，直接排除掉流式体）。

把 prefix 先发出去之后，ring 的空间就被**腾出来给体用**：体可以「边序列化边写」，一段一段
落进 ring 再上网。发送方不需要预先知道体的总长，甚至不需要体可重放——这正是 chunked 机制
存在的意义。

### 3.2 接收方：prefix 先解析，是为了把「要不要接」的决定权交给上层

接收方先只解 prefix，于是**在体到达之前**就已经知道：

- 对方用的是哪个 access method、访问哪个资源；
- 体是定长还是分块、长度是多少、类型是什么。

拿到这些之后，上层才有可能做出这些决定：

- **不想要这个体**：例如按 `path` 判定「这不是我要处理的请求」，或者按 `Body_Size` 判定
  「这比我愿意接的上限还大」——此时可以直接拒绝/中止，而不必先把几百 MiB 读进来再说；
- **换个方式来接**：例如分块体可以边收边处理，不必等收完；
- **先回一个错误**：例如 `413` / `404`，此时体根本不用读。

如果接收方被设计成「一次性收完整条报文」，上面这些机会**全部消失**：它必须先无条件地把体
吃下来，才有机会看一眼它是什么。

### 3.3 因此 prefix 是一个独立的收发单元

两条理由合起来要求：

- **发送侧**：写出 prefix 与写出 body 是两个可分别完成的步骤，中间**不允许**存在「为了写
  prefix 而必须先把 body 准备好」的依赖（例如「先算出体的总长以便写进 `Body_Size`」）；
- **接收侧**：解析 prefix 与接收 body 是两个可分别完成的步骤，中间必须留出**上层可以插进来
  做决定的时机**。

`send_request_prefix` / `recv_response_prefix` 这两个入口就是这条要求的载体。把它们合并成
「一次把整条报文发完/收完」，无论实现上多干净，都是把这条设计整个丢掉。

## 4. `feat/rpc_demo`（提交 `734a68c`）上的实现跑偏在哪

以下 8 条是**历史偏差**，已在
[`body-transfer-impl-20261010-2102.md`](body-transfer-impl-20261010-2102.md) §5 逐条核销；
保留在这里是为了记住「跑偏长什么样」，避免再走回去。

| # | 现状 | 违反了什么 |
| --- | --- | --- |
| 1 | `send_request_async` 在写 prefix **之前**调用 `req.try_body_len()` 预量长度，再写 `Body_Size` | §3.1：要求体可重放，且必须在 prefix 之前完整编码一遍才能发第一个字节。**这是最根本的一处** |
| 2 | `TrRpcBody::try_encoded_len() -> Result<Option<usize>, _>` 只有两态：没有体 / 有体且长度已知 | §1：缺「有体但长度未知」这一态，分块机制在类型层面就表达不出来 |
| 3 | `TrRpcBody` 没有任何「产出 chunk 序列」的接口 | §1：分块机制完全缺失。`grep -ri chunk` 在 `mptp_core/`、`rpc_demo/` 零命中 |
| 4 | 标准头里没有任何承载「定长还是分块」的字段 | §1：模式判别机制不存在 |
| 5 | `read_body_async_` 只认 `Body_Size`：有值就 `Read::take(size)` 定长读，没值就返回 `None`（当作没有体） | §1：没有分块分支 |
| 6 | `ResponseBodyDecision::decide` 把「有 `Body_Type` 但没有 `Body_Size`」判成 `MissingBodySize` **协议违规** | §3.2：对端若按分块发，接收方不是「不识别」而是**报违规**，比不支持更糟 |
| 7 | `recv_request_body_async` / `recv_response_body_async` 一次性把体解完 | §3.2：没有给上层「先看 prefix 再决定要不要接」的时机 |
| 8 | client 侧走的是合并后的 `send_request_async` | §3.3：把两个收发单元又粘了回去 |

**没有跑偏的部分**（修正时可以保留）：

- IO 直接落在 ring 上、不引入中转缓冲（`messaging/io_.rs`）——这条是对的，也是它让 §3.1
  「边序列化边发」有实现的可能；
- `WaitingTx`（环满时让 `AsStdWrite` 走它自己的异步等待分支）——分块发送更需要它；
- `TrRpcBody` 是「线上编码视图」而不是「字节视图」——方向正确，只是要扩出第三态/chunk 接口；
- 「没有体就不读一个字节」「写出前核对声明长度与实际长度」。

## 5. 协议决策（已拍板）

本节原来列了 6 个待定问题，现已全部拍板并落地（论证与实现见
[`body-transfer-impl-20261010-2102.md`](body-transfer-impl-20261010-2102.md)）：

| # | 问题 | 决策 |
| --- | --- | --- |
| 1 | 模式标记用什么承载 | 新标准头 `Body_Transfer`（`0xA5`），**只定义 `Chunked`**（`0x20`）一个值；`Body_Size` 与它互斥，同时在场即违规 |
| 2 | chunk 头怎么编码 | **定长 2 字节大端 `u16`**：写侧可精确预留、读侧可直接读满，不必跑 `serde` |
| 3 | 结束标记怎么表示 | 长度 `0` 的块（照搬 HTTP last-chunk） |
| 4 | `TrRpcBody` 扩成什么样 | **不动体接口**：传输模式由报文头声明、由调用方选择，不由体类型推断；发送体的统一形状是「一个 `TrBuffRead<u8>` 源」 |
| 5 | `ResponseBodyDecision` 要不要扩 | 扩出 `Chunked` 态，判别顺序改为「先方法/状态否决 → 再看模式标记 → 最后看长度」 |
| 6 | suffix stream 与 chunked 的关系 | 终止块之后紧接着就是 suffix stream：体读视图读到终止块即停，后续字节留给同一条 channel |
