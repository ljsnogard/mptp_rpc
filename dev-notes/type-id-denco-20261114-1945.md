## 0. 结论摘要

1. **是**：denco 的 `TrHasTypeId::TYPE_ID_64` 可以直接成为 `mptp_rpc::Data_Type_Id` 的单一
   事实来源。`rpc_core_v1` 只保留 `TrDataTypeId` 作为 MPTP 线协议 facade，feature 开启时
   由 blanket impl 从 `TYPE_ID_64` 取值；feature 关闭时手写 impl 的旧路径不变。
2. **feature 默认开启**：`default = ["rt-tokio", "type-id"]`。理由见 §1.1。
3. `TrDataTypeId` **保留**（不改成直接使用 `TrHasTypeId`）：它是 MPTP 线协议的窄契约
   （非零 `DataTypeId`），而 denco 的三宽度 + `TYPE_NAME` 属于生成层；保留 facade 让
   feature 关闭 / 手写 override / 递归路径都还能工作。
4. `mptp_wire` / `mptp_smux` / `mptp_serving` / `abs_mptp` / `mptp_smux_v1_demo`
   **均无需改动**（§5 有依赖与源码证据）。
5. `rpc_svc_macro` 的 opt-in 方案推荐「impl 级 `typed` + 方法级可覆盖」，但**本期不实施**；
   Push / trait code-first 另立设计。A-08 仍为 `GAP`（§6）。

## 1. 决策

### 1.1 D1：`rpc_core_v1` 的 feature 契约——`type-id` 进 default

```toml
[features]
default = ["rt-tokio", "type-id"]
type-id = ["abs_denco/type-id", "denco_macro/type-id"]
type-id-murmur3 = ["abs_denco/type-id-murmur3", "denco_macro/type-id", "type-id"]
```

选择**默认开**，理由：

- `rpc_core_v1` 的类型头协议本来就默认 `TypePolicy::Strict`；`Data_Type_Id` 是线上契约的
  必需部分，而 denco 的 `type-id` 是 `no_std`、纯 `const`，没有运行期/体积代价。
- 默认关会保留 G-16 的失败模式：下游「忘了开」只能回到手写 ID 表，而这正是本轮要消灭的
  东西。默认开让「同一个 hash 契约」成为 workspace 的默认事实。
- 破坏面可控：blanket impl 只在 `T: TrHasTypeId` 时生效。已经手写 `impl TrDataTypeId`
  的下游**不会**因为默认开而冲突；只有「既 derive `TrHasTypeId` 又手写 `TrDataTypeId`」
  才冲突——那正是迁移时必须删掉的手写 impl。
- `mptp_im_demo` 因为 `rpc_core_v1` 用了 `default-features = false`（固定 compio 后端），
  必须显式加 `type-id`；这是有意的显式声明。

`type-id-murmur3` 隐含 `type-id`（与 `abs_denco` 的 feature 定义一致），并且是**显式**
opt-in：同一 workspace 只能启用一种 hash，默认绝不打开 Murmur。

**「只开一半」的可读错误**：proc macro 看不到下游 feature，`rpc_core_v1` 也无法在编译期
检测 `denco_macro/type-id`。能给出的最可读错误来自 denco 本身：

- 只开 `abs_denco/type-id`、没开 `denco_macro/type-id`：`#[derive(TrHasTypeId)]` 找不到
  派生宏（denco 的 `TrHasTypeId` 还带 `#[diagnostic::on_unimplemented]`，手写路径缺失时
  会提示同时开两个 feature）；
- 只开 `denco_macro/type-id`、没开 `abs_denco/type-id`：生成代码里的
  `abs_denco::type_id` 不存在，rustc 指出该模块被 `cfg` 掉。

不在 `rpc_core_v1` 里伪造「自动检测」；README 与 feature 注释写明必须同时开。

### 1.2 D2：保留 `TrDataTypeId`，用 blanket impl 桥接

```rust
#[cfg(feature = "type-id")]
impl<T: abs_denco::type_id::TrHasTypeId> TrDataTypeId for T {
    const DATA_TYPE_ID: DataTypeId = DataTypeId::from_nonzero_u64(T::TYPE_ID_64);
}
```

- 只使用 `TYPE_ID_64`：MPTP 线上 `Data_Type_Id` 是 `u64`；`TYPE_ID_128` / `TYPE_ID_32`
  不参与线上头（128 位可用于日志/注册表，32 位留给字段宽度本来就是 u32 的协议）。
- `DataTypeId` 仍是「非零 u64」的窄类型，不扩宽。
- 冲突边界：
  - 同一类型既 derive `TrHasTypeId` 又手写 `impl TrDataTypeId` → 编译期 conflicting
    implementations，迁移时必须删除手写 impl；
  - 需要固定旧 ID / 打断递归的类型：**不要**手写 `TrDataTypeId`，改为手写
    `impl TrHasTypeId`（三个 const 都显式给值，或 64 位用 `path_id_64`），这样仍是单一
    事实来源；
  - feature 关闭时 blanket impl 不存在，手写 `TrDataTypeId` 的老代码原样编译。

### 1.3 D3：`DataTypeId` 的编译期非零构造

新增：

```rust
impl DataTypeId {
    pub const fn from_nonzero_u64(raw: u64) -> Self {
        if raw == 0u64 { panic!("Data_Type_Id 不能为 0"); }
        DataTypeId(raw)
    }
}
```

- `new` 保持返回 `Option`（旧 API 不变）；`from_nonzero_u64` 给 `const` 消费方用，
  `0` 在编译期 panic（const 求值报错）。
- 命名取 `from_nonzero_u64`：语义直白，也不暗示它只服务于 denco。
- 不新增 `from_has_type_id` 泛型 const 构造：`TrHasTypeId::TYPE_ID_64` 是关联常量，
  泛型 const 构造会引入不必要的 trait bound 面；blanket impl 里直接调 `from_nonzero_u64`
  即可。

### 1.4 D4：facade 转出

`rpc_core_v1::stream` 在 `type-id` 开启时转出：

- `TrHasTypeId`（trait）、`denco_type_ids!`、`check_unique`、`TypeIdEntry`；
- `preludes` 额外转出 `TrHasTypeId` / `denco_type_ids` / `check_unique`。

**不转出 `#[derive(TrHasTypeId)]`**：denco 的 derive 生成代码硬编码 `abs_denco::...`
路径（见 `denco_macro/src/type_id_.rs`），所以用 derive 的 crate **必须**直接依赖
`abs_denco`。转出这个 derive 会暗示「只依赖 `rpc_core_v1` 就能 derive」，是错的。
业务 crate 仍照旧 `use denco_macro::TrHasTypeId;`。

### 1.5 D5：线上兼容——接受破坏

沿用 denco dev-note §8.10 的结论：**接受 `Data_Type_Id` 破坏**。

- 删除 `im_protocol/src/ids.rs` 与 9 个手写 `impl TrDataTypeId`；
- 全部 DTO 改 derive `TrHasTypeId`，线上 ID 由结构化指纹决定；
- 旧 / 新客户端不兼容：同一端点两端必须用同一 denco rev / feature / hash；
- README / DESIGN §4.4.1 / ACCEPTANCE G-16 / 迁移 note 同步更新。

**ID 变化规则**（denco dev-note §10.3 / §8.6）：

| 变化 | 是否改 ID |
| --- | --- |
| 字段名 / 字段类型 / 字段顺序 | 改 |
| 变体名 / 变体载荷 | 改 |
| 枚举变体重排（名字不变） | 不改 |
| `#[denco(rename)]` 后的线上名 | 改 |
| `transparent` | 等于内层 |
| `Box` / `Rc` / `Arc` / 引用 / `Cow` | 转发到内层 |
| `String` / `str` | 等价 |
| `alias` / `default` / `with_struct_map` | 不改 |
| `skip_encoding` / `skip_decoding` | 改（方向位参与） |

### 1.6 D6：hash / 版本契约

- 默认 FNV-1a 32/64/128；`type-id-murmur3` 切到 Murmur3 x86_32 / MurmurHash64A / x64_128。
- 同一 workspace 只能启用一种；`--all-features` 下 Murmur 覆盖 FNV。
- `TYPE_ID_VERSION = 1`、`HASH_ALGORITHM`（`"fnv1a"` / `"murmur"`）、
  `module_path!()` 所在的 crate 名都属于线上契约；跨进程两端必须使用同一 denco rev /
  feature / hash。
- 不修改 denco 的哈希输入或版本；它已经发布为兼容性契约。

### 1.7 D7：冲突检测与 golden

- `im_protocol` 用 `denco_type_ids![...]` 导出全部线上 DTO，用
  `check_unique(entries, 64)` 替换原来的 `BTreeSet` 手写唯一性测试；
- 增加 `im_protocol` 的 64 位 golden（9 个 DTO），按 `HASH_ALGORITHM` 分支：
  demo 固定 FNV，所以 FNV 值是硬契约，Murmur 分支只断言「非零且互不相同」；
- `rpc_core_v1` 的 examples / tests 删除硬编码 `0x2001`–`0x2003`，改用
  `T::DATA_TYPE_ID` 或 derive 生成；
- registry 形态：**每 crate 导出清单 + workspace 测试汇总**，不做 link-time 自动收集；
- `check_unique` 按消费方实际使用的宽度检查；MPTP 用 64。

### 1.8 D8：`rpc_svc_macro`——只提案，不实施

见 §6。本期不动宏语法、生成形状、`rpc_core_v1` 的 typed unary helper。A-08 仍 `GAP`。

### 1.9 D9：Push / trait code-first

- Push 端点：本期不做 typed 注入；`#[rpc(push = ...)]` 不新增任何 `typed` 语义；
- trait code-first（`#[rpc(service)]` / `#[rpc(impl_of)]`）尚未实现，本轮最多写提案，
  不实现；`__Req_*` 隐藏结构体的 derive 留到 trait 宏落地时一起做。

## 6. `rpc_svc_macro` 提案（本期不实施）

### 6.1 类型来源与破坏面

宏在 controller / 自由函数 / Pull 处能拿到的类型：

| 位置 | 请求类型 | 响应类型 | Pull item |
| --- | --- | --- | --- |
| controller `#[rpc(call)]` | 唯一 body 参数 | `Result<T, E>` 的 `T` | — |
| controller `#[rpc(pull)]` | 路径参数（不进 body） | — | `impl TrAsyncIterator<Item = T>` 的 `T` |
| 自由函数 | 同上 | 同上 | 同上 |

对上述类型加 `TrDataTypeId` bound 会破坏「请求/响应类型没有 ID」的现有用户。因此必须
**opt-in**，不能默认给所有端点加 bound。

### 6.2 opt-in 候选

| 候选 | 形状 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A（推荐） | impl 级 `#[rpc(interface = "im/v1", typed)]`，方法级 `#[rpc(call = "x", typed)]` 可覆盖 | 一次声明整组端点；方法级仍可细调 | 新增属性参数；`typed` 对 Pull / unary 生成内容不同，需要文档 |
| B | 仅方法级 `#[rpc(call = "x", typed)]` / `#[rpc(pull = "x", typed)]` | 最细粒度、破坏面最小 | 每个方法重复；controller 用户容易漏 |
| C | 独立 `#[rpc(types = auto)]` / `#[rpc(type_id)]` | 与访问方法解耦 | 两套属性容易互相矛盾；解析复杂 |
| D | 只对 `impl_of` 自动推导 | 零语法 | trait code-first 未实现；本期不可用 |

**推荐 A**：impl 级默认、方法级覆盖；解析上 `typed` 是 `bool` 标志，语义是「为这个方法
生成类型元信息并写响应类型头」。

### 6.3 生成内容（提案）

unary（`typed`）：

```rust
// 端点装配
.with_metadata(
    RpcDataTypeInfo::new(BodyCodec::MsgPack)
        .with_request_body(<Req as TrDataTypeId>::DATA_TYPE_ID)
        .with_response_body(<Resp as TrDataTypeId>::DATA_TYPE_ID)
        .with_accept(AcceptType::new(
            BodyCodec::MsgPack,
            Some(<Resp as TrDataTypeId>::DATA_TYPE_ID),
        )),
)
```

- 需要 `Req: TrDataTypeId`、`Resp: TrDataTypeId`；`()` 已有 denco impl（`TYPE_ID_64` 非零），
  所以 0 参方法也能 typed。
- 响应头需要 `rpc_core_v1::serving` 的 typed unary helper（例如
  `write_ok_typed_async`）或让 `write_ok_async` 接受 `&RpcDataTypeInfo`。这是公开 API
  变更，需单独立项。
- 客户端 typed unary helper（`call_endpoint_typed_async` / 让 `call_endpoint_async`
  接受 `RpcDataTypeInfo`）同样是公开 API 变更。

Pull（`typed`）：

- handler 改用 `typed_response(...)` + `write_stream_item_async`，写响应 `Body_Type` +
  `Data_Type_Id`（item 类型）；
- 端点元信息写 `response_suffix` + `accept`。

顺带生成 `RpcEndpointInfo`（namespace / service / operation / pattern）是独立问题
（G-12 说明 controller 没有三元组语义），本提案不捆绑。

### 6.4 Push / trait code-first

- Push 本期不做：`#[rpc(push = ...)]` 已经能生成端点，但 typed 需要 `request_suffix` +
  `response_body` 的推导规则与「请求后缀 item 类型」的 bound；没有真实需求前不新增语义。
- trait code-first：`__Req_*` 隐藏结构体需要 `#[derive(TrHasTypeId)]`，响应类型需要
  `TrDataTypeId`；trait / `impl_of` 尚未实现，留到那时一起做。

### 6.5 A-08

本期只完成 core + demo。**A-08 仍为 `GAP`**：宏生成的端点不挂 `RpcDataTypeInfo`，
Pull handler 仍只写 chunk。剩余提案就是 §6.2–§6.3；落地时还需要 typed unary / typed
response 的公开 helper 提案与确认。

### 6.6 2026-11-14 讨论：trait 与 controller 的分工，以及统一请求类型

**问题**：如果 code-first trait 能定义客户端 / 服务端契约，controller / 自由函数这些
“定义 RPC”的方式还要不要保留？`rpc_svc_macro` 的 type-id 职责是否只是“Call 以外的
访问类型，如果提到 type id，两端都可辨认”？

**结论一（修正）：controller 不退役，trait 与 controller 是两种互补的请求形态。**

- **trait（code-first）适合“业务数据优先”的方法**：`Call`（以及 body 中心的 `Post`）
  的请求 / 响应就是业务 DTO；trait 方法签名天然把两端绑定到同一组可命名类型，能生成
  客户端代理，编译器还能检查实现是否匹配。
- **controller 适合“请求上下文优先”的方法**：`View` / `Head` / `Drop`，以及需要同时读
  路径参数、header、body 的 `Post`。trait 方法签名本身**表达不了参数的来源**（这个
  `u64` 来自路径还是 header？body 是哪一个？），强行塞进 trait 只会退化成
  `fn x(&self, req: ...)`，并不比 controller 自然。
- 两种形态最终都编译成 `mptp_serving` 的 per-method `Endpoint` + `TrEndpointHandler`，
  可以混挂在同一个 `RadixRouter` 上；controller 不是 legacy，而是另一种入口。

**结论二：统一请求类型是把“上下文优先”写自然的关键。**

建议在 `rpc_core_v1` 提供一组 handler 侧信封（名称待定，下面是形状）：

```rust
pub struct RpcRequest<'a, M, P = (), T = ()> {
    // M: 访问方法标记（View / Post / Drop / ...）
    // P: 路径参数（typed struct 或 PathParams）
    // T: 已解码的 body；View/Drop/Head 为 ()
    pub path: P,
    pub headers: &'a Headers,
    pub body: T,
    // method / cancel / allocator 等
}

pub type ViewRequest<'a, P = ()> = RpcRequest<'a, View, P, ()>;
pub type PostRequest<'a, P = (), T = ()> = RpcRequest<'a, Post, P, T>;
pub type DropRequest<'a, P = ()> = RpcRequest<'a, Drop, P, ()>;
pub type PullRequest<'a, P = ()> = RpcRequest<'a, Pull, P, ()>;
pub type PushRequest<'a, P = (), T = ()> = RpcRequest<'a, Push, P, T>;
```

它们提供：

- `req.path` 或 `req.path::<u64>("id")`：从路由规则提取 `{id}`（前者编译期校验，后者
  运行期解析；见 §“前置与风险”）；
- `req.header("X-...")` / `req.headers()`：从 header 提取参数；
- `req.body`：`PostRequest<T>` / `PushRequest<P, T>` 在进 handler 前已用 denco 解码成
  `T`（`decode_body_async` 要求 `TrDecodableOwned`，是 owned 值，无 arena 泄漏）；
- `req.method()` / `req.cancel()`：访问方法标记与请求级取消令牌。

**关键点：信封的泛型参数就是线上类型。** `PostRequest<_, T>` 的 `T` 是请求 body，
`PushRequest<_, T>` 的 `T` 是请求 suffix item；响应类型来自 handler 返回类型
（`Result<R, E>` 或 `impl TrMayCancel<MayCancelOutput = RpcResult<R>>`），Pull 的 item
来自返回的迭代器。因此宏可以**从 handler 签名**推导完整 `RpcDataTypeInfo`，不需要额外
的属性写死 ID。信封本身是 handler 侧上下文，**不是线上类型**：不要给它 derive
`TrHasTypeId`，也不要把它写进 `Data_Type_Id`。

**结论三：controller 的客户端不必依赖 server impl。**

统一信封放在 `rpc_core_v1`（不能放 `mptp_serving`：它不做 denco 解码），客户端用**同一组
信封**构造请求；路由常量、DTO、信封类型放在共享协议 crate，客户端用通用 typed helper：

```rust
let user: User = client.view("users/{id}", ViewRequest::new().path("id", 42)).await?;
let room: RoomSummary = client.post("rooms", PostRequest::new(CreateRoomRequest { .. })).await?;
let ack: BackfillAck = client.push("rooms/backfill/42", PushRequest::new(message_stream)).await?;
```

这些 helper 按访问方法写请求头（`Data_Type_Id` / `Accept`）并校验响应头，类型 ID 来自
同一个 `T` / `R`。客户端仍然要写路径常量，但没有第二套 DTO、也没有第二套 ID；这正好
回答“客户端怎么发”的问题。对 `Call` 业务数据，trait 代理仍是更强形式（命名方法、无
字符串路径）；两者不是替代关系。

**分工表**

| 形态 | 适合 | 客户端 | 类型元信息来源 |
| --- | --- | --- | --- |
| `#[rpc(service)] trait` + `#[rpc(impl_of)]` | `Call` / body 中心的 `Post` | 生成的 trait 代理（协议 crate） | trait 方法签名 |
| controller + `XxxRequest` | `View` / `Head` / `Drop` / 上下文型 `Post` | 通用 typed helper + 共享路由常量 | 信封泛型 + 返回类型 |
| Pull / Push | 流式端点 | typed Pull / Push helper | 信封泛型 / 返回 item |
| 手写 `TrEndpointHandler` | 动态路由 / 自定义头 / 完全控制 | 手写 | 手写 `RpcDataTypeInfo` |

**职责重述**：`rpc_svc_macro` 的职责不是“给旧形态补 type id”，而是**从 handler 的
请求信封泛型与返回类型生成每个端点的完整类型元信息，并让客户端用同一组类型发出请求**：

| 访问方法 | 请求方向 | 响应方向 |
| --- | --- | --- |
| `Call` / `Post` | body 类型 + 可选 `Accept` | body 类型 |
| `View` | 无数据头 | body 类型 |
| `Pull` | 无 `Data_Type_Id`；codec + 必需 `Accept`（strict） | suffix item 类型 |
| `Push` | suffix item 类型 + 可选 `Accept` | body 类型（可无） |
| `Head` / `Drop` | 无数据头 | 无数据头 |

- **可辨认**：两端从同一共享类型（信封泛型 / 返回类型）、同一 denco rev / feature /
  hash 生成同一个 ID；
- **已记录**：宏生成 `denco_type_ids!` 清单 + `check_unique` + golden，属于测试 /
  装配期证据，不是运行期全局注册表；
- **不只是 ID**：还要有方向 / 角色、`Body_Type` codec、`Accept` 与 `TypePolicy`；否则
  ID 正确但放错头，仍然是 400 / 406；
- **同一份元信息**：trait 形态在协议 crate 生成 `const INFO: RpcDataTypeInfo`，server
  `with_metadata` + 响应头、client 请求头 + 响应校验都引用它；controller 形态由宏从
  信封生成同一份 `INFO`，server 挂元数据，client helper 从同一组泛型重建同样的头；
- **客户端位置**：trait 代理在协议 crate（或 protocol crate 的 client feature）生成，
  不能留在 server impl 的隐藏模块（修 G-08）；controller 的通用 helper 在 `rpc_core_v1`。

**前置与风险**

1. **信封类型识别**：proc macro 只能按语法路径识别 `ViewRequest` / `PostRequest`，
   别名 / 重导出会失效。需要显式属性（如 `#[rpc(request = view)]`）或要求写全路径；
   这是公开语法变更，需先提案。
2. **路径参数**：两条路线——(a) 宏按 pattern 生成 typed path 结构体，编译期校验
   `{name}` 与字段；(b) 运行时 `req.path::<T>("id")`。前者更安全但把生成类型带进
   handler 签名（可见性问题），后者更灵活但错误在运行期。建议先做 (b)，(a) 作为后续
   增强。
3. **body 预解码 vs 懒解码**：`PostRequest<T>` 预解码最利于类型 ID 与编译期检查；如果
   做成 `req.body::<T>()` 懒解码，宏就拿不到 `T`，必须额外声明。建议信封泛型显式写
   body 类型。
4. **Pull / Push 的 item 类型**：`impl TrAsyncIterator<Item = T>` 在返回位置不可命名，
   信封泛型（`PullRequest<Item>` / `PushRequest<Item, _>`）或关联类型是更稳的表达；
   需要在扩展 code-first / 信封设计时定。
5. **信封不是线上类型**：不要 derive `TrHasTypeId`，不要把它当 body；它只是 handler
   的上下文。
6. **兼容性**：新增信封是 additive；现有 controller / 自由函数签名不变，不破坏现有用户。
7. **跨语言**：trait / 信封都是 Rust 侧；非 Rust 端仍需 IDL / manifest，类型 ID 只做
   一致性校验。

> 这一节修正了本文件上一版“controller 契约角色退役”的判断。controller 与 trait 的
> 分工是**请求形态**的分工，不是新旧替代。

## 8. 风险

1. **默认开 + 下游既 derive 又手写**：编译冲突，但错误信息明确（conflicting
   implementations），迁移文档写明删除手写 impl。
2. **`--all-features` 切 Murmur**：金标准必须按 `HASH_ALGORITHM` 分支；demo 的 golden
   只在 FNV 下是硬契约。
3. **denco rev 漂移**：`mptp_rpc` / `mptp_im_demo` 的 lock 必须一起升；跨进程两端必须
   同 rev / feature / hash。
4. **`type-id` 关闭时手写 ID 仍可能冲突**：这是显式 opt-out 的代价，文档写清「生产环境
   不要关」。
5. **宏集成未做**：A-08 仍 GAP，不能声称「宏会自动挂类型元信息」。
