## 0. 摘要与目标

一句话：**客户端行为收敛到“方法糖 + 类型状态 builder + 显式半关闭 / 取消”，服务端从
“单 handler 自己决定一切”升级为“端点 + 元数据 + 中间件 + 处理器”，同时把 MPTP 协议层与
smux 传输绑定的耦合拆开，让 `mptp_quic` 或任何第二个传输可以零改动复用协议语义。**

三个目标：

1. **规范客户端行为**：让“怎么发请求、怎么收回复、怎么结束”有唯一的正确写法，而不是
   方法糖与裸 `MptpSession` 原语并存、调用者各自为政；
2. **支撑高自由度服务端框架**：把 [`mptp-serving-framework-20261112-1845.md`](mptp-serving-framework-20261112-1845.md)
   里的端点 / 元数据 / 中间件 / 处理器落到 `rpc_core_v1`（或独立 crate），`mptp_smux`
   不再承担路由；
3. **QUIC 纳入 `abs_smux` 抽象**：`abs_mptp` 继续依赖 `abs_smux`（它本就是多流连接 / 子流
   的抽象层）；方向是把 QUIC 做成 `abs_smux` 的第二个实现，而不是解耦 `abs_mptp` 或再抽
   一层 `abs_mux`。

## 1. 现状盘点（今天 API 的问题）

### 1.1 服务端：单 `TrServeHandler` 无法承载分层 / 中间件 / 元数据

`mptp_smux::serving::TrServeHandler` 只给一个 `handle_async(method, &mut ServingSession)`。
路由、鉴权、方法分派、404 / 405 兜底、横切策略（超时 / 限流 / 类型校验）**全堆进这一个
handler**。应用要么手写一大坨 `match method` + `match location`，要么把 `rpc_core_v1::Router`
的“路径前缀 → handler”静态表塞进来。二者都做不到：

- 端点携带元数据、中间件按元数据执行策略；
- 路由只匹配、处理器只关心业务；
- 运行期增删路由（`rpc_core_v1::Router` 是装配期消费式构建，`tlist` 静态列表）。

### 1.2 客户端：方法糖与裸会话并存，行为不够规范

`MptpClient` 同时暴露两套入口：

- 方法糖 `head/view/post/drop/push/pull/invoke` → `RequestBuilder`（类型状态，已经是对的
  方向）；
- 裸入口 `request_to_dock_async` / `request_to_dock_with_prep_async` → `MptpSession`，
  调用者要自己按 `send_req_body → send_req_suffix → close_req → recv_resp_prefix → …`
  的次序驱动。

后者是 escape hatch，但当前**没有一个统一的、带类型状态的“会话完成”路径**把半关闭、
取消、超时、错误分类收拢起来；`Push` 的请求后缀、`Pull` 的回复后缀这些“流”语义，也还没有
一个像 `SuffixStream` 那样好用的客户端读取视图（服务端已有无限写 `SuffixStream`，客户端
只有裸 `RespSuffixRead`）。

### 1.3 传输层现状：`abs_mptp` 依赖 `abs_smux`（有意为之）

`abs_mptp::client::config` 与 `abs_mptp::serving::config` 直接 `use abs_smux`，配置里的
`MuxConn`、`Dock`、`DockBinding`、`ChannelHandle` 都来自 `abs_smux`。**这个依赖不是要消除
的耦合**：`abs_smux` 本就是「多流连接 + 子流 + 半关闭 / reset」的抽象层，`smux_v1` 只是它
的第一个实现。要支持 QUIC，方向是扩展 `abs_smux` 让 QUIC 成为第二个实现，而不是解耦
`abs_mptp` 或再抽一层 `abs_mux`。

### 1.4 连接状态 owner 缺位：servlet 不持有 connection / state

`MptpServlet<C, H>` 只有 `handler_` 与 `PhantomData`，**不持有** binding、不持有
per-connection 状态。文档说“一个 servlet 只服务一条连接”，但构造函数没有把它表达出来；
per-connection 状态（join 身份、订阅表、保活）只能由 handler 闭包捕获。一旦把同一个 servlet
复用到两条连接，per-connection 状态就会串。demo 靠“每条连接新建一个 handler”来规避，这是
约定而非类型保证。

### 1.5 RPC 层路由与 MPTP 层路由脱节

`rpc_core_v1::serving::Router`（顶层前缀路由）与 `RpcRouter<I,S>`（interface 级内联路由）
是两套“路径 → 目标”机制，各自持有 `matchit_route` 索引表；`Router` 走 `TrServeHandler`，
`RpcRouter` 走旧的 `TrReqHandler`，中间还隔着 `LegacyHandler` 适配。分层 router
（[`router-20261106-0112.md`](router-20261106-0112.md)）设计早已存在，但**尚未实施**；
当前是旧形状在跑。

## 2. 目标形态（结合 BLUEPRINT + ASP.NET 设计）

### 2.1 分层图

```text
应用 / RPC：协议端 crate、service 实现、资源 handler（只写业务）
      ▲
      │  endpoint + metadata + middleware + terminal handler
mptp_serving / 服务端框架（本文 §4 方向 B）
      ▲
      │  会话驱动：前缀 → 体 → 后缀 → 半关闭 → 收尾（SessionCore，两端共享）
mptp_smux（smux 绑定 + 会话驱动；未来 QUIC 绑定复用 SessionCore）
      ▲
      │  传输抽象：连接 / 子流 open·accept、half-close / reset、寻址、内存、流控
abs_smux（trait）◀── 实现：smux_v1（当前）/ QUIC（候选）
      ▲
mptp_wire（线格式）      abs_mptp（协议形状，依赖 abs_smux）
```

### 2.2 客户端目标

```rust
// 唯一推荐写法：方法糖 + 类型状态 builder，一条链完成。
let resp = client
    .post("/api/v1/goods")
    .header(StdHeaderKey::Data_Type_Id, type_id_text)
    .body_bytes(&encoded)
    .timeout(Duration::from_secs(5))          // 拟新增：每请求超时
    .send_async()
    .may_cancel_with(token)
    .await?;

// 流式：Pull 的回复后缀是一个可逐条消费的流视图（拟新增）。
let mut stream = client.pull("/stream/logs").send_stream_async().await?;
while let Some(chunk) = stream.next_chunk_async().await? { .. }
```

### 2.3 服务端目标

```rust
let top = Arc::new(RadixRouter::<SrvCfg>::new(AppRootEndpoint));
top.view::<FeedParams>(FeedView::new(...)).with_metadata(Timeout(..))?;
top.pull::<FeedParams>(FeedPull::new(...)).with_metadata(Authorize { .. })?;

let pipeline = Pipeline::new()
    .use_middleware(TimeoutMiddleware)
    .use_middleware(AuthMiddleware);

let server = MptpServlet::new(RouterApp::new(top, pipeline));
```

处理器 `FeedView` / `FeedPull` 只实现 `TrEndpointHandler`，不知道路由与中间件。

### 2.4 运行环境与内存纪律

整套框架的目标运行环境是 **`#![no_std]` + `alloc`**（与 `mptp_wire` / `abs_mptp` /
`mptp_smux` / `matchit_route` 一致）。任何堆上对象都显式说明来源，三条路只走其一：

1. **带分配器参数**：`Vec<T, A>` / `Box<T, A>` / `BTreeMap<K, V, A>` 带 `A: Allocator`；
   `String` 一律用 `abs_str::String<A>`（`new_in` / `from_str_in` / `with_capacity_in`）；
2. **进域**：生命周期归某个 owner 的堆对象用 `sw-scope` 的 `Scope` / `ScopeStr` /
   `Retain<T>` / `Owning<T>`，或 `bumpalo` 的自有 arena（`matchit_route` 已这么做）；
3. **借用**：匹配 / 请求生命周期内能借用的借 `&str`（路径参数借 `matchit_route` 的
   `Params`，不 owned 复制）。

禁止 `std::sync::OnceLock` / `RwLock` / `Mutex` 与不带分配器的 `String` / `Vec` / `Box`。
详细落到各类型的内存策略见
[`mptp-serving-framework-20261112-1845.md`](mptp-serving-framework-20261112-1845.md) §6.8。

## 3. 优化方向 A：客户端行为规范化

### 3.1 收敛到“方法糖 + 类型状态 builder”

保留现有 `RequestBuilder<'_, C, B, S>` 的类型状态设计（它已经把“体 / 后缀有没有、是定长
还是分块”编码进类型），继续做三件事：

1. **`send_async(self)` 成为唯一终结入口**，其内部已经按 `body → suffix → half-close →
   recv_prefix` 的次序驱动会话；逐步把裸 `request_to_dock_*` 降级为 `#[doc(hidden)]` /
   `deprecated`，只有需要**自定义 ring 准备**或**自定义 dock**时用专门入口，而不是让每个
   调用者自己重写一次会话驱动；
2. **把“体 + 后缀”读成一个顺畅的连续路径**：`Response::body_async` / `suffix_async` 已
   存在，但中间还隔着一个“先 `drop` 体视图再取后缀”的手动步骤；应把它收敛成一次取用、
   借用检查保证“体没读完不能进后缀”；
3. **给客户端补一个后缀流读取视图**：对应服务端已有的 `SuffixStream`（无限写），客户端
   补一个 `SuffixRead` 的“逐 chunk 读”接口（`next_chunk_async`），让 `Pull` 的订阅消费与
   `Push` 的上传一样顺手，而不是把裸 `RespSuffixRead` 交给调用者。

### 3.2 显式化半关闭 / 取消 / 超时

- **半关闭**：`MptpSession::close_req_async` 已存在，保持“丢 tx 即半关闭”的语义；`Response`
  读完后框架侧自动走完收尾，调用者无需手动 `finish`；
- **取消**：所有公开异步方法继续用 `gen_may_cancel_future` 封装、继续 `TrMayCancel`，不假定
  `NonCancellableToken`；
- **超时**：给 `RequestBuilder` 增一个可选 `.timeout(Duration)`，在会话外层用 `RequestCancel`
  派生子令牌实现，超时返回结构化错误（不再要求每个调用者自己包一层 `timeout`）。

### 3.3 统一错误分类与 source 保留

`ClientError` 已经分成 `Cancelled / Transport / Protocol / State` 四类。继续：

1. 传输错误保留**具体来源**，不再只存 `String` 描述（见 [`mptp-smux-20261110-0730.md`](mptp-smux-20261110-0730.md)
   §5.4 的缺口）；若泛型化代价过大，至少在文档与 `Display` 里把“连接断 / 协议错 / 取消”
   三者的可分辨性讲清楚；
2. 超时、主动取消、对端 reset 各走各自的错误变体，不折叠成一个 `Transport(String)`。

## 4. 优化方向 B：服务端框架高自由度

### 4.1 引入 endpoint / metadata / middleware

按 [`mptp-serving-framework-20261112-1845.md`](mptp-serving-framework-20261112-1845.md)
实施：路由产 `Endpoint + RouteValues`，`EndpointMetadata` 挂类型化标记，`TrMiddleware` 按
元数据执行策略，`TrEndpointHandler` 只写业务，收尾统一。落地位置：`rpc_core_v1::serving`
（或独立 `mptp_serving` crate），**不进 `mptp_smux`**。

### 4.2 分层 router 落地

实施 [`router-20261106-0112.md`](router-20261106-0112.md) 的 `RadixRouter`：每个 router
自根、两个添加入口（`bind_handler` / `bind_router`）、每层根 handler、`MethodSet` 参与匹配、
类型化路径参数（`TrRouteParams` + derive 编译期校验）、运行期增删。这一步是“端点 + 元数据 +
中间件”能跑起来的骨架，优先级最高。

### 4.3 连接作用域状态 owner

把“一连接一 servlet”从**调用约定**升级为**类型不变量**：

```rust
pub struct MptpConnection<C, H, S = ()> {
    binding_: DockBinding<C>,   // 拥有 binding，不可复用到别的连接
    servlet_: MptpServlet<C, H>,
    state_: S,                  // per-connection 状态，框架不解释
}
```

- 处理器与中间件通过 `MptpContext` 拿到 `&S`（共享借用，因为同连接可并发 session）；
- server 级共享资源（目录、订阅 hub）仍是装配者自己的 `Arc<..>`，**不**降为 connection 级；
- `mptp_quic` 复用同一形状：smux / quic 只提供不同的 binding / connection 类型与状态。

> 这与「QUIC 纳入 `abs_smux`」是同一个问题：先做对 connection scope，再谈第二个传输实现。

## 5. 优化方向 C：把 QUIC 纳入 `abs_smux` 的抽象范围

`abs_mptp` 依赖 `abs_smux` **不是要消除的耦合**：`abs_smux` 本来就是「多流连接 + 子流 +
半关闭 / reset」的抽象层，`smux_v1` 只是它的第一个实现。要支持 QUIC，方向不是再抽一层
`abs_mux`，而是**扩展 `abs_smux`，让 QUIC 成为它的第二个实现**。

### 5.1 不动的部分

- `abs_mptp` 继续依赖 `abs_smux` 的 trait（`TrConnection` / `TrDockBinding` /
  `TrChannelHandle` / `Dock`），`Dock`、ring 注入作为 `abs_smux` 的既有语义保留；
- `mptp_wire`、`abs_mptp` 的协议形状、`mptp_serving` 的服务端框架都不需要为 QUIC 改动。

### 5.2 需要扩展的部分（`abs_smux` 面向 QUIC）

| 关注点 | smux_v1（现状） | QUIC（需要对齐） |
| --- | --- | --- |
| 子流标识 | `Dock` | stream ID |
| 半关闭 / reset | smux FIN / RESET | FIN / `RESET_STREAM` / `STOP_SENDING` |
| 内存模型 | ring 注入（`TrPrepareRing`） | backend buffer / `Bytes` |
| 流控 | smux 窗口 | stream / connection 两级流控 |
| 错误映射 | smux 错误 | QUIC 错误码 |

这些差异按「QUIC 是 `abs_smux` 的第二个实现」处理：要么 `abs_smux` 的 trait 已足够（QUIC
适配成它的形状），要么给 `abs_smux` 补最小必要的接缝（例如让 ring 注入退化为可选的 buffer
抽象），而不是改造 `abs_mptp`。

### 5.3 会话驱动的复用

`mptp_smux` 的 `SessionCore`（前缀 → 体 → 后缀 → 半关闭 → 收尾）与传输无关，QUIC 绑定应当
复用它。是否抽成独立的 `mptp_session`，等 QUIC 绑定真正要写的时候再定；**当前不为了
“传输中立”而提前抽 `abs_mux`**。

验证判据：**用 QUIC（或 QUIC-like 的最小流适配器）作为 `abs_smux` 的第二个实现，跑现有
集成测试（405、body、suffix、cancel、half-close、慢订阅者），只新增 QUIC 绑定 + 新 config；
`mptp_wire`、协议 trait、`mptp_serving` 零改动**。

## 6. 分阶段计划

### P0：分层 router + 端点骨架（新增，不破坏）

- 在 `rpc_core_v1::serving` 落地 `RadixRouter`（`TrRouter` / `TrRouteMatcher` /
  `TrRouterExt` / `MethodSet` / `TrRouteTarget` 或直接 `Endpoint`），复用 `matchit_route`；
- 旧 `Router` / `RpcRouter` 标 `deprecated`，与新骨架并存一版；
- 单测覆盖：handler 规则匹配 / 冲突、子 router 递归、根 handler 兜底、方法糖、类型化参数。

**验收**：新 API 可编译，最小 echo 请求走通，旧测试不回归。

### P1：服务端切换 + demo 迁移

- `MptpServlet` 装配切到分层 router；两个 demo 删本地 router，改用 `RadixRouter`；
- 未命中从“丢 channel”改为“本层根 endpoint 写 404 / 405”；
- 旧 `TrReqHandler` 经 `LegacyHandler` / `ReqHandlerTarget` 无改动接入。

**验收**：两个 demo 的 e2e 通过；`mptp_cs_smoke`（仓库外）迁移后 11 条 RPC 回归通过。

### P2：端点元数据 + 中间件链

- 按服务端框架设计落地 `EndpointMetadata` / `TrMiddleware` / `Pipeline` /
  `MptpContext` / `TrEndpointHandler`；
- RPC 的 `service` 收敛为“只接受 `Call`、带 `AcceptType` 元数据、handler 做 body enum 分派”
  的端点；`#[rpc]` 宏生成物不改，装配用 `rpc_interface` 收敛；
- 中间件先做 `Timeout` / `Authorize` / `TypeCheck` 三个示范。

**验收**：鉴权短路写 401、超时写 408/504、类型不匹配写 406，均不进处理器；处理器代码不含
任何路由 / 中间件概念。

### P3：客户端规范化 + 连接状态 owner

- `RequestBuilder` 增 `.timeout`；`Response` 增“体 + 后缀”连续读取与客户端后缀流读视图；
- 把裸 `request_to_dock_*` 降级为 `#[doc(hidden)]`，普通调用者只用方法糖；
- `MptpConnection<C, H, S>` 落地，处理器 / 中间件拿 `&S`；迁移 demo 的 per-connection 状态。

**验收**：两条并发 `Pull` + 一条 `Call` 互不阻塞；运行期增删资源后客户端可见；in-flight
长流在 grace 内结束；取消 / 超时 / 半关闭行为有端到端用例。

### P4：QUIC 纳入 `abs_smux` + 清理

- 把 QUIC 做成 `abs_smux` 的第二个实现（必要时先给 `abs_smux` 补最小接缝：可选的 buffer
  抽象、FIN / `RESET_STREAM` 语义）；`abs_mptp` 继续依赖 `abs_smux`，不抽 `abs_mux`；
- 会话驱动（`SessionCore`）按需复用，`mptp_session` 是否抽取等 QUIC 绑定时再定；
- 清理 `abs_mptp_smux`（未使用层）与 `x_deps` 里的隐式 API 面；
- 更新 `DESIGN_BLUEPRINT.md`、`preludes`、模块文档；旧 `Router` / tlist 机器删除。

**验收**：用 QUIC（或 QUIC-like 流适配器）作为 `abs_smux` 第二个实现跑现有集成测试，只新增
QUIC 绑定 + config，不改 `mptp_wire` / 协议 trait / `mptp_serving`。

## 9. 英文摘要

This note is the forward plan for optimizing the existing MPTP/SMUX API. Client behavior
converges on per-method sugar over one type-state `RequestBuilder` with explicit
half-close, cancellation and per-request timeout, plus a client-side suffix read view for
`Pull`/`Push`. The server moves from a single `TrServeHandler` that does everything to the
ASP.NET-Core-style separation designed in the companion note: routing produces
`Endpoint + RouteValues`, endpoints carry typed metadata, an ordered middleware chain runs
policies by metadata, and terminal handlers only do business. The layered `RadixRouter` is
implemented first as the backbone, then metadata/middleware land on top, and
`MptpConnection<C, H, S>` makes per-connection state an explicit, type-checked owner.
Finally, the transport direction is clarified: `abs_mptp` keeps depending on `abs_smux`
(which is already the multi-stream abstraction layer); supporting QUIC means making QUIC a
second implementation of `abs_smux`, not decoupling `abs_mptp` or introducing an `abs_mux`.
The `SessionCore` driver is reused across bindings, and a separate `mptp_session` is only
extracted if the QUIC binding actually needs it.
