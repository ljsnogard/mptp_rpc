## 1. 目标与职责边界

`core_rpc_mptp_smux_v1` 从「MPTP 的 rmp-serde 实现 + 七种 access method 的双端形状」重构为
**RPC 语义层**：

- 客户端：通用 RPC client，把业务参数编码成请求体，并把回复解码成业务类型；
- 服务端：通用 router 与业务组织框架，把请求分派到 service 的具体关联函数；
- 两端共用：路径 / 服务 / 方法描述、错误与状态码映射、取消传播。

它**不再负责**：

- MPTP 前缀的线上格式（归 `mptp_smux::messaging`）；
- body 的定长 / 分块帧（归 `abs_mptp::messaging`）；
- 底层多流连接的建立、监听、ring 准备（归 `mptp_smux` / `abs_smux`）；
- 资源型 `Head/View/Post/Drop/Push/Pull` 语义（本期先做 unary `Call`）。

```text
┌──────────────────────────────────────────────────────────────┐
│ 协议端 crate（用户）                                         │
│   #[rpc(service = "...")] service trait + ApiV1 + body enum  │
├──────────────────────────────────────────────────────────────┤
│ core_rpc_mptp_smux_v1                                        │
│   RPC 契约 trait + 通用 client + router + body codec         │
├──────────────────────────────────────────────────────────────┤
│ mptp_smux                                                    │
│   前缀线格式、MptpClient/MptpSession、MptpServer、路径 Router│
├──────────────────────────────────────────────────────────────┤
│ abs_mptp / abs_smux / smux_v1                                │
│   协议形状、body 定长/分块、连接与子流契约                   │
└──────────────────────────────────────────────────────────────┘
```

## 2. 已确认的设计决策

### 2.1 方法路由：method 不出现在 path 上

路径只由 **interface + service** 组成：

```text
path = /{interface}/{service}
```

一个 service 的多个关联函数组织进一个 **body enum**。enum 的变体**直接携带函数参数**，
不再额外生成 `FindArgs` 之类的参数包：

```rust
// 生成在私有模块里，不对外公开。
#[allow(non_camel_case_types)]
enum GoodsCustomerCall<'a> {
    list,
    find { name: &'a str },
}

// 服务端解码用 owned 版本。
#[allow(non_camel_case_types)]
enum GoodsCustomerCallOwned {
    list,
    find { name: String },
}
```

约定：

- 变体名**直接使用函数名**，不强制转成 PascalCase；生成类型不是公开 API，命名规范可以放宽；
- 字段名**直接使用参数名**；多个参数就是多个字段，不合并成参数结构体；
- 无参数函数用 unit variant；
- 客户端 enum 可携带借用参数，服务端 enum 使用 owned 字段；
- 不支持泛型方法、变长参数与默认参数：这些无法用 enum 变体稳定表达；
- 变体标识需要稳定；建议 require 显式 `#[rpc(id = N)]`，否则 enum 重排会破坏线上兼容性。

因此：

- 一个 service 只需要一个路由目标；
- 服务端先解码 body enum，再 `match` 到具体函数；
- 客户端代理的每个方法构造对应变体；
- 方法名不参与路径匹配，同名方法冲突自然消失。

### 2.2 `services` 直接列 trait 名字

接口属性可以写成：

```rust
#[rpc(path = "api/v1", services = [GoodsCustomerService, GoodsAdminService])]
pub struct ApiV1;
```

属性宏把 `services` 解析成一组 `syn::Path`。这里**不再生成 marker / `Includes` 关系**：

- `#[rpc(service = "...")]` 直接往 service trait 里注入一个带缺省值的关联常量：

  ```rust
  pub trait GoodsCustomerService {
      const SERVICE_PATH: &'static str = "customer/goods";
      // ... 业务方法
  }
  ```

  实现者自动继承这个常量，不需要手写。

- 客户端代理由 service 宏直接对统一的 `ClientProxy` 生成：

  ```rust
  impl<C: TrRpcClientConfig, I: TrRpcInterface> GoodsCustomerService
      for ClientProxy<'_, C, I>
  {
      // 方法体由宏生成
  }
  ```

- 接口宏只需要生成 `ServiceSelector` 实现与服务端注册函数；服务端注册通过
  `<S as GoodsCustomerService>::SERVICE_PATH` 取得路径。

这样 `services = [TraitName, ...]` 就是真正的 trait 路径，不需要命名约定，也不需要额外的
marker 类型。

### 2.3 Selector + 极简代理

不再使用带 `Client` 包装层的 `RpcProxy`。客户端侧只保留一个极简代理：它在运行期**只持有一个
`MptpClient`**，interface 信息由零大小的类型参数携带。

```rust
pub trait ServiceSelector<C: TrRpcClientConfig> {
    type View<'a>
    where
        Self: 'a;

    fn select<'a>(client: &'a MptpClient<C>) -> Self::View<'a>;
}

pub struct ClientProxy<'a, C: TrRpcClientConfig, I: TrRpcInterface> {
    client: &'a MptpClient<C>,
    _iface: PhantomData<I>,
}

/// 让 `MptpClient` 直接获得 `call::<ApiV1>()`，不需要额外包一层 `Client`。
pub trait TrRpcClientExt<C: TrRpcClientConfig> {
    fn call<I: TrRpcInterface>(&self) -> ClientProxy<'_, C, I>;
}

impl<C: TrRpcClientConfig> TrRpcClientExt<C> for MptpClient<C> {
    fn call<I: TrRpcInterface>(&self) -> ClientProxy<'_, C, I> {
        ClientProxy {
            client: self,
            _iface: PhantomData,
        }
    }
}

impl<C: TrRpcClientConfig> ServiceSelector<C> for ApiV1 {
    type View<'a> = ClientProxy<'a, C, ApiV1>;

    fn select<'a>(client: &'a MptpClient<C>) -> Self::View<'a> {
        ClientProxy {
            client,
            _iface: PhantomData,
        }
    }
}
```

调用点：

```rust
use core_rpc_mptp_smux_v1::client::TrRpcClientExt;

let proxy = client.call::<ApiV1>();
let result = proxy.find("some keywords").await?;
```

说明：

- `ClientProxy` 运行期只有 `&MptpClient<C>` 一个字段；`I` 是零大小 marker，只用来携带
  `I::PATH`，不占运行期空间；
- 不再需要 `Client` 包装层、`base_path` 字段或每代理的 dock/header 状态；
- `C` 与 `I` 都只出现在类型定义里，调用点由编译器推导；协议端可以再提供别名：

  ```rust
  pub type MyProxy<'a> = ClientProxy<'a, MyClientConfig, ApiV1>;
  ```

- 如果不想引入扩展 trait，也可以让 core 提供一个零大小 newtype `RpcClient<C>(MptpClient<C>)`
  并在它上面实现 `call`；代理内部仍然只持有 `MptpClient`。

- 取舍：一个 `ClientProxy<'_, C, I>` 会实现协议 crate 里的**所有** service trait，`I` 只负责
  路径，不在类型层约束「这个 interface 恰好包含哪些 service」。这与上面的讨论一致，换来的是
  显著更简单的 API。若以后确实需要接口级成员检查，再给 service impl 加回一个 marker 约束，
  不在 Phase 1 引入。

### 2.4 服务端注册

一个服务器可以同时注册多个 interface。每个 interface 的注册会为该 interface 下的每个
service 建立独立队列，并把 `interface path` / `service path` 插入两级 Trie：

```rust
let mut builder = RpcRouter::builder("/");

// ApiV1::workers 创建每个 service 的队列与具体 worker，返回一个具体类型的 worker 组。
let workers_v1 = ApiV1::workers(customer_impl, admin_impl);
builder.interface::<ApiV1>(workers_v1.routes());

let workers_v2 = ApiV2::workers(order_impl);
builder.interface::<ApiV2>(workers_v2.routes());

let router = builder.build();

// worker 组由使用者选择线程/运行时来驱动；core 不替使用者 spawn。
spawn(workers_v1.run());
spawn(workers_v2.run());
```

`ApiV1::workers(...)` 由接口宏生成，参数类型受 `services` 列表里的 trait 约束；它返回：

- `routes()`：每个 service 的 `SERVICE_PATH` 与 `Sender<RpcJob<C>>`，由 `interface` 注册进
  interface 下的 `ServiceTrie`；
- `run()`：由宏生成的**具体** future，内部 `join` 各 service worker；它不装箱，也不要求
  worker 实现额外的 dyn trait。

这样 `RpcRouter<C>` 本身不需要携带 service 集合类型，也不需要任何 per-interface 泛型。

### 2.5 `send_req_body_async` 的语义

`MptpSession::send_req_body_async` 收的是一个**体源**（`TrBuffRead`），并按**已经写出的
header** 决定用定长还是分块方式，把源搬运到子流发送半边。RPC 层应当提供体源，而不是绕过
会话状态机直接操作 channel。

因此 `MptpSession::tx_mut` / `rx_mut` 被删除：

- 会话应当独占收发半边，并维护状态机；
- 丢弃发送半边就是半关闭，丢弃接收半边就是关闭接收方向；调用者不需要直接操作它们；
- 需要「发送完请求后显式收尾」时，应增加**带状态的会话方法**，而不是暴露裸半边；
- 目前没有 workspace 内的调用者，删除不破坏现有代码。

### 2.6 服务端执行模型：interface/service 两级 Trie + 队列 worker（确定）

服务端不使用 `Pin<Box<dyn Future>>`，也不使用 `Box<dyn TrRpcServiceDispatch>`。`MptpServer`
在解码请求前缀之后，把 **channel 收发半边按值**交给 handler；handler 先做**两级路由**，再把
请求打包成 job 放进对应 service 的队列：

```text
MptpServer (I/O)
    │  location = /{interface}/{service}
    ▼
RpcRouter
    ├─ InterfaceTrie:  /api/v1 → ApiV1Entry
    │                     /api/v2 → ApiV2Entry
    └─ 每个 InterfaceEntry 内部：
         ServiceTrie: customer/goods → Sender<RpcJob<C>>
                      admin/goods    → Sender<RpcJob<C>>
    ▼
对应 service 的有界 mpsc
    ▼
service worker（只持有一个具体 service）
    │  解码 body enum → match 方法变体
    └─ 写回复 → 半关闭 tx → drain rx → 释放
```

一个服务器可以同时注册多个 service interface（`ApiV1`、`ApiV2`……）。分派顺序是：

1. 用 interface path 在 `InterfaceTrie` 中做最长前缀匹配；
2. 在命中的 interface 内部，用剩余路径在 `ServiceTrie` 中做最长前缀匹配；
3. 得到该 service 的 `Sender<RpcJob<C>>`，把 job 发进去；
4. worker 只负责自己那一个 service，不再做 service 级 `match`。

两级路由都是**运行期构建的 Trie**，由注册时的 path 插入，不由宏生成 match 分支。宏只负责
提供 `interface path` / `service path` 常量与注册入口。

`RpcJob` 是队列元素类型：

```rust
pub struct RpcJob<C: TrRpcServingConfig> {
    pub method: AccessMethod,
    pub location: String,
    pub headers: Headers,
    pub tx: ChannelTx<C>,
    pub rx: ChannelRx<C>,
    // cancel: 子令牌；server 关闭时用于取消排队中的 job
}
```

因此：

- `MptpServer` 不再在 handler 返回后 `drop(tx)` / `drain(rx)`；channel 的生命周期由 worker
  负责，收尾顺序仍是「写回复 → 半关闭 tx → 读完 rx → 释放」；
- `TrReqHandler::handle_async` 的 `chan_tx` / `chan_rx` 改为**按值**接收；
- handler 只做路由 + `send(job).await`，不等待业务完成；`serve_listener_async` 可以继续接受
  下一条子流；
- 有界队列提供背压：队列满时 `send` 等待；
- 每个 service 的 worker 只持有该 service 的具体实现，方法分派由 body enum 的 `match` 完成，
  没有 boxed future；
- worker 线程/运行时由使用者选择，core 只提供 `run_worker_async` 这类循环，不替使用者 spawn。

代价与约束：

- `ChannelTx<C>` / `ChannelRx<C>` 必须满足 `Send + 'static`；需要在配置或 handler 上显式约束，
  并加编译期断言；
- interface path 之间、同一 interface 内的 service path 之间需要定义重叠规则：建议 Phase 1
  要求互不为前缀，注册冲突直接报错；若允许重叠，匹配需要回退到更短前缀；
- Trie 的路径规范化（首尾 `/`、空段、重复 `/`）必须与客户端拼路径的规则一致；
- worker 的处理错误不再自动回传给 `MptpServer`；worker 负责关闭 channel，并通过日志/监控
  通道上报；
- 需要定义队列容量、worker 数量、优雅关闭（关闭队列 + 取消 job）与 job 的取消令牌；
- `TrReqHandler` 的签名变更会影响现有 demo/handler 实现，需要同步迁移。

## 4. Phase 1：先定契约

### 4.1 Interface 与服务描述

```rust
/// 一段稳定的 RPC interface 路径前缀；不含首尾 `/`。
pub trait TrRpcInterface {
    const PATH: &'static str;
}
```

service trait 不继承额外的 marker trait；`#[rpc(service = "...")]` 直接给它注入：

```rust
pub trait GoodsCustomerService {
    const SERVICE_PATH: &'static str = "customer/goods";

    fn find<'f>(
        &'f self,
        name: &'f str,
    ) -> impl TrMayCancel<'f, MayCancelOutput = RpcResult<Vec<GoodsInfo>>>;
}
```

body enum 由 service 宏生成在私有模块中，不进入公开 API。

### 4.2 客户端 selector 与极简代理

### 4.3 服务端：两级 Trie router + 每 service 队列

路由器本身就是 `TrReqHandler`，按 **interface → service** 两级 Trie 匹配；宏不生成 match
分支，只提供注册数据（path 与队列 sender）。

```rust
pub struct RpcRouter<C: TrRpcServingConfig> {
    base: String,
    interfaces: PathTrie<InterfaceEntry<C>>,
}

pub struct InterfaceEntry<C: TrRpcServingConfig> {
    path: String,
    services: PathTrie<ServiceEntry<C>>,
}

pub struct ServiceEntry<C: TrRpcServingConfig> {
    path: String,
    tx: mpsc::Sender<RpcJob<C>>,
}
```

`PathTrie<T>` 是按路径**段**组织的运行期 Trie：

```rust
impl<T> PathTrie<T> {
    pub fn insert(&mut self, path: &str, value: T) -> Option<T>;
    pub fn match_longest<'a>(&'a self, path: &str) -> Option<(&'a T, &'a str)>;
}
```

`match_longest` 返回命中的值以及剩余路径；它只按完整路径段回退，不做裸字符串前缀匹配，
因此 `/api/v10` 不会误命中 `/api/v1`。

分派流程：

```rust
let (iface, rest) = router.interfaces.match_longest(location)?;
let (service, _) = iface.services.match_longest(rest)?;

service
    .tx
    .send(RpcJob {
        method,
        location: location.to_owned(),
        headers: headers.clone(),
        tx: chan_tx,
        rx: chan_rx,
        // cancel
    })
    .await?;
```

- 一个服务器可以同时注册 `ApiV1`、`ApiV2` 等多个 interface；
- 每个 interface 内部再按 service 的 `SERVICE_PATH` 注册到 `ServiceTrie`；
- 每个 service 有独立的队列与 worker；worker 只持有该 service 的具体实现，不需要再做
  service 级分派；
- 方法仍由 body enum 的变体决定（`match`），因为同一 service path 下本来就有多个方法；
- 未命中 interface/service 时，router 自己写 404 并按序收尾，不把 channel 交给 worker。

worker 侧的分派仍然没有 boxed future：

```rust
pub trait TrRpcServiceDispatch<C: TrRpcServingConfig> {
    type DispatchAsync<'f>: TrMayCancel<'f, MayCancelOutput = Result<(), RpcServeError>>
    where
        Self: 'f;

    fn dispatch_async<'f>(
        &'f self,
        ctx: RpcCallCtx<'f, C>,
    ) -> Self::DispatchAsync<'f>;
}
```

worker 的 `RpcCallCtx` 持有 job 的 `tx` / `rx` / headers / location，并提供 typed helper：

```rust
impl<C: TrRpcServingConfig> RpcCallCtx<'_, C> {
    pub async fn decode_call_async<T: TrDecodableOwned>(&mut self)
        -> Result<T, RpcServeError>;

    pub async fn reply_ok_async<T: TrEncodable + ?Sized>(&mut self, value: &T)
        -> Result<(), RpcServeError>;
}
```

worker 在方法执行结束后统一做收尾：写回复 → 半关闭 `tx` → 读完 `rx` → 释放。整个路径没有
`Pin<Box<dyn Future>>`，也没有 `Box<dyn ServiceDispatch>`；interface/service 两级分派都由
Trie 完成，方法分派由 body enum 完成。

### 4.5 错误与状态码

```rust
pub type RpcResult<T> = core::result::Result<T, RpcError>;

pub enum RpcError {
    Transport(String),
    Encode(String),
    Decode(String),
    Remote { status: Status, body: Vec<u8> },
    Cancelled,
}
```

建议默认映射：

| 情况 | 状态码 |
|---|---|
| 成功 | `200 Ok` |
| 参数解码失败 / 请求不合法 | `400 BadRequest` |
| 服务或方法不存在 | `404 NotFound` |
| 不是 `Call` 访问方法 | `405 MethodNotAllowed` |
| `Data_Type_Id` 不匹配 | `406 NotAcceptable` |
| 业务 handler 报错 | `500 InternalServerError` |
| 未实现 | `501 NotImplemented` |
| 超时 | `504 GatewayTimeout` |

### 4.6 异步与取消形式（已确定：保留 `TrMayCancel`）

上面示例里的 `async fn` 只是讨论时的简写，**不改变取消契约**。项目保留
`gen_may_cancel_future` / `TrMayCancel`：

- service trait 方法返回 `impl TrMayCancel<'_, MayCancelOutput = RpcResult<T>>`；
- 客户端代理的产物由宏通过 `gen_may_cancel_future` 生成具名、可取消的 future；
- 服务端实现由用户按现有方式用 `gen_mcf2` 包装异步函数；
- 所有公开异步入口都把取消令牌继续向下传，不假定调用者不会取消。

`async fn` 不是可选项：它返回的 opaque future 没有 `may_cancel_with`，无法满足主动取消语义。

### 4.7 body codec

Phase 1 先固定 MessagePack（`mp_denco` + `abs_denco` 的 `TrEncodable` / `TrDecodable`），
不急着抽 `TrRpcCodec` trait。服务端按 `Headers::body_size()` / `Headers::is_chunked()` 选择
`LimitedReader` / `ChunkedReader`，客户端用 `RespBodyRead` 的 `try_into_*` 取读口。

### 11.2 关键决策：单一 owned body enum

原计划是「客户端 `Call<'f>` 借用版 + 服务端 `CallOwned` owned 版」。实际实现时发现
`denco_macro 0.1.0` 明确拒绝带生命周期参数的派生类型：

```text
denco derive 暂不支持带生命周期参数的类型
```

因此改为**客户端与服务端共用一个 owned body enum `Call`**。客户端在构造变体时把借用参数
转成 owned 字段：

| 参数 | body enum 字段 | 客户端转换 | 服务端调用 |
|---|---|---|---|
| `&str` | `String` | `to_string()` | `&field`（`&String` 自动收窄成 `&str`） |
| `&[u8]` | `Vec<u8>` | `to_vec()` | `&field`（`&Vec<u8>` 自动收窄成 `&[u8]`） |
| `&String` | `String` | `clone()` | `&field` |
| `&Vec<u8>` | `Vec<u8>` | `clone()` | `&field` |
| `&Copy` 标量 | 原标量 | `*value` | `&field` |
| 按值 `T` | `T` | move | `field` |

其它 `&T` 一律编译错误，提示改为 owned 参数。代价是借用参数在客户端有一次分配 / 复制；
收益是 body enum 可以继续使用 denco 派生，且客户端与服务端共享同一个线上形状。

### 11.3 方法契约

- 只能 `&self`，不能 `async fn`，返回
  `impl TrMayCancel<'f, MayCancelOutput = RpcResult<T>>`；
- 成功类型 `T` 必须实现 denco 的 `TrEncodable + TrDecodableOwned`；当前 `()` 不在其中；
- 业务错误必须用框架的 `RpcError`（推荐 `RpcError::Service { status, message }`）；
  自定义错误类型会让 dispatch 里的 `err.status()` 无法解析；
- 不支持泛型方法、`&mut` 参数、`&dyn Trait`、嵌套借用与高阶生命周期；
- service trait 不接受泛型参数与 trait 级 where 子句；关联常量 / 关联类型必须有默认值。

### 11.4 生成代码的依赖

- body enum 的 denco 派生会引用 `abs_denco`、`abs_cancel`、`gen_mcf2`；隐藏模块已经
  `use core_rpc_mptp_smux_v1::x_deps::{abs_denco, abs_cancel, gen_mcf2};`，因此业务类型
  自己的派生只需要协议 crate 能解析这三个名字；
- 服务端 dispatch 的 step 函数用 `gen_mcf2` 生成具名 future；当前 gen_mcf2 要求使用方
  打开 `#![feature(impl_trait_in_assoc_type)]`；
- `ClientProxy` 的实现要求 `C: TrRpcClientConfig + Send + Sync + 'static`、
  `I: TrRpcInterface + Send + Sync + 'static`。

### 11.8 64 KiB 暂存区修正：ring 边编码边发送

Phase 4 的第一版把 `rpc_demo` 的 64 KiB 预编码搬进了 core：先 `encode_to_vec_async_`，
再把 `Vec` 当体源交给 `send_req_body_async`。这是原型残留，违反了 §2.5「RPC 层提供体源」
与更早设计里的「边序列化边发送」。修正如下：

- **不动 `mptp_smux`**：`send_req_body_async` 本来就不关心体怎么产生，只按已经写出的
  `Body_Size` / `Body_Transfer` 搬运；
- core 新增一个 64 字节的**栈上** SPSC ring（`buffex::ring`，固定数组）：编码器把 MessagePack 字节写进
  写半边，`send_req_body_async` 从读半边搬走；ring 满时编码端等待，读走多少就再编多少；
  64 B 足够容纳 `mp_denco` 的最大单次写入（128 位整数头+负载约 18 B），更大的字符串 /
  二进制体按 `Demand::no_more_than` 分段写入；
- 客户端请求头改为 `Body_Transfer: Chunked`；服务端成功回复同样用 `ChunkedEncode`
  从 ring 搬到子流；请求解码直接走 `LimitedReader` / `ChunkedReader`，不再先读成
  `Vec` 再解码；
- **并发方式**：在同一个 task 内 `futures::future::join` 编码分支与发送分支。没有单独
  `spawn` 的原因：core 不替使用者选运行时（compio 也没有 `TrSpawnSend`），而 `spawn`
  还会给客户端的请求类型加上 `Send + 'static`，从而限制宏生成的业务类型。ring 已经提供
  背压与解耦；将来若确实需要真并行，再引入运行时段与相应约束；
- 删除 `K_BODY_STAGING_CAP_`、`encode_to_vec_async_` 与「超过 64 KiB 报错」的测试，
  新增 200 KiB 大体的流式往返、ring 并发推进、定长 / 分块两种解码视图测试；
- `buffex` 经 path 依赖同仓 `abs_buff`；`mptp_rpc` 与 `mptp_cs_smoke` 的 workspace
  根都加 `[patch."https://gitee.com/lino_snsalias/buffex.rs.git"] abs_buff = path`，
  保证 `TrBuffRead` / `TrBuffWrite` 落在同一个 crate 实例上。

- `RpcRouterError`：注册重复、队列关闭、拒绝回复失败；
- `K_DEFAULT_SERVICE_QUEUE_CAP = 32`；
- `x_deps::futures`：宏生成的 worker / worker 组通过它使用 `futures`，协议 crate 不需要
  自己依赖 `futures`。

`rpc_svc_macro`：

- service 宏额外生成 `Worker<__S, __C>`：
  - `new(service)` / `with_capacity(service, cap)`；
  - `route() -> ServiceRoute<__C>`；
  - `service() -> &__S`；
  - `run_async() -> impl TrMayCancel<..., MayCancelOutput = RpcResult<()>>`；
- interface 宏 `#[rpc(path = "...", services = [...])]`：
  - `impl TrRpcInterface`；
  - `impl<C: TrRpcClientConfig> ServiceSelector<C>`；
  - `ApiV1::workers::<C, ...>(service...)`；
  - 具体类型 `__rpc_interface_ApiV1_Workers<C, S...>`，提供 `routes()` 与 `run_async()`。

### 12.2 关键决策

1. **worker 不 spawn、不选运行时**。宏只生成一个具体 future；使用者决定是独立线程、
   tokio / compio / smol，还是当前 task。这样 core 不需要 runtime 依赖，也不会把
   `Send + 'static` 强加给业务类型。
2. **队列用 `futures::channel::mpsc`**，不用 tokio mpsc（core 保持运行时无关），也不用
   `abs_sync` 的手写队列。`futures::mpsc::Sender` 在 `RpcJob<C>: Send` 时是 `Send + Sync`，
   可以安全地放进 router、跨线程交给 worker。
3. **interface worker 组生成在 interface marker 所在模块**，而不是嵌套隐藏模块。原因是
   `services = [...]` 里的 trait 路径可能是 `super::foo::Trait`；嵌套模块会改变这些相对
   路径的含义。类型名带 `__rpc_interface_{Ident}_Workers` 前缀避免碰撞。
4. **service 的隐藏模块仍然是嵌套模块**：`__rpc_service_{Trait}` 生成在 trait 所在模块，
   因此 interface 里的 module path 只是把 trait 路径最后一段替换成该名字。trait 与
   interface 不在同一模块时，`services` 需要写完整路径。
5. **`run_async` 的取消语义**：
   - service worker 在等待下一个 job 时 `select` 队列 `next()` 与取消信号，空闲时也能
     及时停止；
   - 取消监听用 `cancel.child_token()`，不要求令牌实现 `Clone`（`gen_mcf2` 生成的
     `may_cancel_with` 只会补 `TrCancellationToken`，不会传播 `Clone`）；
   - interface worker 组用 `try_join` 树；任一 worker 出错时提前返回，其余 worker future
     被丢弃，队列随之关闭。
6. **路径重叠规则**：interface 之间按最长段匹配，service 之间按最长段匹配；同一个
   interface 内重复 service 路径、重复 interface 路径在注册时报错。`api/v10` 不会误命中
   `api/v1`。
7. **queues 容量**：缺省 32；service worker 可用 `with_capacity` 覆盖。interface worker 组
   目前固定用缺省容量，后续可加装配参数。
8. **与 `MptpServer` 的接法**：把 `RpcRouter` 作为单一 handler 注册到
   `mptp_smux::serving::Router` 的 `""` 前缀；interface / service 两级匹配全部在
   `RpcRouter` 内完成，`MptpServer` 不需要知道 RPC 路径结构。
9. **`RpcRouter::add_interface` 接收 `ServiceRoute` 集合**，而不是裸 sender。这样
   “service 实现 → worker → route → router” 的装配链保持显式；宏只负责生成 worker，
   不把 service 集合塞进 router 的泛型。

### 12.6 compio 下第二次 RPC 卡住的根因与修复（2026-10-21）

`mptp_cs_smoke` 在 compio + UDS 上恢复 workspace/session 用例后，第一条 RPC 正常，第二条
在同一连接上停在：

```text
最终裁决失败：子流超时：保活无应答或建流未裁决
```

诊断结论：

- 客户端第二次 `bind` / `open` 正常，服务端也 `income` / `accept` 成功；卡住的是服务端
  没有把第二条 `ACCEPT` 帧交给 mux 循环；
- 卡住时服务端 CPU 约 80%～86%，说明有一个任务在忙转；
- 该任务是**第一个 service worker 的收尾**：`RpcCallCtx::close_async` →
  `drain_to_eof_inner_async_`；
- `mptp_smux` 的 `drain_to_eof_inner_async_` 原来只对借出的段调用 `iter_slices()` 统计
  长度，然后 drop。`iter_slices()` 只读、不推进段的 `offset_`；drop 时回收量为 0，于是
  同一段被无限读回；
- 这条路径在旧 `rpc_demo` 没暴露，因为它的客户端请求体用定长 `Body_Size`，解码完没有
  残留；`core_rpc_mptp_smux_v1` 的客户端声明 `Body_Transfer: Chunked`，MessagePack 解出
  值后会留下 2 字节的零终止块 `[0, 0]`；
- compio 是单线程本地运行时，worker 的忙转直接饿死 smux 的 demux / mux 循环，导致
  `ACCEPT` 帧发不出去；tokio 多线程下其它任务仍有机会运行，因此问题被掩盖。

修复：

- `mptp_smux::serving::server_::drain_to_eof_inner_async_` 在丢段之前，用
  `segm.move_items_to_buff(&mut sink)` 把剩余字节搬进 4 KiB 栈上暂存，真正推进消费量，
  再继续读到 `Closing`；
- 不改变线上格式、不改变 `TrBuffRead` 契约，也不需要改 compio 适配器；
- 修复后 `mptp_cs_smoke` 在同一连接上完成 11 条 RPC，`ApiV1` / `ApiV2` 都通过。

教训：收尾路径里的“读干净”必须真正消费；只读视图不是消费。这个 bug 由
`mptp_cs_smoke` 的真实 compio 端到端用例暴露，编译期测试覆盖不到。

## 13. Router trait 拆分与 `rpc_router_trie`（2026-10-21）

状态：**core 的 router 契约与 trie 实现已拆分**；宏生成代码仍只依赖 core 的
`RpcJob` / `ServiceRoute`，迁移点集中在测试、文档与 `mptp_cs_smoke` 的装配代码。

### 13.1 目标

`core_rpc_mptp_smux_v1` 同时承担了太多角色：客户端运行时、服务端 per-call 上下文、
router 匹配、队列交付与 MPTP handler 接入。后续要把“支持 `rpc_svc_macro` 的部分”拆成
基础 client / service interface trait，因此先把 **router** 这条线抽出来：

- 宏与库使用者只依赖**契约**，不依赖某一种路径匹配实现；
- 库使用者可以自行实现 router（正则、静态表、前缀树、动态注册……）；
- 缺省 trie 实现放到独立 crate，core 不再持有它。

### 13.2 决策：匹配与交付分开

最终采用三个契约 + 一个适配器：

```rust
pub trait TrRpcServiceRoute<C: TrServingConfig>: Sized {
    fn path(&self) -> &'static str;
    fn enqueue_async<'f>(&'f self, job: RpcJob<C>)
        -> impl TrMayCancel<'f, MayCancelOutput = Result<(), RpcRouteError>> + 'f
    where C: 'f;
}

pub trait TrRpcRouter<C: TrServingConfig>: Sized {
    type Route: TrRpcServiceRoute<C>;
    type RegisterErr: core::error::Error;

    fn add_interface<I>(&mut self, interface: &str, routes: I) -> Result<(), Self::RegisterErr>
    where I: IntoIterator<Item = Self::Route>;

    fn resolve(&self, location: &str) -> Option<&Self::Route>;
}

pub struct RpcRouterHandler<R, C> where C: TrServingConfig, R: TrRpcRouter<C> { /* ... */ }
```

理由：

1. **匹配与交付是两件会独立变化的事**。匹配可能换成前缀树、正则或动态表；交付可能换成
   不同队列、线程池或负载均衡。把两者塞进一个 trait，会让任意一边的替换都牵动另一边。
2. **404 / 405 与收尾只应实现一次**。`RpcRouterHandler` 统一负责 `Call` 检查、未命中拒绝、
   `RpcJob` 构造、入队与错误映射；自定义 router 只回答“命中谁”。
3. **宏不需要认识具体 router**。生成的 worker 只交出 `ServiceRoute<C>`；`TrRpcRouter`
   的 `add_interface` 接受任意 `Route: TrRpcServiceRoute<C>`，因此自定义队列将来也能
   被宏生成的 worker 使用（需要先让 worker 的 route 类型可配置，见 13.5）。
4. **错误分层**。`RpcRouteError` 只表达交付失败（`Closed` / `Cancelled` / `Other`），
   `RpcDispatchError` 再包一层拒绝写回复失败；注册错误由 `TrRpcRouter::RegisterErr`
   自己表达。`RpcRouterError` 因此只剩注册重复两类，不再混入运行期错误。

### 13.3 `rpc_router_trie`

新 crate 只放：

- `PathTrie<T>`：按完整路径段匹配、最长前缀、段边界回退；仍是 `pub(crate)`；
- `RpcRouter<C>`：两级 Trie，实现 `TrRpcRouter<C>`，`type Route = ServiceRoute<C>`；
- `RpcRouterError`：`DuplicateInterface` / `DuplicateService`；
- `RpcRouter::into_handler()`：等价于 `RpcRouterHandler::new(router)`。

`RpcRouter` **不再**直接实现 `TrReqHandler`；接入 `MptpServer` 必须经
`RpcRouterHandler`。这样 core 不需要知道具体 router，具体 router 也不需要知道拒绝回复的
写法。

### 13.4 迁移点

- `core_rpc_mptp_smux_v1::serving`：
  - 新增 `route_.rs`（`RpcJob` / `ServiceRoute` / `TrRpcServiceRoute` / `RpcRouteError`）
    与 `router_.rs`（`TrRpcRouter` / `RpcRouterHandler` / `RpcDispatchError`）；
  - 删除 `trie_.rs`；
  - 根导出移除 `RpcRouter` / `RpcRouterError`，新增三个契约与 `RpcRouterHandler`。
- `rpc_svc_macro`：生成代码不变；集成测试的 `RpcRouter` 改从 `rpc_router_trie` 导入，
  handler 文档链接改为 `TrRpcRouter::add_interface`。
- `mptp_cs_smoke`：`RpcRouter` 改从 `rpc_router_trie` 导入，注册后 `into_handler()`。
- `rpc_demo` 仍使用自己的手写 router，不受影响。

### 13.5 未完成与下一步

- **基础 client trait**：让宏生成的客户端方法不再直接依赖 `ClientProxy` /
  `call_unary_async`，而是依赖一个可替换的 client 契约；
- **基础 service interface trait**：让宏生成的 dispatch / worker 不再直接依赖具体
