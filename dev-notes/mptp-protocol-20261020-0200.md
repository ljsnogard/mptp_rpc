# MPTP 通信格式与实现综述

状态：**规范性综述**。本文描述 MPTP（Multiplexed P2P Transportation Protocol）当前的线上格式
与实现模型，目标是让任何语言的实现者都能据此做出可互操作的对端，而不依赖 Rust 生态。

本文只描述**现在是什么**，不记录技术决策的历史。实现可以用同步阻塞 IO、异步 IO、事件循环或
任何其他模型；凡涉及“参考实现”的说明都不构成协议要求。

规范用语：

- **必须 / MUST**：不遵守就无法与本文描述的实现互操作；
- **不应 / SHOULD NOT**：违反会产生未定义或不可移植的行为；
- **可以 / MAY**：实现自由选择，不影响线格式。

## 1. 范围与术语

### 1.1 MPTP 负责什么

MPTP 定义一条**字节流通道**上的一次请求 / 回复如何表示：

- 请求与回复的**前缀**（方法、位置、状态、头表）；
- 报文体是**没有体、定长体还是分块体**，以及分块体的帧格式；
- 体之后的**后缀流**如何与体区分；
- 一次请求 / 回复在通道上的先后顺序与结束方式。

MPTP **不负责**：

- 通道本身的建立、复用、可靠传输与流控（由下层多流传输负责）；
- 业务报文体的序列化格式（由应用通过 `Body_Type` 声明，内容对 MPTP 不透明）；
- 业务类型系统与类型标识的分配（应用可用 `Data_Type_Id` 声明）；
- 服务端路由策略、RPC 方法到业务函数的映射。

### 1.2 术语

| 术语 | 含义 |
| --- | --- |
| **通道（channel）** | 一条可靠、有序、双向的字节流。MPTP 的一条报文占用一条通道。 |
| **前缀（prefix）** | 体之前的协议控制信息。请求是“方法 + 位置 + 头”，回复是“状态 + 头”。 |
| **体（body）** | 前缀声明的业务负载，长度由前缀唯一决定。 |
| **后缀流（suffix stream）** | 体之后的裸字节流，没有长度声明、没有块帧，直到发送方半关闭写方向。 |
| **头表（headers）** | 数字键到 `HeaderVal` 的映射，承载长度、类型、传输方式等元数据。 |
| **发送方 / 接收方** | 相对某一条报文而言；一条通道上双方都既可能是发送方也可能是接收方。 |
| **半关闭** | 只关闭写方向，读方向仍可继续接收，通常表现为对端读到 EOF。 |
| **重置** | 立即中止通道，可能丢弃在途数据；与半关闭不同。 |

### 1.3 分层

```text
┌──────────────────────────────────────────────┐
│ 应用 / RPC：业务类型、序列化、路由、handler    │
├──────────────────────────────────────────────┤
│ MPTP：前缀、头表、体边界、后缀流、会话顺序      │
├──────────────────────────────────────────────┤
│ 多流传输：通道的 open / accept / read / write  │
│           / half-close / reset / 流控           │
└──────────────────────────────────────────────┘
```

MPTP 从通道的**第一个前缀字节**开始，到双方各自半关闭写方向并读完对端数据为止。通道如何
建立、通道 ID 如何分配、是否复用同一条物理连接，都不在 MPTP 的线上格式里。

## 2. 通道模型

### 2.1 通道前提

一条 MPTP 通道必须满足：

1. **可靠**：字节不丢失、不重复、不损坏；
2. **有序**：两个方向各自保持写入顺序；
3. **双向**：双方都能独立读写；
4. **支持半关闭**：发送方可以只关闭写方向，接收方读到 EOF 后仍可继续写；
5. **按字节流处理**：MPTP 不依赖消息边界，所有边界都由前缀与体帧自行界定。

如果下层只有“整条消息”抽象，也可以在其上模拟字节流；只要对端看到的字节序列与本文一致。

### 2.2 一次通道承载一次请求 / 回复

当前 MPTP 格式**没有请求 ID、没有多路复用帧、没有消息序号**。一条通道上的字节序列固定为：

```text
请求方向：request-prefix [request-body] [request-suffix] EOF（半关闭）
回复方向：response-prefix [response-body] [response-suffix] EOF（半关闭）
```

因此：

- 一条通道只承载**一次**请求和它对应的回复；
- 会话型方法（`Push` / `Pull` / `Call`）的持续数据走同一条通道的**后缀流**，不是第二条请求；
- 若要在一条通道上复用多次请求，必须另行定义请求边界；本文不定义，当前实现也不支持。

### 2.3 通道标识

“本端通道 ID / 远端通道 ID”是多流传输的概念，**不出现在 MPTP 字节流中**。Rust 参考实现把
它称为 dock，但其他实现可以使用任意 ID 方案。MPTP 只要求双方对“当前这条通道”有一致的
读写对象。

## 3. 报文总体布局

### 3.1 请求

```text
request = request-prefix request-body? request-suffix?
```

- `request-prefix`：方法、位置、头表；
- `request-body`：仅当头表声明了体时存在；
- `request-suffix`：仅当应用需要持续发送时存在，裸字节。

### 3.2 回复

```text
response = response-prefix response-body? response-suffix?
```

- `response-prefix`：状态、头表；
- `response-body`：仅当回复头表声明了体时存在；
- `response-suffix`：仅当应用需要持续发送时存在，裸字节。

### 3.3 前缀为什么与体分开

前缀是协议实现自己生成的小块控制信息，发送方可以在**不知道体总长**的情况下先把它发出去；
接收方也可以先解析前缀，再决定是否接收体、如何接收体。

由此产生两条硬约束：

1. **发送方不得为了写前缀而先完整编码或测量体**。定长体要求长度已知，那就由应用选择定长；
   长度未知就用分块体。
2. **接收方解析前缀时不得读走体的第一个字节**。前缀解析必须恰好停在体开始处，否则后续
   边界全部错位。

## 4. MessagePack 编码约定

MPTP 前缀使用 MessagePack。下列约定适用于前缀中的所有值。

### 4.1 基本类型

| 语义 | MessagePack 表示 |
| --- | --- |
| 无符号整数 | 任意合法整数表示；规范编码取能容纳该值的最短形式 |
| 字符串 | UTF-8 字符串，长度按字节计 |
| 映射 | MessagePack map，键唯一；键顺序无语义 |
| 空值 | `nil`（`0xC0`） |

**整数宽度不进入语义**。发送方可以写最短形式，也可以写更宽的整数；接收方按目标类型读取时
必须接受所有能装进目标范围的整数表示。例如状态码 `200` 的规范编码是 `cc c8`，但
`cd 00 c8` 同样合法。

字符串必须是合法 UTF-8；长度前缀只计字节，不计字符。

映射的键必须唯一。接收方遇到重复键应视为无效输入；规范编码通常按键升序写出，但接收方不得
依赖顺序。

### 4.2 前缀不是容器

请求前缀是**三个连续的 MessagePack 值**，回复前缀是**两个连续的 MessagePack 值**：

```text
request-prefix  = method location headers
response-prefix = status headers
```

不要把三个值包成一个数组或结构体；那会多写一个容器头，改变字节序列。接收方按“读一个值 →
再读一个值”的方式解析。

## 5. 请求前缀

```text
request-prefix = access-method location headers
```

### 5.1 `access-method`

一个整数，取值是位标志，不是序号：

| 方法 | 值（十进制 / 十六进制） | 语义摘要 |
| --- | --- | --- |
| `Head` | 0 / `0x00` | 查看资源元信息 |
| `View` | 1 / `0x01` | 查看资源内容 |
| `Post` | 2 / `0x02` | 上传资源 |
| `Drop` | 4 / `0x04` | 删除资源 |
| `Push` | 16 / `0x10` | 向资源端推送流式数据 |
| `Pull` | 32 / `0x20` | 从资源端拉取流式数据 |
| `Call` | 64 / `0x40` | 调用功能 |

发送方必须只使用上表中的值。接收方遇到其他值必须按协议错误处理，不得猜测成某个近似方法。
规范编码是正定长整数（值都小于 128，通常就是单个字节）。

### 5.2 `location`

一个 UTF-8 字符串，表示资源位置（路径）。示例：`/rpc/echo`、`/api/v1/customer/goods`。

MPTP 不规定路径的语法细节；实现通常把它当作以 `/` 分隔的路径。服务端路由可以按路径段做
最长前缀匹配，但这是实现策略，不是线格式。

### 5.3 `headers`

`nil` 或头表映射：

```text
headers = nil | header-map
header-map = map<uint16, header-value>
```

没有头时发送 `nil`。空映射也是合法的，但语义上仍是“没有条目”；发送方在无头时应优先发送
`nil`。接收方必须保留“没有头”与“空头表”的区别（如果其类型系统需要区分）。

头表的详细编码见第 7 节。

---

## 6. 回复前缀

```text
response-prefix = status headers
```

### 6.1 `status`

一个 `u16` 整数状态码。取值沿用 HTTP 的常见约定，便于理解，但 MPTP 不是 HTTP：

| 范围 | 含义 |
| --- | --- |
| `2xx` | 成功 |
| `3xx` | 重定向 |
| `4xx` | 客户端错误 |
| `5xx` | 服务端错误 |

常用值：`200` 成功、`201` 已创建、`301/302/303` 重定向、`400` 请求错误、`401` 未认证、
`403` 禁止、`404` 不存在、`405` 方法不允许、`406` 不可接受、`500` 服务端错误、`501` 未实现、
`502` 网关错误、`503` 不可用、`504` 超时。

**状态码是开放数值**，不是封闭枚举。接收方必须保留任意 `u16` 状态值，不得把未知状态折叠成
相近的已知状态。应用根据数值自行决定处理方式。

### 6.2 `headers`

与请求头表相同：`nil` 或头表映射。回复可以没有头，也可以携带 `Body_Size`、`Body_Type`、
`Data_Type_Id` 等标准头。

## 7. 头表

### 7.1 键空间

头键是 `u16` 整数，按区段划分：

| 区段 | 用途 |
| --- | --- |
| `0x0000`–`0x009F` | 用户自定义 |
| `0x00A0`–`0x00AF` | 两端共享的标准头 |
| `0x00B0`–`0x00CF` | 客户端常用请求头 |
| `0x00D0`–`0x00FF` | 服务端常用响应头 |

标准键：

| 键 | 十进制 / 十六进制 | 含义 |
| --- | --- | --- |
| `Reserved` | 160 / `0xA0` | 保留 |
| `Body_Size` | 161 / `0xA1` | 体的定长字节数 |
| `Body_Type` | 162 / `0xA2` | 体的编码类型 |
| `Data_Type_Id` | 163 / `0xA3` | 应用类型标识 |
| `Created_At` | 164 / `0xA4` | 创建时间（文本） |
| `Body_Transfer` | 165 / `0xA5` | 体的传输方式 |
| `User_Agent` | 176 / `0xB0` | 客户端信息 |
| `Accept` | 177 / `0xB1` | 可接受的内容类型 |
| `Authorization` | 178 / `0xB2` | 认证凭证 |
| `Cookie` | 179 / `0xB3` | Cookie |
| `Forwarded` | 180 / `0xB4` | 转发信息 |
| `Server` | 208 / `0xD0` | 服务端信息 |
| `Location` | 209 / `0xD1` | 重定向位置 |
| `Last_Modified` | 210 / `0xD2` | 最后修改时间 |
| `Set_Cookie` | 211 / `0xD3` | 设置 Cookie |
| `ETag` | 212 / `0xD4` | 实体标签 |
| `Cache_Ctrl` | 213 / `0xD5` | 缓存控制 |
| `Expires` | 214 / `0xD6` | 过期时间 |

未列出的键按区段规则使用；接收方不得因为它不认识某个头就丢弃整张头表，应原样保留或至少
忽略该条。

### 7.2 头值编码

头值只有两种形态，**直接使用 MessagePack 的整数或字符串**，不写变体标签：

```text
header-value = uint16 | string
```

其中：

- 整数（`0..65535`）表示数字形态；规范编码取最短形式；
- 字符串表示文本形态；内容是 UTF-8；
- 不存在 `{"Num": ...}` 或 `{"Text": ...}` 这样的包装。

示例：

```text
{0xA1: "12"}
= 81 cc a1 a2 31 32
  │  │     └ "12"（裸字符串）
  │  └ key 0xA1 encoded as uint16
  └ map(1) for headers
```

```text
{0xA2: 1}
= 81 cc a2 01
  │  │     └ 1（裸整数）
  │  └ key 0xA2 encoded as uint16
  └ map(1) for headers
```

MessagePack 的整数标记与字符串标记本来不同，因此接收方按标记分派即可：整数进数字形态，
字符串进文本形态。其他语言实现不要额外发明 `"Num"` / `"Text"` 标签。

### 7.3 标准头取值

| 头 | 取值 |
| --- | --- |
| `Body_Size` | 非负整数：十进制文本或整数；`0` 表示没有体 |
| `Body_Type` | `1` = MessagePack，`2` = JSON；其他值由应用定义 |
| `Data_Type_Id` | 应用类型标识；推荐文本，常见为 `0x` 前缀的十六进制 |
| `Body_Transfer` | `0x20` 或文本 `"chunked"`（忽略大小写）= 分块；其他值未定义，发送方不得使用 |
| `Created_At` | 文本日期时间 |
| `User_Agent` 等 | 文本或数字，按头语义使用 |

`Body_Type` 只描述体的序列化格式，不决定体边界；边界只由 `Body_Size` / `Body_Transfer`
决定。

`Data_Type_Id` 只描述“体是什么应用类型”，不决定体边界；它的分配规则由应用约定。若接收方
决定校验它，应在解码体之前比较，不匹配就不要解码。

## 8. 体的传输

### 8.1 三种状态

体的边界必须能从前缀**唯一**确定：

| 状态 | 头表声明 | 体中字节 |
| --- | --- | --- |
| **没有体** | 既无 `Body_Size`，也无 `Body_Transfer` | 0 字节 |
| **定长体** | `Body_Size: N`，`N > 0` | 恰好 `N` 字节 |
| **分块体** | `Body_Transfer: chunked` | 若干块 + 终止块 |

`Body_Size: 0` 等价于没有体（参考实现的归一规则）。发送方在无体时应直接省略两个头，而不是
发送 `Body_Size: 0`。

### 8.2 声明互斥与歧义

`Body_Size` 与 `Body_Transfer` 是互斥的两种声明。发送方**必须**只发送其中一种。

接收方遇到两者同时存在时，这是协议违规。参考实现的处理是**优先按 `Body_Size` 解释**；严格
实现可以拒绝该报文。无论选择哪一种，都必须是确定性的，不能随机挑一个。

### 8.3 定长体

```text
fixed-body = N 字节
```

- `N` 由 `Body_Size` 给出；
- 接收方恰好读取 `N` 字节，之后立即进入后缀流阶段（如果有）；
- 发送方必须恰好写满 `N` 字节；源提前结束是截断，属于协议错误；
- 发送方多写的字节会被接收方当作**后缀流**的开始；如果应用没有后缀语义，那就是协议垃圾；
- 定长体不需要终止标记。

`Body_Size` 的文本形态是十进制字符串（允许首尾空白），数字形态是整数。大于 `65535` 的长度
应使用文本形态，因为 `Num` 头值只承载 `u16`。

### 8.4 分块体

```text
chunked-body = *chunk last-chunk
chunk        = chunk-size(2 字节大端 u16) chunk-data
last-chunk   = 0x0000
```

规则：

- 块长是**固定 2 字节大端无符号整数**，不是 MessagePack 整数；
- 块长只计 `chunk-data` 的字节数，不含这 2 字节前缀；
- 单块数据最多 `65535` 字节；更长的内容必须拆成多块；
- 长度为 `0` 的块是终止块，没有数据，也没有 trailer；
- 终止块之后紧接的就是后缀流（如果应用有）；
- 空分块体只有一个终止块：`00 00`。

示例：分块体 `abc`：

```text
00 03 61 62 63 00 00
└─┬─┘ └──┬──┘ └─┬─┘
 3     abc     0（终止）
```

### 8.5 没有体

没有体时，前缀之后直接是后缀流（如果有）。接收方**不得**读取任何“体字节”，也不得用连接
关闭来推断体长度。

### 8.6 体的内容

MPTP 不解释体。应用根据 `Body_Type` / `Data_Type_Id` 决定如何解码：

- `Body_Type` 缺失时，体格式由应用约定；
- MessagePack 体可以用标准 MessagePack 解码器，但**必须**在体边界内解码：
  - 定长体用“最多 N 字节”的限长读取器；
  - 分块体用“逐块读取”的读取器；
  - 解码器在值结束后可能还有剩余字节（多值、填充或损坏），接收方必须把体剩余部分读到边界
    为止，否则后续后缀流会错位。

## 9. 后缀流

后缀流是体之后的裸字节序列：

```text
... body? suffix ... EOF
```

规则：

- **没有长度声明**；
- **没有块帧**；
- 没有类型声明；
- 发送方写完所需字节后**半关闭写方向**，接收方读到 EOF 即结束；
- 后缀流的起点由体边界决定：
  - 没有体：前缀之后立即开始；
  - 定长体：`N` 字节之后；
  - 分块体：终止块 `00 00` 之后。

后缀流用于 `Push` / `Pull` / `Call` 等需要持续传输的场景。MPTP 不区分后缀流中的消息边界；
应用若需要，必须自己在字节流上定义格式。

**不得**用“读到连接关闭”来界定体：一条通道上体之后可能还有后缀流，关闭会把它一起吞掉或
提前结束。体边界只能由前缀声明。

`Body_Transfer` 的其他取值没有定义：发送方不得发送；接收方可以拒绝，也可以按“没有分块
声明”继续看 `Body_Size`，但不得据此猜测分块。

## 10. 方法语义

方法值是位标志，不是“第几个方法”。以下是各方法**意图**上的语义；实际是否存在体，仍以
头表声明为准：

| 方法 | 请求体 | 回复体 | 后缀流 |
| --- | --- | --- | --- |
| `Head` | 不应有 | 不应有 | 无 |
| `View` | 不应有 | 通常有 | 无 |
| `Post` | 通常有 | 可选 | 无 |
| `Drop` | 不应有 | 不应有 | 无 |
| `Push` | 可选 | 可选 | 客户端 → 服务端，必需 |
| `Pull` | 可选 | 可选 | 服务端 → 客户端，成功时必需 |
| `Call` | 通常有 | 通常有 | 可选，双向均可 |

实现注意：

- `Head` / `Drop` 的回复若声明了体，参考客户端按协议违规处理，不读取体；
- 方法语义不能替代头表：即使方法“通常有体”，只要头表没有声明，就没有体；
- 状态码不能替代体声明：错误回复也可以没有体，成功回复也可以没有体；
- 后缀流是否存在由应用决定，MPTP 不用方法值强制。

## 11. 会话状态机

一条通道上的双方各自维护一个状态机。以下是参考实现的客户端视角；服务端是其镜像。

```text
开始
  │ 写完请求前缀
  ├─ 前缀声明了体 ──▶ SendingBody
  └─ 没有体 ────────▶ WaitingResp

SendingBody
  │ 按定长 / 分块写完请求体
  ▼
WaitingResp
  │ 可选：写请求后缀流
  ├──────────────▶ SendingSuffix ──写完──▶ WaitingResp
  │ 读回复前缀
  ▼
PrefixReady
  │ 按回复头表取体视图
  ├─ 没有体 ──▶ SuffixReady（可直接读后缀）
  └─ 有体 ────▶ BodyReady
                   │ 读完 / 放弃体
                   ▼
                SuffixReady
                   │ 读后缀直到 EOF
                   ▼
                Terminated
```

约束：

1. 请求前缀声明了体时，必须先写完体，才能读回复前缀；否则体留在通道里，回复会从错误的位置
   开始。
2. 请求前缀没有声明体时，不得发送体。
3. 回复前缀到达之前，不得读取回复体；体边界尚未确定。
4. 进入后缀流阶段前，必须把**尚未读完的体**读完或丢弃；否则后缀流会从体中间开始。
5. 没有体时，读取体应表现为立即 EOF，且不得触碰通道。
6. 任何协议错误或传输错误都应终止会话；不要在可能错位的字节流上尝试恢复。

服务端视角：

```text
读请求前缀 → 路由 → handler 读体 / 后缀 → 写回复前缀 → 写回复体 / 后缀
→ 半关闭写方向 → 读尽对端数据 → 关闭读方向
```

服务端可以把请求头表复制一份交给 handler；handler 对头表的修改不写回已经解析的前缀，回复
头表是独立构造的。

## 12. 通道生命周期与收尾

### 12.1 发送方

1. 写请求 / 回复前缀；
2. 如果有体，按声明写体；
3. 如果有后缀流，写后缀；
4. **半关闭写方向**；
5. 继续读对端数据，直到对端半关闭或出错；
6. 关闭读方向。

### 12.2 接收方

1. 读前缀；
2. 读体（按声明）；
3. 读后缀直到 EOF；
4. 如果还要回复，先写回复，再按发送方流程收尾。

### 12.3 收尾次序

参考实现采用：

```text
先半关闭写端（让排队的响应发完）
→ 等对端关闭（读到 EOF）
→ 再放掉读端（避免提前 RESET 丢弃在途响应）
```

如果先重置读方向，下层多流传输可能丢弃仍在途中的响应，对端只会看到半截报文或 EOF。具体
API 由传输层决定，但语义上必须保证“已写出的响应先排空，再拆通道”。

### 12.4 错误与重置

- 前缀编码 / 解码失败、未知方法、头表形状非法：通道已不可同步，应重置或关闭；
- 体截断、分块缺终止块：协议错误，通道不可继续；
- 应用层拒绝（例如类型不匹配）：如果应用选择回复，应先写回复，再按正常收尾；
- 取消 / 超时：若已写出部分体或前缀，通道通常不可复用，应重置。

## 13. 服务端路由与处理

### 13.1 路由

`location` 是路径字符串。参考实现按**最长路径前缀**匹配，并且只在 `/` 分隔处回退：

```text
登记：/topic、/topic/chat、/rpc
请求：/topic/chat/42  → 命中 /topic/chat
请求：/topic/chat     → 命中 /topic/chat
请求：/topic          → 命中 /topic
请求：/topicx         → 不命中 /topic（不是它的子路径）
```

这是实现建议，不是线格式要求。路由表、注册方式和中间件模型由框架决定。

### 13.2 handler 输入

handler 通常拿到：

- `access_method`；
- `location`；
- 请求头表的可变副本；
- 通道的读半边与写半边（或读体 / 写回复的封装）。

handler 自己决定：

- 是否读取请求体；
- 是否读取请求后缀流；
- 回复状态与回复头；
- 是否写回复体 / 回复后缀。

handler 可以在不读请求体的情况下直接回复（例如按头拒绝）；框架在收尾时会把剩余请求数据
读尽，避免提前重置导致在途响应丢失。

框架负责前缀解析、体边界判定和收尾，不替 handler 决定业务语义。

### 13.3 类型分派

如果应用使用 `Data_Type_Id`：

1. 发送方在设置体时写入类型标识（通常是 `0x` 十六进制文本）；
2. 接收方在解码体之前读取并比较；
3. 不匹配时不要解码，返回应用错误（参考 demo 使用 `406`）；
4. 没有声明时由应用决定是拒绝还是按默认类型处理。

标识如何分配不是 MPTP 的一部分。参考 demo 使用类型名的 FNV-1a 64 位哈希，但其他实现可以
使用 UUID、IDL 编号或注册中心分配的 ID；只要两端一致即可。

## 14. 错误处理

| 情况 | 建议处理 |
| --- | --- |
| 前缀不是合法 MessagePack | 协议错误；关闭 / 重置通道 |
| 方法值未知 | 协议错误；不得猜测 |
| 头表不是 `nil` 或 map | 协议错误 |
| 头键不是 `u16` | 协议错误 |
| 头值既不是整数也不是字符串 | 协议错误 |
| 头值类型与标准头要求不符 | 按标准头语义拒绝，或忽略该头 |
| `Body_Size` / `Body_Transfer` 同时存在 | 协议违规；参考实现优先 `Body_Size`，严格实现可拒绝 |
| `Body_Size` 不是合法十进制 | 协议错误（参考实现按没有体处理，不建议模仿） |
| 定长体不足 `N` 字节 | 截断，协议错误 |
| 分块体缺终止块 | 截断，协议错误 |
| 分块长度为 0 后仍有体数据 | 那是后缀流；若应用没有后缀语义，按多余数据处理 |
| `Head` / `Drop` 回复声明了体 | 协议违规；客户端不应读取体 |
| 状态码未知 | 保留原值，不折叠 |
| 头键未知 | 保留 / 忽略，不因此丢弃整张头表 |
| `Data_Type_Id` 不匹配 | 不解码体，返回应用错误 |
| `Body_Type` 不支持 | 应用错误（例如 415 或 406） |

错误回复本身也必须遵守回复前缀格式；错误回复可以没有体。

## 15. 实现清单（语言无关）

### 15.1 前缀编码

```text
encode_request(method, location, headers):
    write_integer(method)
    write_string(location)
    if headers is empty and absent:
        write_nil()
    else:
        write_header_map(headers)

encode_response(status, headers):
    write_integer(status)
    if headers is empty and absent:
        write_nil()
    else:
        write_header_map(headers)
```

要求：

- 三个 / 两个值连续写，不包容器；
- 整数取最短规范形式即可；
- 头表按键升序写可以获得确定性字节，但接收方不得依赖顺序；
- 编码失败时不要写出半截前缀；如果无法保证原子性，失败后应重置通道。

### 15.2 前缀解码

```text
decode_request(reader):
    method = read_integer_as_u8()
    if method not in {0,1,2,4,16,32,64}: error
    location = read_utf8_string()
    headers = read_nil_or_header_map()
    return (method, location, headers)

decode_response(reader):
    status = read_integer_as_u16()
    headers = read_nil_or_header_map()
    return (status, headers)
```

要求：

- 只读前缀所需的字节，不预读体；
- 读整数时接受所有能装进目标范围的整数表示；
- 读头表时验证每个头值是整数或字符串；
- 读取失败、UTF-8 非法、类型不符时报协议错误。

### 15.3 体读取视图

```text
body_view(headers):
    if Body_Size present and > 0:
        return Fixed(reader.limit(N))
    if Body_Size present and == 0:
        return Empty
    if Body_Transfer == chunked:
        return Chunked(reader)
    return Empty
```

- `Fixed`：最多读 `N` 字节，读完即 EOF；
- `Chunked`：循环读 2 字节大端长度，长度为 0 结束，否则读恰好该长度字节；
- `Empty`：立即 EOF，不读通道。

### 15.4 体写入

```text
write_body(writer, headers, source):
    switch body_mode(headers):
        Empty: return
        Fixed(N): copy_exactly(source, writer, N)
        Chunked:
            while source has data:
                block = source.read_up_to(65535)
                if block empty: break
                write_u16_be(block.length)
                write(block)
            write_u16_be(0)
```

要求：

- 定长：写满 `N`；源提前结束是错误；
- 分块：每块长度不超过 65535；最后必须写终止块；
- 分块发送失败时若已写出部分块而没有终止块，通道不可继续，应重置。

### 15.5 后缀流

```text
copy_raw(source, writer)
half_close(writer)
```

后缀流不封帧、不计数、不加类型；读取方一直读到 EOF。

### 15.6 会话状态

实现至少需要区分：

- 前缀是否已写 / 已读；
- 请求体是否已写；
- 回复前缀是否已读；
- 回复体是否已读 / 是否放弃；
- 是否进入后缀流；
- 是否已终止。

状态转移必须阻止“体未写完就读回复”“前缀未到就读体”“没有体却写体”等错位操作。

## 16. 限制、安全与健壮性

### 16.1 协议硬限制

| 项 | 限制 |
| --- | --- |
| 方法值 | 仅 7 个值；其他为错误 |
| 状态码 | `0..65535` |
| 头键 | `0..65535` |
| 头数字值 | `0..65535` |
| 分块单块 | `0..65535` 字节 |
| 分块终止 | 长度 `0`；无 trailer |
| 定长体长度 | 由应用限制；`Body_Size` 文本可表达更大值 |

### 16.2 建议的实现限制

- 前缀总长度上限（防止头表耗尽内存）；
- 头表条目数上限；
- 定长体长度上限（结合业务配额）；
- 分块数量上限；
- 单个字符串 / 头值长度上限；
- 读取 MessagePack 长度时先检查剩余可读字节，避免按声明长度立即分配巨大内存；
- 对未知头、未知状态保持宽容，对形状错误保持严格。

### 16.3 半关闭与重置

- 发送完请求 / 回复后必须半关闭写方向，让对端知道数据结束；
- 读到 EOF 是正常结束，不是错误；
- 重置会丢弃在途数据，只应在通道不可继续时使用；
- 不要用“关闭整条连接”来界定体或后缀流。

## 17. 测试向量

以下字节均为十六进制，空格仅用于阅读。

### 17.1 最小请求

`View` 访问 `/x`，无头：

```text
01 a2 2f 78 c0
│  │  └──┬──┘ │
│  │     "x"  nil
│  └ fixstr(2), "/x"
└ method View = 1
```

### 17.2 无头请求

`Call` 访问 `/rpc/echo`，无头：

```text
40 a9 2f 72 70 63 2f 65 63 68 6f c0
│  │  └──────────┬──────────┘ │
│  │        "/rpc/echo"       nil
│  └ fixstr(9)
└ method Call = 64
```

### 17.3 最小回复

状态 `200`，无头：

```text
cc c8 c0
│  │  └ nil
│  └ 200
└ uint8
```

等价的固定宽度写法（接收方必须接受）：

```text
cd 00 c8 c0
```

### 17.4 头表

`{0xA1: Text("12")}`：

```text
81 cc a1 a2 31 32
```

`{0xA2: Num(1)}`：

```text
81 cc a2 01
```

### 17.5 带头的请求

`Call /rpc/echo`，`Body_Size: Text("5")`，`Body_Type: Num(1)`：

```text
40
a9 2f 72 70 63 2f 65 63 68 6f
82
cc a1 a1 35
cc a2 01
```

随后是 5 字节体，例如 `61 62 63 64 65`（`abcde`）。

### 17.6 分块体

体 `abc`：

```text
00 03 61 62 63 00 00
```

空分块体：

```text
00 00
```

### 17.7 固定体

前缀声明 `Body_Size: 3` 后，体就是三个字节，例如：

```text
61 62 63
```

没有额外长度前缀或终止标记。

## 18. 兼容性与扩展

- 当前格式**没有版本字段**。实现必须与本文一致；不兼容的改动需要新的协议版本或新的传输层
  协商。
- 新标准头应使用 `0xA0`–`0xAF` 中尚未占用的键；用户自定义头使用 `0x00`–`0x9F`。
- 未知头键、未知状态码必须能够被保留或忽略，不得导致整条报文不可解析。
- 未知方法值必须拒绝；不能用保留位猜测方法。
- 新增 `Body_Transfer` 取值时，必须同时定义其边界规则；当前只有 `chunked`。
- 分块体当前没有 extension 与 trailer；需要时通过新头或新的传输方式表达，不要复用块长字段。
- `Body_Type` 可扩展；未知类型由应用决定是否支持，但不应影响体边界的解析。
