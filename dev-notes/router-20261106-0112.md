## 0. 摘要

### 0.1 一句话

Router 是**可递归嵌套的分层路由表**：每一个 router 都拥有一张**以自己为根**的局部
路由树，不外乎包含一个**根 handler** 和若干**规则**；每条规则要么**绑定一个 handler**
（精确路径模式 + 方法集合），要么**绑定一个子 router**（静态路径前缀 + 子 router）。
父 router 只知道「在哪个前缀挂了一个子 router」，既不知道子 router 里有哪些具体规则，
也不知道父层还有哪些兄弟路由；一个请求从顶层 router 开始逐层向下匹配，任何一层无法
命中时由**该层自己的根 handler** 兜底，绝不自动上抛给父层或绝对根。router 的添加入口
只有两个：绑定 handler、绑定子 router；七种访问方法通过方法糖或 `MethodSet` 指定。

### 0.2 关键决策

| # | 决策 | 结论 | 主要理由 |
| --- | --- | --- | --- |
| 1 | 路由结构 | **分层 router**，不再有 level / interface / scope 等框架概念 | 用户修正：层级与 interface 都被分层 router 取代；RPC 的 interface / service 只是若干挂载点 |
| 2 | 表的所有权 | **每个 router 拥有以自己为根的局部路由表**，不是「全局一张表」 | 父 router 不知道兄弟规则、不知道子 router 内部规则；各 router 可独立增删 |
| 3 | 注册入口 | `TrRouter` **只有两个添加方法**：`bind_handler`（规则 → handler）、`bind_router`（规则 → 子 router）；另有撤销方法 | 用户修正：针对一条路由规则，要么绑 handler，要么绑子路由 |
| 4 | 匹配方式 | 顶层 router 递归匹配：本层 handler 规则精确命中 → 返回；否则命中子 router 挂载前缀 → 把**剩余路径**交给子 router 递归；本层都没有 → 本层根 handler | 分层 router 自然形成「最深进入层的根兜底」，不需要父层协调 |
| 5 | 根 handler | **每个 router 构造时必须提供根 handler**；顶层的是绝对根，子 router 的是相对根 | 上一轮修正保留：下层未命中必须由本层相对根兜底，不能上抛给绝对根 |
| 6 | 隔离性 | 父 router 只持有子 router 的匹配句柄（`Arc<dyn TrRouteMatcher>`），不枚举、不修改子 router 内部规则 | 每层各自维护、可独立替换与运行期增删 |
| 7 | 方法绑定 | 参考现有 `Router::call` 风格：`.head/.view/.post/.drop/.push/.pull/.call(rule, handler)`，或 `.on(rule, MethodSet, handler)` | 七种访问方法各有绑定入口；一个 handler 可响应多种方法 |
| 8 | 注入方式 | `MptpServer` 只依赖 `TrRouteMatcher<C>`；注册额外要求 `TrRouter<C>` | 默认实现 `RadixRouter` 同时实现两者；用户可注入自定义实现 |
| 9 | 静态 / 动态 | 不区分；每个 router 的局部表都支持运行期增删 | 用户要求运行期动态资源；注册不触发父 router 变更 |
| 10 | 请求取消 | `RouteRequest` 携带可取消的 `RequestCancel`，不得假定它是 `NonCancellableToken` | 上一轮修正保留 |
| 11 | 资源概念 | 资源 = 应用持有的 handle + 一组 route 绑定；不抽 `TrResource` trait | 上一轮修正保留 |

### 0.3 与上一版的关系（被取代的内容）

| 上一版内容 | 现状 | 取代原因 |
| --- | --- | --- |
| level（层级）与 interface 作为框架概念 | **删除** | 用户修正：它们都是「分层 router」的特例，不应成为独立概念 |
| `RouterCtx` 作用域、`scope` / `scope_default`、`insert_level` | **删除** | 每个 router 自己就是注册句柄；挂子 router 用 `bind_router` |
| 单一全局路由表 / 全局「插入层级 + 插入 route」 | **删除** | 改为每个 router 自根局部表；父 router 不知道子 router 内部规则 |
| 「绝对根 + 每层相对根」的层级表述 | **保留语义，改述为**：每个 router 都有自己的根 handler；顶层的是绝对根，挂载的子 router 的是相对根 | 用户确认下层未命中必须由本层兜底 |
| 七种方法用内部方法槽位表达 | **改为**：`bind_handler(rule, MethodSet, handler)` + 七种方法糖；一个 handler 可覆盖多种方法 | 用户要求参考 `Router::call` 写法 |
| 上一版的精确 route / 兜底顺序 | **保留**，但由「每个 router 递归自治」实现：本层 handler 规则 → 子 router → 本层根 handler | 分层 router 的递归匹配天然实现最深进入层兜底 |
| `RequestCancel` / 「资源 = handle + 绑定」 | **保留** | 上一轮修正 |

### 0.4 与「全局一张表」说法的区别（重要）

本文不再使用「全局一张路由表」的说法。正确的模型是：

- 每个 router 实例 = 一棵**以自己为根**的局部路由树（根 handler + handler 规则 +
  子 router 规则）；
- 顶层 router 是唯一一个被 `MptpServer` 直接持有的 router；它通过 `Arc<dyn
  TrRouteMatcher>` 间接持有子 router，但**不枚举**子 router 的规则；
- 子 router 也不知道父 router、父层的兄弟 router，以及自己被挂载的绝对前缀；
  它只处理「相对于自己根」的路径；
- 因此父层新增/删除兄弟路由、子 router 内部新增/删除规则互不影响，只需要各自持有
  自己的句柄。绝对路径与匹配长度由父层在递归返回时叠加。

## 1. 设计不变量

| # | 不变量 | 含义 |
| --- | --- | --- |
| I1 | **分层 router，无全局概念** | 不存在 level / interface / scope 等框架类型；RPC 的 interface / service 只是子 router 的实例 |
| I2 | **每个 router 自根** | router 的规则路径都相对于自己的根；它不知道父层、兄弟路由，也不知道自己的绝对挂载前缀 |
| I3 | **两个添加入口** | 针对一条规则，只能二选一：绑定 handler（精确模式 + 方法集合）或绑定子 router（静态前缀）；撤销是独立入口，不属于添加 |
| I4 | **父子隔离** | 父 router 只通过 `Arc<dyn TrRouteMatcher>` 调用子 router；不枚举、不修改子树内部规则 |
| I5 | **递归匹配 + 本层兜底** | 本层 handler 规则未命中 → 尝试子 router → 都没有则本层根 handler；**不会**自动上抛给父层 / 绝对根 |
| I6 | **每个 router 必有根 handler** | 构造时安装；顶层的是绝对根，子 router 的是相对根；不可被规则覆盖 |
| I7 | **方法是一等维度** | handler 规则绑定 `MethodSet`；可一 handler 多方法，也可同路径不同方法多 handler |
| I8 | **只向下追加** | 规则路径相对当前 router 根；无 replace；handler 规则与子 router 挂载路径不得互相重叠/前缀（同一 router 内） |
| I9 | **结果拥有所有权** | 匹配返回 `Arc<dyn TrRouteTarget>` 与拥有所有权的匹配信息；任何 router 的锁不得跨 `await` 持有 |
| I10 | **请求取消可取消** | 每个被分发的请求带 `RequestCancel`；target 不得假定它永不取消 |
| I11 | **资源不是框架类型** | 资源 = 应用持有的 handle + 一组 route 绑定；不抽 `TrResource` trait |

## 2. 概念模型

### 2.1 一个 router 的结构

```text
RadixRouter<C>（以自己为根）
  ├─ root handler                     ← 本层兜底；顶层即绝对根
  ├─ handler 规则（一棵精确匹配的路径树）
  │    ├─ "echo"          → MethodSet::ALL → EchoTarget
  │    ├─ "feeds/{id}"    → View          → FeedViewTarget
  │    └─ "feeds/{id}"    → Pull          → FeedPullTarget
  └─ 子 router 规则（静态前缀 → 子 router 句柄）
       ├─ "api/v1"        → Arc<dyn TrRouteMatcher>  ← interface router
       └─ "admin"         → Arc<dyn TrRouteMatcher>  ← 另一个 router
```

- **handler 规则**：精确路径模式（`{name}` / `{*rest}`），同一模式可按方法分成多条；
- **子 router 规则**：静态前缀；请求路径命中该前缀后，把**前缀之后的剩余路径**交给
  子 router 递归匹配；
- **根 handler**：本层规则都没命中时兜底；顶层 router 的根 handler 就是绝对根 handler；
- router 不知道父层、兄弟、自己的绝对挂载前缀，也不知道子 router 的内部规则。

### 2.2 调用链（递归）

```text
MptpServer<C, R: TrRouteMatcher<C>>
  │  解码请求前缀；产生 RequestCancel
  │
  └─ R::match_route(method, location)                  ← 顶层 router
       ├─ 本层 handler 规则精确命中 → Found(handler target, matched_len = location len, params)
       ├─ 本层子 router 规则前缀命中 → 取剩余路径调用子 router.match_route(...)
       │     └─ 子 router 重复同样的过程；返回后父层把 mount 前缀长度 / blocked_len 加上
       └─ 本层都没命中 → Found(本层 root handler, matched_len = 0 相对, remaining = 本层剩余路径)
  ↓
target.handle_route(RouteRequest { location: 完整绝对 location, matched_len: 绝对长度, cancel, ... })
```

要点：

- handler 拿到的 `RouteRequest.location` 始终是**顶层完整 location**，`matched_len` 是
  绝对长度（父层递归返回时叠加），`remaining` 是命中前缀之后的绝对剩余路径；
- 各层 router 的局部匹配只处理「相对自己根」的路径；
- 任何一层都没有把请求「上抛」给父层的机制；子 router 未命中时由它自己的根 handler
  处理，父 router 拿到子 router 返回的 target 后原样返回。

### 2.3 匹配语义

#### 2.3.1 路径规范化

进入匹配前，`location` 统一做以下规范化：

1. 去掉首尾的 `/`；`/topic/chat/42` 与 `topic/chat/42` 等价；
2. 按 `/` 切段，**不做** percent-decode、不做大小写归一化；
3. 空段（连续 `//`）不匹配任何 handler 规则；是否把空段视为非法输入见 11.12；
4. handler 规则的模式支持 matchit 0.8+ 的花括号语法：`{name}` 匹配一个非空段，
   `{*rest}` 匹配剩余全部（可为空串，但只能位于路径末尾）；
5. 子 router 的挂载路径只允许**静态段前缀**（不含参数 / catch-all；见 11.19）。

#### 2.3.2 一个 router 内部的匹配顺序

1. **handler 规则**先做精确匹配：整条（相对）路径必须被模式完全消费，且方法在
   `MethodSet` 内；静态段 > 参数 > catch-all，失败回溯；
2. 若 handler 规则本身路径命中但方法不支持，记下 `FallbackInfo::MethodNotAllowed`
   （`allowed` 为该路径模式上所有方法槽的并集，`blocked_len` 为当前层相对路径长度）；
3. 否则尝试 **子 router 规则**：挂载前缀必须是完整段前缀；命中后对剩余路径递归调用
   子 router；把子 router 返回的 `matched_len` / `blocked_len` 加上本层已消费长度；
4. 若都没有命中，返回**本层根 handler**，`matched_len = 0`（相对本层），
   `remaining = 本层剩余路径`，并携带第 2 步的 `FallbackInfo`（若有）；
5. 由于同一 router 内 handler 规则与子 router 挂载路径**不允许互相重叠或互为前缀**
   （I8），第 1 步与第 3 步不会同时成立，实现无需在两者之间猜优先级。

#### 2.3.3 递归示意

```text
请求：View api/v1/workspace/reports/42
顶层 router（根 = AppRoot）
  ├─ handler 规则 "echo" 等：不匹配
  └─ 子 router "api/v1" 命中 → 剩余 "workspace/reports/42"
       interface router（根 = InterfaceRoot）
         ├─ handler 规则（interface 自己的）：不匹配
         └─ 子 router "workspace" 命中 → 剩余 "reports/42"
              service router（根 = ServiceRoot，负责 Call / 405）
                └─ handler 规则 "reports/{id}" 命中 View → Found（matched_len 叠加为完整长度）
```

请求 `View api/v1/workspace/unknown` 时：service router 没有 handler 规则命中 → 返回
**service router 的根 handler（ServiceRoot）**；父层（interface router）**不会**接管，
也不会继续尝试自己的根 handler 或其他子 router。这就是「下层 router 未命中由相对根
兜底」在分层结构里的实现。

#### 2.3.4 冲突与覆盖

- 同一 router 内，handler 规则与子 router 挂载路径**不得相等、不得互为前缀**；违反
  返回 `RouteError::Conflict`。这保证「一条规则要么 handler、要么子 router」不会被
  同名前缀同时占用；
- 同一 handler 规则路径、方法集合有交集 → `Conflict`；方法集合不相交 → 允许（同一
  路径不同方法分别绑定 handler）；
- 子 router 挂载路径必须是静态前缀，且不能与其他子 router 挂载路径重叠；
- 无 replace API；handler 规则与子 router 规则都只能在当前 router 内向下追加；
- **父 router 的规则不会被子 router 内部规则覆盖**（父 router 根本不看子 router 内部）；
  子 router 内部的规则也不会改变父 router 的匹配结果；两侧只通过 `bind_router` 的挂载
  前缀发生关系。

#### 2.3.5 方法绑定风格

参考现有 `Router::call` 的写法：

```rust
// 每种访问方法一个入口；不同方法可以绑不同 handler。
router.head("feeds/{id}", HeadTarget)?;
router.view("feeds/{id}", ViewTarget)?;
router.pull("feeds/{id}", PullTarget)?;
router.call("rpc", CallTarget)?;

// 或者一个 handler 同时响应多个方法。
router.on("feeds/{id}", MethodSet::VIEW | MethodSet::HEAD, FeedReadTarget)?;

// 一条规则要么 handler，要么子 router。
router.bind_router("api/v1", interface_router)?;
```

### 2.4 根 handler：每层一个

| 位置 | 名称 | 何时调用 | 必须性 |
| --- | --- | --- | --- |
| 顶层 router | **绝对根 handler** | 顶层 router 的所有 handler 规则 / 子 router 都未命中 | 构造 `RadixRouter::new(absolute_root)` 必填 |
| 子 router | **相对根 handler** | 该子 router 的所有局部规则都未命中 | 构造 `RadixRouter::new(relative_root)` 必填 |

推论：

1. 请求每深入一层 router，就多一个该层自己的兜底候选；
2. 兜底总是发生在**当前这一层**：子 router 未命中时由它自己的根 handler 处理，父层
   不会自动接管；
3. 因此顶层绝对根只处理「顶层 router 本身没有命中任何规则」的请求；
4. 服务实现者只持有自己 router 的注册句柄，因此改不了父层、兄弟 router 或绝对根——
   这是「不能覆盖启动前规则」在分层结构里的直接体现；
5. 子 router 若希望把未命中请求交给父层，必须自己在相对根 handler 里显式转发，框架
   不提供自动上抛。

## 3. 契约设计

> 本节代码是**设计示意**；不保证可直接编译。

### 3.1 `TrRouter<C>`：两个添加入口 + 撤销

```rust
/// 一个 router 的注册契约。
///
/// **添加**规则只有两个入口：绑定 handler、绑定子 router。
pub trait TrRouter<C: TrConfig>: Send + Sync {
    /// 为一条规则绑定 handler（精确路径模式 + 方法集合）。
    ///
    /// - `rule` 相对本 router 的根；不允许空串；
    /// - 与既有 handler 规则「同模式 + 方法有交集」→ `Conflict`；
    /// - 与既有子 router 挂载路径重叠 / 互为前缀 → `Conflict`。
    fn bind_handler(
        &self,
        rule: &str,
        methods: MethodSet,
        handler: RouteTarget<C>,
    ) -> Result<RouteId, RouteError>;

    /// 为一条规则绑定子 router（静态路径前缀）。
    ///
    /// 请求命中该前缀后，剩余路径交给子 router 递归匹配；本 router 不关心子 router
    /// 内部的规则。
    fn bind_router(
        &self,
        rule: &str,
        router: NestedRouter<C>,
    ) -> Result<RouteId, RouteError>;

    /// 撤销一条规则（不属于「添加」入口）。
    fn remove_route(&self, id: RouteId) -> Result<(), RouteError>;
}
```

`TrRouter` 只有两个**添加**方法；撤销通过 `remove_route`，匹配通过下一节的
`TrRouteMatcher`。默认实现 `RadixRouter<C>` 同时实现两者。

为了让 `Arc<RadixRouter<C>>` 既能当注册句柄又能当子 router 句柄，提供转发实现：
`impl<C, R: TrRouter<C> + ?Sized> TrRouter<C> for Arc<R>`；`TrRouteMatcher` 同理。

### 3.2 `TrRouteMatcher<C>`：匹配契约

```rust
/// 一个 router 的匹配契约。`MptpServer` 只依赖它。
pub trait TrRouteMatcher<C: TrConfig>: Send + Sync {
    /// 在「相对于本 router 根」的 `location` 上匹配。
    ///
    /// 返回的目标可能是：
    /// - 本层 handler 规则绑定的 target；
    /// - 子 router 递归匹配后返回的 target（父层已叠加 matched_len）；
    /// - 本层根 handler（都没命中 / 方法不支持）。
    fn match_route(&self, method: AccessMethod, location: &str) -> RouteOutcome<C>;

/// 子 router 句柄：父层只把它当作匹配器，不枚举其规则。
pub type NestedRouter<C> = Arc<dyn TrRouteMatcher<C>>;
```

### 3.3 `TrRouterExt<C>`：七种方法糖

```rust
/// 在任意 `TrRouter` 上的方法糖；参考现有 `Router::call` 的写法。

    fn view(&self, rule: &str, handler: impl TrRouteTarget<C> + 'static) -> Result<RouteId, RouteError>;
    fn post(&self, rule: &str, handler: impl TrRouteTarget<C> + 'static) -> Result<RouteId, RouteError>;
    fn drop(&self, rule: &str, handler: impl TrRouteTarget<C> + 'static) -> Result<RouteId, RouteError>;
    fn push(&self, rule: &str, handler: impl TrRouteTarget<C> + 'static) -> Result<RouteId, RouteError>;
    fn pull(&self, rule: &str, handler: impl TrRouteTarget<C> + 'static) -> Result<RouteId, RouteError>;
    fn call(&self, rule: &str, handler: impl TrRouteTarget<C> + 'static) -> Result<RouteId, RouteError>;
}

impl<C, T> TrRouterExt<C> for T where C: TrConfig, T: TrRouter<C> + ?Sized { /* ... */ }
```

每种方法糖内部都调用 `bind_handler(rule, MethodSet::just(method), ..)`；`on` 用于一个
handler 同时响应多种方法。

### 3.4 `TrRouteTarget` / `RouteRequest` / `RequestCancel`

```rust
/// 一个可以被路由到的目标（handler）。对象安全：匹配结果只暴露 `dyn` 形式。
pub trait TrRouteTarget<C: TrConfig>: Send + Sync {
    /// 处理一次已经完成路由的请求。
    ///
    /// target 拥有两个 channel 半边，负责写回复与收尾（写回复 → 半关闭 tx → 读完 rx）。
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, C>) -> RouteTargetFuture<'f>;
}

pub type RouteTarget<C> = Arc<dyn TrRouteTarget<C>>;

pub type RouteTargetFuture<'f> =
    Pin<Box<dyn Future<Output = Result<(), RouteTargetError>> + Send + 'f>>;
```

擦除层要求 `C: 'static`；`RouteTargetFuture` 要求 `Send`，因此非 `Send` 的旧 handler
不能直接接入（适配器约束见下）。

```rust
/// 一次已经完成路由的请求。
pub struct RouteRequest<'f, C: TrConfig> {
    method: AccessMethod,

    /// 顶层完整 location，已按 2.3.1 规范化（去掉首尾 `/`）。
    location_: &'f str,

    /// 绝对长度：handler 规则命中 = location 长度；根 handler 兜底 = 已消费的绝对长度。
    matched_len_: usize,

    /// 路径参数；只在 handler 规则命中时非空。
    params_: RouteParams,

    /// handler 规则路径命中但方法不支持、落到根 handler 时的诊断信息。
    fallback_: Option<FallbackInfo>,

    headers_: &'f mut Headers,

    /// 请求级取消令牌；**不得假定它永不取消**。
    cancel_: RequestCancel,

    tx_: ChannelTx<C>,
    rx_: ChannelRx<C>,
}

impl<'f, C: TrConfig> RouteRequest<'f, C> {
    pub fn method(&self) -> AccessMethod;
    pub fn location(&self) -> &'f str;
    pub fn matched_len(&self) -> usize;
    /// 已消费的绝对前缀（handler 命中时等于完整 location，根兜底时是父层叠加结果）。
    pub fn matched_prefix(&self) -> &'f str;
    /// 命中前缀之后的绝对剩余路径（没有时为空串）。
    pub fn remaining(&self) -> &'f str;
    pub fn params(&self) -> &RouteParams;
    pub fn fallback(&self) -> Option<FallbackInfo>;
    pub fn headers(&mut self) -> &mut Headers;
    /// 请求级取消令牌；必须传给所有可取消 await。
    pub fn cancel(&self) -> &RequestCancel;

    pub fn into_parts(self) -> RouteRequestParts<'f, C>;

    /// 标准收尾；内部使用请求取消令牌。
    pub fn close_async(self) -> impl TrMayCancel<'f, MayCancelOutput = usize> + 'f
    where
        Self: 'f;

    /// 写一条状态回复；内部使用请求取消令牌。
    pub fn reply_status_async<'a>(
        &'a mut self,
        status: Status,
        message: &str,
    ) -> impl TrMayCancel<'a, MayCancelOutput = Result<(), RouteTargetError>> + 'a;
}

impl<'f, C: TrConfig> RouteRequest<'f, C> {
    /// crate 内部构造器：server 在 `match_route` 返回 `Found` 之后组装请求。

        matched: RouteMatch<C>,
        method: AccessMethod,
        location: &'f str,
        headers: &'f mut Headers,
        cancel: RequestCancel,
        tx: ChannelTx<C>,
        rx: ChannelRx<C>,
    ) -> Self;
}

pub struct RouteRequestParts<'f, C: TrConfig> {

    pub params: RouteParams,
    pub fallback: Option<FallbackInfo>,
    pub headers: &'f mut Headers,
    pub cancel: RequestCancel,
    pub tx: ChannelTx<C>,
    pub rx: ChannelRx<C>,
}
```

#### 3.4.1 `RequestCancel`

```rust
/// 一次请求的取消令牌，由分发层在路由时产生。
///
/// **它不是 `NonCancellableToken`**：当前「按规则定时取消」的机制尚未实现，但契约上
/// 它可能因超时、服务关闭、资源 drain 等原因被取消。target 必须：
/// 1. 把 `req.cancel().child_token()` 传给所有可取消的异步调用；
/// 2. 在取消路径上完成必要的收尾；
/// 3. 不得写「令牌一定不会取消」这类假设。
#[derive(Clone)]
pub struct RequestCancel { /* 对象安全的擦除句柄 */ }

impl TrCancellationToken for RequestCancel {
    type Cancellation = RequestCancelFuture; // Pin<Box<dyn Future<Output = ()> + Send>>
    type ChildToken = RequestCancel;
    fn is_cancelled(&self) -> bool;
    fn can_be_cancelled(&self) -> bool;
    fn child_token(&self) -> Self;
    fn cancellation(self) -> Self::Cancellation;
}
```

产生位置：分发层（当前 `MptpServer`，未来可由 router 的取消策略接管）为每个被分发的
请求产生 `RequestCancel`。v1 可能只是从 serve 令牌派生一个 child（甚至暂时不可取消），
但**类型与契约按可取消设计**；具体机制见 11.2。

#### 3.4.2 与旧 `TrReqHandler` 的适配

```rust
pub struct ReqHandlerTarget<H> { handler_: H }

impl<H> ReqHandlerTarget<H> { pub fn new(handler: H) -> Self; }

impl<C, H> TrRouteTarget<C> for ReqHandlerTarget<H>
where
    C: TrConfig + 'static,
    H: TrReqHandler<C> + Send + Sync + 'static,
    H::Err: 'static,
    // 旧 handler 的 future 只有 TrMayCancel 约束，没有 Send；装箱需要显式要求。
    for<'f> H::HandleAsync<'f>: Send + 'f,
{
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, C>) -> RouteTargetFuture<'f> {
        Box::pin(async move {
            let cancel = req.cancel().child_token();
            let parts = req.into_parts();
            self.handler_
                .handle_async(parts.method, parts.location, parts.headers, parts.tx, parts.rx)
                .may_cancel_with(cancel)
                .await
                .map_err(RouteTargetError::from_handler)
        })
    }
}
```

旧 handler 拿到的是被 `RequestCancel` 包裹后的 future；即使 handler 内部没有显式处理
令牌，取消也会在 await 边界生效。

### 3.6 `MethodSet`

`AccessMethod` 的线上取值是位标志，但 `Head` 是 `0`，不能直接当掩码用；`MethodSet`
是独立的小类型：

```rust
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub struct MethodSet(/* u8 bitmask */);

impl MethodSet {
    pub const NONE: MethodSet;
    pub const ALL: MethodSet;
    pub const HEAD: MethodSet;
    pub const VIEW: MethodSet;
    pub const POST: MethodSet;
    pub const DROP: MethodSet;
    pub const PUSH: MethodSet;
    pub const PULL: MethodSet;
    pub const CALL: MethodSet;

    pub const fn just(method: AccessMethod) -> MethodSet;
    pub const fn contains(self, method: AccessMethod) -> bool;
    pub const fn intersects(self, other: MethodSet) -> bool;
    pub const fn union(self, other: MethodSet) -> MethodSet;
}

impl core::ops::BitOr for MethodSet { /* ... */ }
```

绑定语义：

- `intersects` 用于冲突检测：同一 handler 规则路径上方法集合有交集 → `Conflict`；
- `contains` 用于匹配：handler 规则只有在方法集合包含本次方法时才算命中；
- 协议规定 `Head` 对任意资源总是可用，但框架不自动合成 HEAD handler：资源暴露时应
  显式绑定 `Head` target（或让一个 target 通过 `MethodSet` 同时覆盖多种方法）。

### 3.7 默认实现 `RadixRouter<C>`：每 router 自根

```rust
pub struct RadixRouter<C: TrConfig> {
    /// 本 router 的根 handler；顶层的是绝对根，子 router 的是相对根。
    root_: RouteTarget<C>,

    /// 本 router 的局部状态（实现细节，内部同步）。
    table_: RwLock<LocalTable<C>>,
}

impl<C: TrConfig> RadixRouter<C> {
    pub fn new(root: impl TrRouteTarget<C> + 'static) -> Self;

    /// 把本 router 变成可被父层挂载的匹配句柄。
    pub fn as_nested(&self) -> NestedRouter<C>;   // 或直接 Arc<Self> 的 clone
}

impl<C: TrConfig> TrRouter<C> for RadixRouter<C> { /* 两个添加 + remove */ }
impl<C: TrConfig> TrRouteMatcher<C> for RadixRouter<C> { /* 递归匹配 */ }
```

数据结构：

```text
LocalTable<C>
  ├─ handler_trie: RouteTrie<C>        ← 精确路径模式树；每个终端节点按方法槽存 target
  └─ routers: Vec<(StaticPrefix, NestedRouter<C>)>  ← 子 router 挂载表
```

匹配流程（实现要点）：

1. 持本层读锁：先查 handler trie（精确匹配 + 方法过滤，静态 > 参数 > catch-all）；
2. 未命中则查 `routers` 的静态前缀；由于挂载前缀互不重叠，最多命中一条；
3. **释放本层读锁**后再递归调用子 router / 调用 target，避免跨层持锁；
4. 子 router 返回后，把 `matched_len` / `blocked_len` 加上本层已消费长度；
5. 都不命中则返回 `root_`，`matched_len` 为父层叠加后的长度。

`bind_handler` / `bind_router` / `remove_route` 持写锁；冲突规则见 2.3.4。

### 3.8 根 handler 与 `MptpServer`

每个 `RadixRouter::new(root)` 都要求根 handler；因此：

- 顶层 router：`RadixRouter::new(AppRoot)`，`AppRoot` 即**绝对根 handler**；
- 子 router：`RadixRouter::new(InterfaceRoot)` / `RadixRouter::new(ServiceRoot)`，它们的
  根 handler 即**相对根 handler**；
- `MptpServer<C, R>` 只要求 `R: TrRouteMatcher<C>`；默认拿 `Arc<RadixRouter<C>>` 即可。

```rust
pub struct MptpServer<C, R> where C: TrConfig, R: TrRouteMatcher<C> { /* ... */ }
impl<C, R> MptpServer<C, R> where C: TrConfig, R: TrRouteMatcher<C> {
    pub fn new(router: R) -> Self;
    pub fn router(&self) -> &R;
    pub fn serve_channel_async<'f>(&'f self, tx: ChannelTx<C>, rx: ChannelRx<C>) -> ...;
    pub fn serve_listener_async<'f>(&'f self, binding: &'f mut DockBinding<C>, reserve: usize) -> ...;
}
```

分发步骤：解码前缀 → 产生 `RequestCancel` → `router.match_route(method, location)` →
构造 `RouteRequest` → `target.handle_route`。`Unmatched` 只在实现缺根 handler 时出现，
server 写协议级 404 兜底。

## 4. 示例用法

> 示例用于固定**调用形状**，省略 `SrvCfg` 配置实现、导入与错误映射；不保证可直接编译。

### 4.1 应用装配：顶层 router + 子 router + 动态资源

```rust
use std::sync::Arc;

use abs_cancel::NonCancellableToken;
use abs_mptp::spec::{Status, StdHeaderKey};
use mptp_smux::{
    messaging::{Headers, ResponsePrefix, write_response_prefix_async},
    serving::{
        FallbackInfo, MethodSet, MptpServer, RadixRouter, ReqHandlerTarget, RouteRequest,
        RouteTargetFuture, TrRouteTarget, TrRouter, TrRouterExt, close_channel_async,
    },
};
use rpc_core_v1::serving::TrRpcRouterExt;

// 顶层 router 的根 handler = 绝对根：只处理顶层没有命中任何规则的请求。
struct AppRoot;

impl TrRouteTarget<SrvCfg> for AppRoot {
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, SrvCfg>) -> RouteTargetFuture<'f> {
        Box::pin(async move {
            let mut parts = req.into_parts();
            let cancel = parts.cancel.child_token();
            let mut resp_headers = Headers::new();
            let status = match parts.fallback {
                Some(FallbackInfo::MethodNotAllowed { .. }) => Status::MethodNotAllowed,
                None if parts.location.starts_with("old/") => {
                    resp_headers.set_text(StdHeaderKey::Location, "/api/v1");
                    Status::MovedPermanently
                }
                None => Status::NotFound,
            };
            let prefix = ResponsePrefix::with_headers(status, Some(resp_headers));
            write_response_prefix_async(&prefix, &mut parts.tx)
                .may_cancel_with(cancel.child_token())
                .await?;
            close_channel_async(parts.tx, &mut parts.rx).await;
            Ok(())
        })
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // 顶层 router：拥有以自己为根的局部表；根 handler 是绝对根。
    let top = Arc::new(RadixRouter::<SrvCfg>::new(AppRoot));

    // 普通 handler 规则：每个访问方法一个入口，或一个 handler 覆盖多种方法。
    top.on("echo", MethodSet::ALL, ReqHandlerTarget::new(EchoHandler))?;

    // 子 router：interface 只是挂在 "api/v1" 下的一个 router。
    top.rpc_interface::<ApiV1>(|api| {
        api.add_service::<WorkspaceServiceImpl>({
            let store = store.clone();
            move |cx| WorkspaceServiceImpl::new(cx, store)
        })?;
        Ok(())
    })?;

    // 资源 = handle + 一组绑定；feeds router 自己就是注册句柄。
    let feed = Arc::new(TelemetryFeed::new());
    let feeds = Arc::new(RadixRouter::<SrvCfg>::new(FeedsRoot));
    let view_id = feeds.view("telemetry/{id}", TelemetryViewTarget::new(feed.clone()))?;
    let pull_id = feeds.pull("telemetry/{id}", TelemetryPullTarget::new(feed.clone()))?;
    let head_id = feeds.head("telemetry/{id}", TelemetryHeadTarget::new(feed.clone()))?;
    top.bind_router("feeds", feeds.clone())?;   // 父层只挂载，不知道 feeds 内部规则

    let mut binding = /* ... 绑定 dock ... */;
    let server = MptpServer::<SrvCfg, _>::new(top.clone());
    let serve = server
        .serve_listener_async(&mut binding, 8)
        .may_cancel_with(NonCancellableToken::new()); // 示例：真实取消源由应用提供

    // 运行期下线资源：直接在资源 router 上撤销，不需要通知父 router。
    feeds.remove_route(view_id)?;
    feeds.remove_route(pull_id)?;
    feeds.remove_route(head_id)?;

    serve.await?;
    Ok(())
}
```

### 4.2 service 开发者：持有 service router，运行期追加绑定

`add_service` 会为 service 创建一个**子 router**（根 handler 为 `ServiceRoot`，负责
`Call` 分发与非 `Call` 的 405），并把它挂在 interface router 的 `SERVICE_PATH` 下。
构造闭包收到的 `RpcServiceCtx` 里有这个 service router 的句柄：

```rust
pub struct WorkspaceServiceImpl {
    store_: Arc<Store>,
    /// 本 service 的 router；路径都相对于 service 自己的根。
    router_: Arc<RadixRouter<SrvCfg>>,
}

impl WorkspaceServiceImpl {
    pub fn new(cx: &RpcServiceCtx<SrvCfg>, store: Arc<Store>) -> Self {
        WorkspaceServiceImpl {
            store_: store,
            router_: cx.router().clone(),
        }
    }

    /// 运行期挂一个报表资源：handle + 一组方法绑定；不需要资源 trait。
    pub fn expose_report(
        &self,
        id: ReportId,
        report: Arc<Report>,
    ) -> Result<Vec<RouteId>, RouteError> {
        let mut ids = Vec::new();
        ids.push(
            self.router_
                .view(&format!("reports/{id}"), ReportViewTarget::new(report.clone()))?,
        );
        ids.push(
            self.router_
                .pull(&format!("reports/{id}"), ReportPullTarget::new(report))?,
        );
        Ok(ids)
    }
}
```

服务实现者只拿得到 service router 的句柄：它不知道 interface router 还挂了哪些 service，
也不知道顶层 router 有哪些兄弟规则；它也无法修改父层或绝对根。

### 4.3 七种访问方法的绑定方式

```rust
// 方式一：每种方法一个入口，可以绑不同 handler。
feed_router.head("streams/{id}", StreamHead::new())?;
feed_router.view("streams/{id}", StreamView::new())?;
feed_router.post("streams", StreamCreate::new())?;
feed_router.drop("streams/{id}", StreamDelete::new())?;
feed_router.push("streams/{id}", StreamPush::new())?;
feed_router.pull("streams/{id}", StreamPull::new())?;
feed_router.call("streams/{id}", StreamCall::new())?;

// 方式二：一个 handler 响应多种方法（MethodSet）。
feed_router.on(
    "streams/{id}",
    MethodSet::VIEW | MethodSet::HEAD,
    StreamReadTarget::new(),   // 内部按 req.method() 分支：HEAD 不写 body

// 方式三：同一路径、不同方法分别绑定（底层即多条 handler 规则）。
feed_router.on("streams/{id}", MethodSet::VIEW, StreamView::new())?;
feed_router.on("streams/{id}", MethodSet::PULL, StreamPull::new())?;
```

### 4.4 运行期添加 / 删除资源

```rust
// 资源出现：在它所属的 router 上绑定；父 router 无需变更。
// feeds 是先前 bind_router 时保留的 Arc<RadixRouter<SrvCfg>> 句柄。
let id = feeds.view(&format!("telemetry/{name}"), TelemetryViewTarget::new(feed.clone()))?;

// 资源下线：撤销绑定；in-flight 请求继续持有 target 的 Arc。
feeds.remove_route(id)?;
// 若资源 router 不再需要，可从父层撤销挂载；但 in-flight 仍然安全。
```

删除语义：

- `remove_route` 只影响该 router 之后的新匹配；in-flight 请求不受影响；
- 父 router 完全不需要知道子 router 内部增删（这正是分层 router 的隔离收益）；
- 资源的业务删除（`DROP`）与路由撤销是两件事；框架不强制；
- 资源没有框架级生命周期：应用持有 handle 与 `RouteId`/router 句柄即可。

## 5. 现状与差距（2026-11-07）

### 5.1 现状事实

**`mptp_smux::serving`**

- `TrPathHandler`（`const PATH`）、`TrPathRouter`（单一 `Handler` + `match_path(&self, &str)
  -> Option<&Handler>`）、`TrPathRouterMut`（**全仓无实现、无调用**）；
- 内置 `Router<C, R: TrRouteValues>` 用 `tlist` 类型级列表做「最长前缀 → handler」，
  装配期消费式构建；`Router::match_path` 恒等返回 `Some(self)`，真正的匹配发生在
  `handle_async` 内部；
- `RouterCtx<C>` / `RpcServiceCtx` 都是 ZST 占位：`Router::route` 自己 `new()` 一个
  `RouterCtx`，`RpcRouter::new` 接收后丢弃（`_ctx`），`add_service` 自己 `new()` 一个
  `RpcServiceCtx`——**从 ctx 到 service 构造闭包的链路是断的**；
- `MptpServer<C, R>` 的约束是 `R: TrPathRouter` 且 `R::Handler: TrReqHandler<C>`；
  `serve_*` 只拿 `&self`；未命中返回 `ServeError::NotFound`，**channel 被丢弃、不写 404**；
- `serve_listener_async_` 内联 `await` 每条 channel 的 handler，串行 accept；错误直接
  `?` 上抛终止监听循环；取消令牌实际未启用（两个 demo 都传 `NonCancellableToken`）。

**`rpc_core_v1::serving`**

- 内联链：`RpcRouter<I, S>` 用 `tlist` 在 interface 前缀下按 `SERVICE_PATH` 做最长前缀，
  只接受 `Call`（否则 405），未命中写 404；`add_service` 消费式构建；
- 队列链：`TrRpcRouter` / `RpcRouterHandler` / `RpcJob` / `ServiceRoute` /
  `TrRpcServiceRoute`，`rpc_router_trie` 提供独立 trie 实现；**当前无运行期使用者**；
- 两处各有一份 `path_prefix_len_`（`mptp_smux` 与 `rpc_core_v1`），语义相同、代码重复。

**调用点**

- 本仓内运行期只有两个 demo 使用 router，且各自带一份本地 `Router<T>`：
  `mptp_smux_v1_demo`（路径 → `DemoHandler`）与 `rpc_demo`（空前缀 → 手写 queue 版
  `RpcRouter`）；
- 仓库内的 `Router::call` / `add_service` 仅见于单测、doctest 与编译期断言；
- 仓库外的 `mptp_cs_smoke`（同级目录、独立 workspace，path 依赖本仓的 `mptp_smux` /
  `rpc_core_v1`）仍使用 `Router::call + RpcRouter::add_service` 装配，11 条 RPC 的 e2e
  是迁移时的回归基准。

### 5.2 能力矩阵（今天 → 目标）

| # | 能力 | 今天 | 目标 |
| --- | --- | --- | --- |
| 1 | 可注入 router 实现 | ⚠️ 有缝，但受单一 `Handler` / 借用返回 / 无方法参数限制，且内置实现恒等返回自身 | ✅ `TrRouter` + `Arc<dyn>` |
| 2 | 运行期增删路由规则 | ❌ | ✅ 每个 router 独立 `bind_handler` / `bind_router` / `remove_route` |
| 3 | 每层知道自己的前缀 | ❌（`RouterCtx` 是 ZST） | ✅ 各 router 自根；`RouteRequest` 给绝对 `matched_prefix` / `remaining` |
| 4 | 只能向下追加、不能覆盖 | ❌ | ✅ router 自根 + 规则冲突检测 + 无 replace；父层不枚举子 router 内部规则 |
| 5 | 方法参与路由 | ❌（顶层只透传） | ✅ `MethodSet` 参与匹配 |
| 6 | 七种方法可用 | ⚠️（单 handler 可自己处理任意 method，但缺框架级方法匹配与回复 helper） | ✅ 方法糖 + 按方法绑定 target；资源不抽 trait |
| 7 | 统一 404 / 405 / redirect | ⚠️ RPC 层自己写；MPTP 层直接丢 channel | ✅ 每个 router 自己的根 handler；子 router 未命中不上抛父层 |
| 8 | 每个 router 的根 handler 必存且不可覆盖 | ❌ | ✅ `RadixRouter::new(root)`；顶层绝对根、子 router 相对根 |
| 9 | 路径参数 | ❌ | ✅ `{name}` / `{*rest}`（matchit 语法） |
| 10 | 冲突检测 | ❌（重复前缀静默并存） | ✅ `RouteError::Conflict` |
| 11 | 请求取消与定时策略 | ❌（令牌实际未启用） | ⚠️ `RequestCancel` 契约先定；超时规则与并发接入见 7.2 / 11.2，仍是 P3 |
| 12 | 静态零装箱 | ✅ | ❌ 放弃：统一表必须类型擦除 |

### 5.3 主要取舍

1. **静态零装箱 → 每请求一次 `Arc` + boxed future**：统一到运行期表后这是必然代价。
   单个请求路径上只有一次 `Arc` clone 与一次装箱，通常可接受；若将来有实测热点，再评估
   `Small`-future 或静态 fast-path，但不作为本轮设计目标。
2. **`tlist` 路由机器删除**：`RouteValues` / `TrRouteValues` / `TrPathRouterList` 这些
   `#[doc(hidden)]` 但公开导出的类型会随旧 `Router` 一起删除。
3. **`TrReqHandler` 保留**：它是「单 handler 行为契约」，与 router 解耦；新设计通过
   `ReqHandlerTarget` 继续使用它，避免所有 handler 重写。
4. **RPC 队列链**：`rpc_router_trie` 独立 crate 与其他队列类型当前无运行期使用者；
   统一 router 落地后，队列 / 背压应表达为 **target 内部实现**（一个 target 自己持有
   有界队列与 sender），而不是第二个 router。去留见 11.8。
5. **路由组织从「单表 + 前缀规则」改为「分层 router + 精确 handler 规则」**：每个
   router 以自己为根，父层只挂子 router；需要「整棵子树由一个 handler 负责」时，写一个
   子 router 并给它一个相对根 handler，而不是注册前缀规则。
6. **资源不再是框架 trait，也没有 `RouteHandle` 包装**：资源 = handle + 一组绑定；应用
   持有 `Arc<RadixRouter>` 或父层 router 句柄，直接 `remove_route(RouteId)`。

## 6. RPC 层收敛方案

### 6.1 映射：interface / service 都是子 router

统一 router 落地后，RPC 的两级命名空间不再需要框架级「interface / service」概念，
它们只是两个普通子 router：

| RPC 概念 | 在分层 router 中 |
| --- | --- |
| interface（`I::PATH`） | 一个子 router，根 handler = interface 默认根；挂在顶层 router 的 `I::PATH` 下 |
| service（`SERVICE_PATH`） | 一个子 router，根 handler = `ServiceRoot`；挂在 interface router 的 `SERVICE_PATH` 下 |
| service 之下的资源 | service router 内的 handler 规则（或更深子 router） |
| `Call` 方法 | `ServiceRoot` 内部按 `AccessMethod::Call` 分发（不注册 handler 规则） |
| 非 `Call` / 未知子路径 | `ServiceRoot`（service router 的根 handler）决定 405 / 404 |

因此 `rpc_core_v1` 只提供「构造并挂载这两种 router」的辅助函数；框架核心不知道
interface / service 的存在。

### 6.2 新增 API（`rpc_core_v1::serving`）

```rust
/// 在任意 `TrRouter` 上挂载 RPC interface 子 router。
///
/// 提供 blanket 实现：`impl<C, T> TrRpcRouterExt<C> for T where T: TrRouter<C> + ?Sized`，
/// 因此 `Arc<RadixRouter<C>>` 也可直接调用。
pub trait TrRpcRouterExt<C: TrServingConfig>: TrRouter<C> {
    /// 用默认根 handler（`DefaultRootHandler`）创建 interface router 并挂载。
    fn rpc_interface<I: TrRpcInterface>(
        &self,
        build: impl FnOnce(&RpcInterfaceCtx<I, C>) -> Result<(), RouteError>,
    ) -> Result<(), RouteError>;

    /// 用自定义 interface 相对根 handler。
    fn rpc_interface_with_root<I: TrRpcInterface>(
        &self,
        interface_root: impl TrRouteTarget<C> + 'static,
        build: impl FnOnce(&RpcInterfaceCtx<I, C>) -> Result<(), RouteError>,
    ) -> Result<(), RouteError>;
}

/// interface router 的构造上下文。
pub struct RpcInterfaceCtx<I: TrRpcInterface, C: TrServingConfig> {
    router_: Arc<RadixRouter<C>>,
    _interface_: PhantomData<fn() -> I>,
}

impl<I: TrRpcInterface, C: TrServingConfig> RpcInterfaceCtx<I, C> {
    pub fn router(&self) -> &Arc<RadixRouter<C>>;

    /// 为 service 建一个子 router（根 handler = `ServiceRoot`），挂在 `SERVICE_PATH`。
    pub fn add_service<S>(
        &self,
        make_service: impl FnOnce(&RpcServiceCtx<C>) -> S,
    ) -> Result<(), RouteError>
    where
        S: TrRpcService<I, C, Err = RpcError> + Send + Sync + 'static;
}

/// service router 的注册上下文。
pub struct RpcServiceCtx<C: TrServingConfig> {
    router_: Arc<RadixRouter<C>>,
}

impl<C: TrServingConfig> RpcServiceCtx<C> {
    pub fn router(&self) -> &Arc<RadixRouter<C>>;
}
```

`rpc_interface` 的实现：

```text
let interface_router = Arc::new(RadixRouter::<C>::new(interface_root));
build(&RpcInterfaceCtx { router_: interface_router.clone() })?;
self.bind_router(I::PATH, interface_router)?;   // 父层只记住前缀与匹配句柄
```

`add_service` 的实现需要解决「根 handler 需要 service 实现、service 实现又需要
service router 句柄」的循环；实现上可以：

1. 建一个 `ServiceRoot` 的共享槽（`Arc<OnceLock<S>>`）；
2. 先建 service router（根 handler 指向这个槽）；
3. 用 `RpcServiceCtx { router_: service_router.clone() }` 调 `make_service`；
4. 把实现装进槽，再把 service router 挂到 interface router 的 `SERVICE_PATH`。

装配期完成后槽一定有值，不影响请求路径。

### 6.3 `ServiceRoot`：service router 的相对根 handler

service router 的根 handler 同时承担：

1. `Call`：解码 body enum → `TrRpcService::dispatch_async` → 写回复 → 收尾；
2. 非 `Call`：回 `405 + Allow`（优先使用 `req.fallback()` 的 `allowed`，否则 `Allow: Call`）；
3. 未知子路径上的 `Call`：返回 404 或交给业务错误映射。

```rust
struct ServiceRoot<S, I, C> {
    service_: Arc<OnceLock<S>>,
    _interface_: PhantomData<fn() -> I>,
    _config_: PhantomData<fn() -> C>,
}

impl<S, I, C> TrRouteTarget<C> for ServiceRoot<S, I, C>
where
    C: TrServingConfig + 'static,
    I: TrRpcInterface,
    S: TrRpcService<I, C, Err = RpcError> + Send + Sync + 'static,
{
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, C>) -> RouteTargetFuture<'f> {
        Box::pin(async move {
            let cancel = req.cancel().child_token();
            match req.method() {
                AccessMethod::Call => {
                    let parts = req.into_parts();
                    let mut ctx =
                        RpcCallCtx::<C>::new(parts.location, &*parts.headers, parts.tx, parts.rx);
                    // 示意：实际实现应把「槽未初始化」映射成错误而不是 expect。
                    let service = self.service_.get().expect("装配完成后槽一定有值");
                    let result = service
                        .dispatch_async(&mut ctx)
                        .may_cancel_with(cancel);
                    ctx.close_async().await;
                    result.map_err(|err| RouteTargetError::Internal(err.to_string()))
                }
                _ => {
                    let allowed = match req.fallback() {
                        Some(FallbackInfo::MethodNotAllowed { allowed, .. }) => allowed,
                        None => MethodSet::just(AccessMethod::Call),
                    };
                    let parts = req.into_parts();
                    let _ = (allowed, parts.cancel);
                    todo!("写 405 + Allow 并收尾")
                }
            }
        })
    }
}
```

| 项 | 处置 |
| --- | --- |
| `TrRpcInterface::PATH` / `#[rpc(path = "...")]` | **保留**：线上路径唯一来源；在 `rpc_interface` 中作为挂载前缀 |
| `TrRpcService` / `SERVICE_PATH` / body enum / `TrRpcCallCtx` / 宏生成物 | **保留**，不改宏 |

## 7. 资源、七种方法与并发（router 之外的部分）

router 只做「规则 → handler / 子 router」与逐层匹配。资源不是框架类型，而是应用侧
「**handle + 一组 route 绑定**」的运行时组合。

### 7.1 七种访问方法与 target

| 方法 | 典型 target | 成功 | 常见失败 | body / 流 |
| --- | --- | --- | --- | --- |
| `Head` | 元信息 target | `200` | `404` | **不写 body** |
| `View` | 读取 target | `200` | `404` / `406` | 回复体；可选 suffix |
| `Post` | 创建 / 上传 target | `201` + `Location`（新建）或 `200` | `400` / `405` / `Status::new(409)` | 请求体 |
| `Drop` | 删除 target | `204`（`Status::new(204)`）或 `200` | `404` / `Status::new(409)` | 无 |
| `Push` | 客户端推流 target | `200` / `Status::new(202)` | `404` / `405` | 请求 suffix 流 |
| `Pull` | 服务端拉流 target | `200` + 持续写 | `404` / `405` | 回复 suffix 流 |
| `Call` | RPC service router 的根 handler | `200` + 编码结果 | `4xx` / `5xx` | 现有 RPC 链不变 |

约定：每种方法可独立绑定 handler（`.view(..).pull(..)`），也可用
`on(rule, MethodSet, handler)` 让一个 handler 同时响应多种方法；协议规定 `Head` 对任意
资源总是可用，但框架不自动合成，资源暴露时应显式绑定 `Head` handler。

### 7.2 serving 层还需要什么

1. **请求级取消（`RequestCancel`）**：v1 只建立契约与占位实现；「按规则定时取消」
   （超时、每请求预算等）需要 serving / router 的策略层实现；
2. **并发接入**：`serve_listener_async_` 目前内联 `await` handler，`Pull` 长流会饿死
   后续 channel；需要 spawner 或并发驱动（P3）；
3. **单 channel 错误隔离**；
4. **优雅关闭 `ServeHandle`**；
5. **`Allow` 头**：405 的标准表达，见 11.3；
6. **观测**：每 router / 每 route 计数、活跃流、拒绝原因；不引入中间件链。

### 7.3 资源 = handle + 绑定（不抽 trait）

- **handle**：应用自己的业务对象（通常 `Arc<T>`），框架不认识它的类型；
- **绑定**：为该 handle 在某个 router 上登记的一组 handler 规则（路径模式 + 方法 +
  target）；target 通常持有 handle 的克隆；
- 资源的「存在」= handle 被持有 + 至少一条绑定存在；
- 资源不需要、也不应该实现「七种方法齐全」的 trait；绝大多数资源只提供其中几种；
- 资源生命周期由应用自己的 handle 与 router 句柄管理；撤销绑定不影响 in-flight 请求；
  长流退出由 target 自己持有资源级信号，框架不提供统一资源抽象。

## 10. 测试与验收建议

### 10.1 单元测试

- 路径规范化：首尾 `/`、空段、参数语法、catch-all 位置；
- 单个 router 内：handler 规则精确匹配、静态 > 参数 > catch-all、冲突插入报错、
  同路径不同方法共存；
- 规则二选一：同一 router 内 handler 规则与子 router 挂载路径重叠 / 互为前缀 → `Conflict`；
- 子 router：前缀命中后剩余路径递归；父层把 `matched_len` / `blocked_len` 叠加正确；
- 子 router 未命中：由子 router 自己的根 handler 返回，**不会**调用父层根 handler 或
  兄弟 router；
- 方法绑定：七种方法糖各自生成正确的 `MethodSet`；`on(MethodSet, ..)` 多方法共用一个
  handler；方法不支持时由当前 router 的根 handler 拿到 `FallbackInfo`；
- 运行期增删：在子 router 上 `bind_handler` / `remove_route` 不影响父层；并发
  `bind_handler` / `bind_router` / `remove_route` / `match` 无数据竞争；
- `RequestCancel`：target 拿到的是可取消令牌；适配器 / 长流 target 必须把
  `child_token()` 传进 await；实现中不得断言令牌是 `NonCancellableToken`；
- `ReqHandlerTarget`：旧 handler 经适配器行为不变；
- 自定义 `TrRouteMatcher` / `TrRouter`：一个最小实现能接入 `MptpServer`（编译期 +
  运行期各一条）。

### 10.2 集成 / e2e

- 装配两个 demo 后，原有客户端脚本行为不变；
- `mptp_cs_smoke` 的 11 条 RPC（`ApiV1` / `ApiV2`）回归通过；
- 服务运行中在资源 router / service router 上绑定资源 → 客户端 `VIEW` 成功；撤销 →
  新请求落到该 router 的根 handler；
- 顶层绝对根与子 router 相对根的 404 / 405 / redirect 输出可被客户端识别；
- interface router / service router：非 `Call` 请求由 service router 的根 handler 返回
  405 + `Allow`；未知顶层路径由绝对根返回 404；子 router 未命中不回到绝对根；
- 两条 `PULL` + 一条 `CALL` 并发（P3 之后）。

### 10.3 约束

- 测试使用中英双语文档注释（`AGENTS.md` 第 2 条）；
- 单元测试 ≤1 分钟、全量 ≤5 分钟（第 12 条）；
- 库代码不 `unwrap` / `expect`；
- 新公开项有 `///` 文档与可编译示例。

## 11. 开放问题

1. **是否引入 matchit 依赖？**
   本稿建议**不引入**：matchit 的 handler 规则精确匹配语义已与本设计对齐，但缺少方法
   维度、分层 router / 根 handler、运行期并发增删与 `Arc` target；且当前环境离线依赖
   受限。默认实现按它的设计自研 trie；可复用 `rpc_router_trie` 的段式 trie 代码。
2. **`RequestCancel` 的产生位置与类型擦除**
   契约已定：每个被分发的请求都带 `RequestCancel`，**可能取消**，handler 必须按可取消
   编写。未定的是实现细节：
   (a) 产生位置：由 `MptpServer` 从 serve 令牌派生，还是在 router 上增加「按规则产生
       请求取消令牌」的策略方法（超时、每请求预算、router 级配额等）？
   (b) 类型擦除：`RequestCancel` 需要在内部从任意 `K: TrCancellationToken` 构造；是要求
       `K: Clone + 'static` 后包装，还是定义对象安全的 `TrErasedCancel` 再实现
       `TrCancellationToken`？
   (c) 超时规则与默认值：v1 可以先只做「serve 令牌 child、不超时」，但不得改变 handler
       侧「令牌可能取消」的契约。
3. **`Allow` 头**
   新增 `StdHeaderKey::Allow`（建议编号 `0xD7`：`0xD0`–`0xD6` 已被 `Server` / `Location` /
   `Last_Modified` / `Set_Cookie` / `ETag` / `Cache_Ctrl` / `Expires` 占用），还是先用
   用户自定义字符串键？若新增，需要协议两端同意，并决定方法名的编码格式。
4. **路径参数是否 P0 就支持？**
   本稿倾向支持（默认实现本来就按 matchit 设计）；若想缩小首版范围，可先只支持静态段 +
   catch-all，参数留到 P1。子 router 挂载路径第一版只支持静态前缀，见 11.20。
5. **根 handler 的安装位置**
   本稿要求每个 `RadixRouter::new(root)` 都提供根 handler：顶层的是绝对根，子 router 的
   是相对根。备选是允许「子 router 未显式给根 handler 时自动用 `DefaultRootHandler`」；
   需要确认是否强制显式给出。
6. **撤销的 RAII 包装**
   目前 `bind_handler` / `bind_router` 返回 `RouteId`，撤销要显式 `remove_route(id)`。
   是否提供 RAII `RouteGuard`（drop 自动撤销）？显式撤销对「资源 DROP 与路由撤销解耦」
   更可控；RAII 能防忘记撤销。可同时提供。
7. **静态零装箱是否保留可选 fast-path？**
   与「所有规则运行期可增删」冲突；本稿建议放弃，等真实性能数据再评估。
8. **队列链 / `rpc_router_trie` 去留**
   改成 target / router 内部实现（推荐）还是保留为独立可选 crate？11.1 说「可复用其段式
   trie 代码」只是代码级借鉴，不等于保留该 crate。
9. **router 句柄是否也承载应用状态？**
   目前 router 只承载根 handler + 局部规则；会话 / 连接上下文是否通过 router 句柄注入，
   还是留在 target 的构造闭包里？后者更简单，前者能统一传递。
10. **in-flight 与 drain**
    删除规则不打断 in-flight；由于资源不是框架类型，drain / grace period / 强制 reset
    由资源自己的 target 实现（框架可提供辅助工具）。是否需要框架级默认值或协议约定，
    需要确认。
11. **路由内省**
    是否需要每个 router 的 `rules()` / 计数 / 列出当前绑定（调试、admin、观测）？注意
    「父层不枚举子 router 内部规则」是本设计的隔离前提，内省 API 也应只在各自 router
    本地开放，不能跨层遍历。
12. **归一化边界**
    尾斜杠等价（本稿选择等价）、连续斜杠、percent-decode、大小写：哪些归 router，哪些
    归调用方？需要一次协议层确认，避免两端不一致。
13. **相对根 handler 是否允许「显式转发」给上层**
    本稿规定子 router 未命中只由自己的根 handler 处理，不允许框架自动上抛。如果子
    router 希望「自己没命中就交给父层」，应当在自己的根 handler 内显式转发（重定向或
    内部调用）。是否需要框架提供标准的「转发 / 链式根 handler」辅助类型，需要确认。
14. **注册绕过与路径封口**
    `bind_handler` / `bind_router` 是公开 trait 方法，拿到某个 `Arc<RadixRouter>` 的代码
    可以直接在该 router 上注册任意规则；它仍改不了父层与绝对根（没有父层句柄），但可能
    覆盖同 router 内既有规则吗？——冲突检测会拒绝同模式同方法，因此不会覆盖，只会新增。
    是否需要更严格的 newtype 封口，把「只能由持有者注册」表达出来？
15. **`FallbackInfo.allowed` 是否取并集**
    本稿取「路径精确命中的 handler 规则上所有方法槽的并集」。是否需要把该 router 内所有
    可命中规则的方法并集起来，还是只报当前这一条？需要协议/客户端行为确认。
16. **参数零拷贝优化**
    第一版 `RouteParams` 拥有所有权（拷贝参数名与值）。是否在 P2 改为 matchit 式零拷贝
    （参数名借路由表、值借 location）？后者需要 `RouteMatch` 带生命周期参数，会扩散到
    `RouteOutcome` / `RouteRequest`，建议等接口稳定后再做。
17. **子 router 挂载的撤销**
    `bind_router` 返回 `RouteId`；父层 `remove_route(mount_id)` 只应「摘掉挂载点」，不应
    递归删除子 router 内部规则（子 router 可能被多个父层共享，且父层不应看到其内部）。
    是否需要显式的「递归卸载 / 销毁」语义，需要确认。
18. **`bind_router` 与 handler 规则重叠的冲突策略**
    本稿规定同一 router 内子 router 挂载路径与 handler 规则路径不得重叠 / 互为前缀。是否
    需要在挂载时对「已有更长 handler 规则」给出警告 / 冲突，还是允许（但匹配会含糊）？
19. **子 router 挂载是否允许参数前缀**
    第一版挂载路径只允许静态段（便于前缀匹配与冲突检测）。是否支持 `users/{id}` 这类
    参数化挂载（把参数交给子 router 的根 handler）？会显著增加匹配复杂度，建议后置。
20. **子 router 挂载路径与协议层路径的关系**
    `I::PATH` / `SERVICE_PATH` 由宏生成为 `&'static str`，挂载路径也是静态字符串；是否
    需要支持运行期拼出的动态挂载路径（例如多租户前缀）？如需要，挂载路径的存储与冲突
    检测要重新设计。
21. **循环挂载与共享挂载**
    子 router 是 `Arc<dyn TrRouteMatcher>`，把它挂回自己的子树（或形成环）会导致递归
    匹配不终止；同一个子 router 挂到多个父 router 则可能是合理需求。是否需要检测环、
    是否允许共享挂载，需要明确。
22. **子 router 的根 handler 默认值**
    本稿要求每个 `RadixRouter::new(root)` 都显式给根 handler。是否提供
    `RadixRouter::new_with_default_root()`（内部用 `DefaultRootHandler`）作为便利构造，
    需要确认。

## 12. 被取代的初稿方案（决策记录）

| 初稿方案 | 被取代原因 |
| --- | --- |
| 两层 router：MPTP 顶层 + RPC 层 | RPC 的路径匹配与 MPTP 层语义相同，只是 router 嵌套；两层会重复实现匹配与 404/405 |
| 静态 `tlist` router 保留、动态表并行 | 用户要求「不再支持仅静态的路由规则」；双入口会把零装箱变成永久兼容负担 |
| 旧的三层拆分：`TrRouteMatcher` / `TrRouteTable` / `TrRouteTarget` | 现在保留 `TrRouter`（注册）+ `TrRouteMatcher`（匹配）+ `TrRouteTarget`（目标）三条最小契约；不再有 `TrRouteTable` |
| `PathOnly` / `MptpServer::with_table` | 没有需要适配的旧入口，直接切换更干净 |
| 资源放置 A/B/C 模型 | 资源就是「handle + 一组绑定」，在哪个 router 上绑定就属于哪个命名空间 |
| `ResourceHandler` 统一写 404 / 405 | 方法与兜底语义收敛到各 router 自己的根 handler；资源只是 handle + 绑定 |
| 静态路径零装箱是硬目标 | 统一运行期 router 表的必要代价；改为「每请求一次擦除」，性能数据出来后再定优化 |
| 「空前缀绑定 + 任意祖先回退」的兜底 | 用户修正：改为「每个 router 自带根 handler，下层未命中由本层兜底，不上抛」 |
| route 作为「前缀 + 剩余路径」 | 用户修正：handler 规则改为精确匹配；需要整棵子树时写子 router + 相对根 handler |
| target 内部一律传 `NonCancellableToken` | 用户修正：`RouteRequest` 携带可取消的 `RequestCancel` |
| `TrResource` / `ResourceTarget` 资源抽象 | 用户修正：资源不是 trait，而是 handle + 一组绑定 |
| **level / interface / scope 作为框架概念** | **本版修正：全部取消，改为可递归嵌套的分层 router；RPC 的 interface / service 只是子 router 实例** |
| **「全局一张路由表」+ `insert_level` / `insert_route` 全局注册** | **本版修正：每个 router 以自己为根拥有局部表；父 router 不枚举子 router 内部规则；挂子 router 用 `bind_router`** |
| **TrRouter 四个以上注册入口（level / route / scope / ...）** | **本版修正：添加规则只有两个入口——绑定 handler、绑定子 router** |
| **七种方法用内部槽位绑定、无统一写法** | **本版修正：参考 `Router::call` 风格，每种方法一个方法糖，另可用 `MethodSet` 让一个 handler 响应多种方法** |

---

## 13. 附：给 service 开发者的三句话

1. **今天**：router 是「路径前缀 → 一个 handler」的静态表；你拿到的 ctx 只是占位，
   运行期不能注册任何东西。
2. **将来**：你拿到的是**自己这一层的 router 句柄**（以自己为根，看不到父层、兄弟与
   子树内部规则）；你只能在自己的 router 上绑定 handler 或挂子 router，更上层与你无关。
3. **现在能做的准备**：把业务资源的「方法处理」「路径注册」「生命周期」分开写；资源就是
   你持有的 handle + 一组绑定，不需要等框架提供某种资源 trait。只要不依赖具体 router
   类型，分层 router 落地时迁移成本最小。
