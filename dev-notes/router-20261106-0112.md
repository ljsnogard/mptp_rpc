# 统一 Router 设计：可注入契约、嵌套作用域与运行期资源绑定

- 日期：2026-11-06 01:12 初稿；**2026-11-07 修订（决策转向）；2026-11-07 二次修订（两类根 handler、请求取消令牌、资源概念）**
- 状态：设计提案 + 契约草案 + 示例用法；**尚未实施**
- 范围：`mptp_smux::serving` 的 router 抽象与默认实现、`MptpServer` 接缝，以及
  `rpc_core_v1::serving` 的 RPC 路由层如何收敛到它
- 不在范围：`abs_smux` 传输层、ring 内存准备、报文前缀的线上格式、业务 body codec
- 相关文档：
  [`rpc-framework-20261020-0332.md`](rpc-framework-20261020-0332.md)、
  [`mptp-protocol-20261020-0200.md`](mptp-protocol-20261020-0200.md)、
  [`../DESIGN_BLUEPRINT.md`](../DESIGN_BLUEPRINT.md)

> **本版推翻了初稿的若干方向**：不再有「MPTP 层 router + RPC 层 router」两层结构；不再
> 保留「静态 tlist 实现 + 动态表」双入口；不再用 A/B/C 模型讨论资源挂在哪一层；
> `TrRouteMatcher` / `TrRouteTable` / `PathOnly` 等草案名作废。新的核心决策是：
>
> 1. **只有一个 router**，固定在 MPTP 层完成全部 routing 绑定；
> 2. router 抽成可注入的 `TrRouter` trait，默认实现以 [matchit](https://crates.io/crates/matchit)
>    为数据结构与语法参考，功能上参考 [salvo](https://salvo.rs) 的嵌套 Router；
> 3. 所有规则都**运行期可增删**；沿用旧代码种子的思路——`Router::call` /
>    `RpcRouter::add_service` 传给构造闭包的 `ctx` 就是注册入口，新设计把它实化为
>    `RouterCtx` / `RpcServiceCtx`；
> 4. 每一层（`RouterCtx`）都知道自己的匹配前缀，只能在自己的前缀下追加**更长**路径，
>    不能覆盖既有规则；
> 5. 由此，**根路径上的 handler 必须存在且不可被下层覆盖**，它承接所有没有被更长规则
>    命中的请求，决定回给客户端 404、405 还是 redirect。
>
> 本文中的新 trait / 类型名仍是**草案名**，用于讨论。按 `AGENTS.md` 第 1 条，任何公开
> API 变更在实施前都需要团队逐项确认；第 9 节给出变更清单。

## 0. 摘要

### 0.1 一句话

Router 是一棵由「**层级**（level，即一级 router）与**具体路由**（route）组成的树：
层级是带**相对根 handler** 的路由器节点；route 是层级之下的「**精确路径模式 + 方法集合
→ target**」。匹配时**先找精确命中的 route**；找不到时由**请求实际进入的最深层级**的
相对根 handler 兜底，**绝不会越过它直接抛给绝对根 handler**。根级（空前缀）的相对根
handler 就是**绝对根 handler**，也是整个树的最终兜底。所有层级与 route 都通过作用域化
的 `RouterCtx` 在运行期增删，且只能向下追加。

### 0.2 关键决策

| # | 决策 | 结论 | 主要理由 |
| --- | --- | --- | --- |
| 1 | 路由层次 | **只保留 MPTP 层一个 router** | RPC 的 interface / service 只是两级层级，不需要第二个 router；避免两套匹配算法随版本漂移 |
| 2 | 注入方式 | 抽出 `TrRouter<C>` trait，默认实现 `RadixRouter<C>` | `MptpServer` 只依赖 trait；用户可以替换 trie / 匹配算法 |
| 3 | 实现参考 | matchit 的精确路径匹配（`{id}` / `{*rest}`、静态 > 参数 > catch-all、冲突检测） | 本设计的 route 也是精确匹配，语义与 matchit 基本对齐；只补 method、层级根兜底与运行期增删 |
| 4 | 功能参考 | salvo 的嵌套 Router、每层作用域、方法声明、路径参数 | salvo 的 404/405 在 Service/Catcher 层；本设计把兜底下放到**每一层自己的相对根 handler** |
| 5 | 两类根 handler | **绝对根 handler**（根级、构造必填）与**相对根 handler**（每个子层级挂载必填）；兜底只到「最深进入层级」的相对根 | 用户修正：下层 router 无法匹配具体 handler 时，必须由该层相对根兜底，不能抛给唯一绝对根 |
| 6 | 匹配语义 | **route 精确匹配优先**；route 不匹配（或方法不支持）时落到最深进入层级的相对根 handler | route 不再承担「前缀 + 剩余路径」；剩余路径只出现在根 handler 的请求上下文里 |
| 7 | 静态 / 动态 | **不再区分**；所有层级与 route 走同一张运行期表 | 用户要求运行期动态资源；零装箱静态路径优势放弃，接受每请求一次 `Arc` + 装箱 |
| 8 | 覆盖规则 | 无 replace API；route 冲突报错；层级与 route 都只能追加严格更长的路径 | 用结构保证「不能覆盖启动前规则」；新挂载的层级不遮挡既有精确 route |
| 9 | 方法维度 | route 绑定携带 `MethodSet`；匹配按方法过滤；方法不支持时由最深进入层级的相对根决定 405 / 404 / redirect | 七种访问方法参与路由；405 决策下放到层级的根 handler |
| 10 | 请求取消令牌 | `RouteRequest` 携带 `RequestCancel`：**可能取消**，不得假定为 `NonCancellableToken` | 用户修正：未来每请求由 router 按规则给定时取消令牌，机制未实现不等于 handler 可以假定不可取消 |
| 11 | 资源概念 | 资源 = 应用持有的 **handle** + 若干 **route 绑定**；**不抽 `TrResource` trait** | 用户修正：绝大多数资源不可能提供完整七种方法；资源只是句柄与路由的运行时组合 |

### 0.3 与初稿的关系（被取代的内容）

| 初稿内容 | 现状 | 取代原因 |
| --- | --- | --- |
| 两层 router：顶层 `Router` + RPC 层 `RpcRouter` | **作废** | RPC 的路径匹配没有独立语义，只是层级嵌套；两层会重复实现匹配与 404/405 |
| 静态 `tlist` `Router` + 动态表双入口 | **作废** | 用户要求所有绑定都能运行期增删 |
| `TrRouteMatcher` / `TrRouteTable` 拆分 | **作废** | 注入面只需要一个 `TrRouter` |
| 资源放置模型 A / B / C | **作废** | 资源不是 router 的层级概念，只是「handle + 路由绑定」 |
| **「空前缀绑定 + 任意祖先回退」的兜底模型** | **本轮修正为：绝对根 + 每层相对根，兜底只到最深进入层级** | 用户修正：下层 router 无法匹配具体 handler 时必须由该层相对根负责，不能抛给唯一绝对根 |
| **「target 内部一律传 `NonCancellableToken`」** | **本轮修正为：`RouteRequest` 携带 `RequestCancel`，必须按可能取消处理** | 用户修正：不能假定取消令牌都是不可取消的 |
| **`TrResource` 资源 trait** | **本轮删除** | 用户修正：资源不是需要框架抽象的能力集合，而是 handle + route 绑定的运行时概念 |
| 取消令牌如何穿过擦除层 | **保留为开放问题**（`RequestCancel` 的具体产生机制与类型擦除细节） | v1 先定契约，定时取消机制未实现 |

## 1. 设计不变量

下面十条是后续所有讨论与实现的基准；与本文件其他内容冲突时以本节为准。

| # | 不变量 | 含义 |
| --- | --- | --- |
| I1 | **单一层次** | 全部 routing 绑定发生在 MPTP 层；`rpc_core_v1` 只提供层级的注册 helper 与 target 适配器 |
| I2 | **单一可变表** | 层级与 route 在装配期和运行期使用同一套 `&self` API（内部同步）；不存在「冻结」状态 |
| I3 | **只向下追加** | 层级挂载与 route 绑定都发生在某个既有作用域之下，路径**严格长于**该作用域前缀；无 replace API；`(path, method)` 冲突报错 |
| I4 | **每层知道前缀** | `RouterCtx::prefix()` 给出当前层级前缀；`RouteRequest::matched_prefix()` / `remaining()` 给出本次命中的前缀与剩余路径 |
| I5 | **两类根 handler** | 根级必须有**绝对根 handler**（构造时安装）；每个挂载的子层级必须有**相对根 handler**（挂载时安装）；兜底只到「请求实际进入的最深层级」的相对根，不得跳过它 |
| I6 | **精确 route 优先，且不可被层级遮挡** | 先找精确命中的具体 route；新挂载的层级不改变既有 route 的命中结果（「不能覆盖启动前规则」的另一方面） |
| I7 | **结果拥有所有权** | `match_route` 交出 `Arc<dyn TrRouteTarget>` 与拥有所有权的匹配信息；router 的读写锁不得跨 `await` 持有 |
| I8 | **target 负责回复与收尾** | 命中 target 之后，写回复与 channel 收尾由 target 完成；router / server 只在实现缺根级时写协议级 404 |
| I9 | **请求级取消令牌可取消** | 每次路由到 target 都带一个 `RequestCancel`；它可能因超时 / 关闭 / drain 被取消，target 不得假定它永不取消 |
| I10 | **资源不是框架类型** | 资源是应用侧的 handle 与一组 route 绑定；框架不定义 `TrResource` 之类的能力集合 trait |

## 2. 概念模型

### 2.1 调用链

```text
MptpServer<C, R>
  │  解码请求前缀：method / location / headers
  │  为本次请求产生 RequestCancel（v1：从 serve 令牌派生；超时规则未实现）
  │
  ├─ R: TrRouter<C>::match_route(method, location) -> RouteOutcome
  │     │
  │     ├─ Found(RouteMatch { target, matched_len, params, fallback })
  │     │     │
  │     │     ├─ target = 精确命中的 route 的 target
  │     │     │     matched_len = location 长度；params = 路径参数
  │     │     │
  │     │     └─ target = 「最深进入层级」的相对根 handler
  │     │           matched_len = 该层级前缀长度；remaining = 前缀之后的路径
  │     │           fallback = Some(..) 当某个 route 路径命中但方法不支持
  │     │
  │     └─ Unmatched(UnmatchedReason)    ← 只有实现缺根级绑定时才出现
  │
  └─ target.handle_route(RouteRequest { ..., cancel_: RequestCancel })
        ├─ 普通 handler / 资源 target / RPC ServiceRoot / 层级根 handler
        └─ 写回复 → 半关闭 tx → 读完 rx（与旧 TrReqHandler 契约相同）
```

### 2.2 概念对照

| 概念 | 含义 | 今天的代码 | 新设计 |
| --- | --- | --- | --- |
| level（层级） | 一级 router，拥有独立的相对根 handler 与 route 集合 | 不存在（只有单个 `Router` / `RpcRouter`） | `RouterCtx` 对应的节点；`scope()` 挂载 |
| route（具体路由） | 「精确路径模式 + 方法集合 → target」 | `Router::route` + `RouteValues` | `RouterCtx::route(...).on(methods, target)` |
| 绝对根 handler | 根级（空前缀）的相对根 handler，最终兜底 | 不存在 | `RadixRouter::new(absolute_root)` |
| 相对根 handler | 某个子层级自己的兜底 handler | 不存在（`RpcRouter` 的 404/405 算是近似物） | `RouterCtx::scope(rel, relative_root)` |
| target（目标） | 被路由到的对象，拥有回复权 | `TrReqHandler<C>` 实体 | `Arc<dyn TrRouteTarget<C>>`（旧 handler 经适配器） |
| resource（资源） | 应用持有的 handle + 一组 route 绑定 | **不存在** | **不是框架类型**：用户自定义类型 + 注册的 route |
| method（方法） | 七种访问方法之一 | `AccessMethod`，只透传 | `MethodSet` 参与 route 匹配 |
| 请求取消 | 一次请求可能被取消 | 只靠外层 `may_cancel_with` | `RequestCancel` 随 `RouteRequest` 交付 |

### 2.3 匹配语义

#### 2.3.1 路径规范化

进入匹配前，`location` 统一做以下规范化。与今天的实现保持兼容的是「去掉首尾 `/`、按
完整段匹配、不做 percent-decode」；新增的是参数与 catch-all 语法：

1. 去掉首尾的 `/`；`/topic/chat/42` 与 `topic/chat/42` 等价；
2. 按 `/` 切段，**不做** percent-decode、不做大小写归一化；
3. 空段（连续 `//`）不匹配任何非根 route；是否把空段视为非法输入见 11.12；
4. 语法采用 matchit 0.8+ 的花括号形式：`{name}` 匹配一个非空段；`{*rest}` 匹配剩余
   全部路径（可为空串，但只能位于路径末尾）；
5. 层级前缀与 route 模式使用同一套段语义；层级前缀只能是静态段。

#### 2.3.2 route 匹配：精确路径

具体 route 采用**精确匹配**（与 matchit 一致）：整条规范化 `location` 必须被路由模式
完全消费；`{name}` 消费一个段，`{*rest}` 消费剩余全部（可为空）。

- 同一层内的优先级：`静态段 > 命名参数 > catch-all`，失败要回溯；
- route 冲突规则与 matchit 对齐：同结构不同参数名冲突、一个段内不能有多个参数、
  catch-all 只能位于末尾且不能有子节点；
- 同一路径、方法集合不相交的 route 可以共存（例如同一路径分别绑 `Call` 与 `View`）；
- **route 不再承担「前缀 + 剩余路径」**：`{*rest}` 是表达「吃掉剩余段」的唯一方式；
  需要「整个子树交给一个 handler」时，应当挂载一个**层级**并为它提供相对根 handler，
  而不是注册一个前缀 route。

#### 2.3.3 兜底顺序：最深进入层级

对一次 `(method, location)`，匹配按以下顺序得出结果：

1. **先找精确 route**：若存在完整匹配 location 且 `MethodSet` 包含该方法的 route，
   返回该 route 的 target，`fallback = None`；
2. 否则，计算**请求实际进入的最深层级** `L`：层级前缀是 location 的完整段前缀
   （空前缀的根级恒进入）；`L` 是这些层级中前缀最长的一个；
3. 若存在「路径精确匹配但方法不支持」的 route，记录
   `FallbackInfo::MethodNotAllowed { allowed, blocked_len }`（`allowed` 取该 route 的
   方法集合，`blocked_len` 为 location 长度）；
4. 返回 `L` 的相对根 handler：`matched_len = len(L.prefix)`，
   `remaining = location[len(L.prefix)..]`，携带第 3 步的 `FallbackInfo`（若有）；
5. **绝不跳过 `L` 去调用祖先层级（或绝对根）的根 handler**；祖先层级的 route 也不会
   被拿来兜底（route 只做精确匹配）；
6. 已存在的精确 route **优先于任何层级根**；因此挂载新层级不会改变既有 route 的命中
   结果（I6）。绝对根只在「请求没有进入任何更深层级」时才会被调用。

> 这里的「最深进入层级」是修正后的关键：例如 `/api/v1` 是 interface 层级、
> `/api/v1/workspace` 是 service 层级，请求 `/api/v1/workspace/unknown` 必须由 service
> 层级的相对根 handler 处理，而不是由 `/api/v1` 的相对根或绝对根处理。

#### 2.3.4 匹配结果示例

假设表中有：根级（绝对根 `RootAll`）、层级 `api/v1`（相对根 `InterfaceRoot`）、
层级 `api/v1/workspace`（相对根 `ServiceRoot`）；以及 route
`api/v1/workspace/reports/{id}`（`View | Pull`）。

| 请求 | 结果 | `matched_len` / 剩余 | `fallback` |
| --- | --- | --- | --- |
| `View /api/v1/workspace/reports/42` | route target | `len(location)` / `""` | `None` |
| `View /api/v1/workspace/reports/42/tail` | `ServiceRoot`（service 层级） | `len("api/v1/workspace")` / `"reports/42/tail"` | `None` |
| `Post /api/v1/workspace/reports/42` | `ServiceRoot`（service 层级） | 同上 | `MethodNotAllowed { allowed: {View,Pull}, blocked_len: len(location) }` |
| `Call /api/v1/workspace` | `ServiceRoot`（service 层级） | `len("api/v1/workspace")` / `""` | `None` |
| `View /api/v1/workspace` | `ServiceRoot`（service 层级） | 同上 | `None`（由 ServiceRoot 自己判断 405） |
| `Call /api/v1/unknown` | `InterfaceRoot`（interface 层级） | `len("api/v1")` / `"unknown"` | `None` |
| `View /other` | `RootAll`（绝对根） | `0` / `"other"` | `None` |

> 注意表中「`View /api/v1/workspace` 命中 ServiceRoot」：service 本身以**层级**方式
> 挂载，ServiceRoot 是它的相对根 handler，因此 Call 由它分发，其它方法也由它统一决定
> 405 / 404。这正是「下级 router 的根 handler 兜底」的含义。

#### 2.3.5 冲突与覆盖

- route 冲突：同一路径模式 + 方法集合有交集 → `RouteError::Conflict`，绝不覆盖；
- 层级冲突：同一前缀已存在层级 → `RouteError::LevelExists`；层级前缀不得与既有层级
  前缀相同；
- 层级挂载 **不是**「覆盖」：route 精确匹配优先，所以新层级不会改变既有 route 的命中；
- 路径统一按规范化后的形式比较，`/api/v1` 与 `api/v1/` 视为同一路径；
- 没有 replace / seal API：启动前与启动后的规则在同一张表里，由「无 replace + 冲突
  报错 + 只能向下」三条共同保证不覆盖。

### 2.4 嵌套与「只能追加」不变量

层级与作用域是这套设计里唯一的结构性约束手段：

```text
根级 level(prefix = "")                 ← 绝对根 handler（构造时安装）
  ├─ route("feeds")                     ← 精确 route
  ├─ scope("api/v1", InterfaceRoot)     ← 子层级；相对根 handler 必填
  │     ├─ route("health")              ← 精确 route
  │     └─ scope("workspace", ServiceRoot)   ← 服务层级；相对根 handler 必填
  │           ├─ route("reports/{id}")  ← 资源 route（service 之下）
  │           └─ scope("feeds", FeedsRoot)   ← 更深层级（可选）
  └─ scope("other", OtherRoot)
```

规则：

1. `RouterCtx::scope(rel, relative_root)` 挂载一个子层级：`rel` 必须是相对路径
   （非空、不含首尾 `/`、不含空段、不含 `.` / `..`），并**必须**给出该层级的相对根
   handler；
2. `RouterCtx::route(rel)` 注册一条精确 route：`rel` 同样是相对路径；route 的目标
   `MethodSet` 由绑定声明；
3. 层级与 route 都只能发生在当前层级前缀之下，因此都严格更长；
4. 服务实现者拿到的 `RouterCtx` 前缀就是它被挂载的位置，因此只能在挂载点之下新增
   层级或 route；
5. 层级根 handler 是**兜底**而不是 route：它不参与精确匹配，只在「请求进入该层级但
   没有 route 命中（或方法不支持）」时被调用；
6. 因为精确 route 优先，挂载新层级不会遮挡既有 route；反过来，既有层级也不会遮挡
   启动前已注册的精确 route。

#### 2.4.1 两类根 handler

| 类型 | 位置 | 何时调用 | 必须性 |
| --- | --- | --- | --- |
| **绝对根 handler** | 根级（空前缀） | 请求没有进入任何更深层级时 | router 构造必填（`RadixRouter::new`） |
| **相对根 handler** | 每个挂载的子层级 | 请求进入了该层级、但没有 route 命中（或方法不支持），且该层级是**最深进入层级** | 挂载该层级时必填（`scope(rel, root)`） |

推论（按修正后的模型）：

1. 请求每进入一层，就多了一个「该层无法匹配具体 handler」时的兜底候选；
2. 兜底总是由**最深进入层级**的相对根负责，而不是逐级上抛，也不是直接丢给绝对根；
3. 因此根 handler 是分层的：每层可以有自己的 404 / 405 / redirect 语义；绝对根只处理
   「连一层都没进入（或请求恰好在根级）」的情况；
4. 服务开发者只持有自己层级的 `RouterCtx`，所以它既看不到、也改不了祖先层级的相对根
   与绝对根——这是「不能覆盖启动前规则」的结构性保证。

> 如果某个子层级确实希望把未命中请求「转发」给上一层，它应当在自己的相对根 handler
> 里显式实现转发（例如重定向或内部调用），而不能依赖框架自动跳过自己。

## 3. 契约设计

> 本节代码是**设计示意**：用于固定类型名、方法形状与生命周期关系，不保证可直接编译。
> 真正的实现需要遵守 `AGENTS.md` 的文档、错误类型与取消约定。

### 3.1 `TrRouter<C>`：可注入的路由表

```rust
/// 统一路由表：匹配 + 层级 / route 的运行期登记与撤销。
///
/// 实现者只回答「怎么存、怎么匹配、怎么增删」，不负责写回复、收尾、状态码。
pub trait TrRouter<C: TrConfig>: Send + Sync {
    /// 按访问方法与完整 location 匹配。
    ///
    /// 返回值里可能是一个精确 route 的 target，也可能是「最深进入层级」的相对根
    /// handler；两种都由 [`RouteMatch`] 区分。返回的目标必须**拥有所有权**，实现不得
    /// 要求调用方在返回后继续持有路由表的读锁。
    fn match_route(&self, method: AccessMethod, location: &str) -> RouteOutcome<C>;

    /// 挂载一个子层级：`path` 是规范化后的绝对前缀（不含首尾 `/`）。
    ///
    /// - 同一前缀已存在层级时返回 [`RouteError::LevelExists`]；
    /// - 根路径 `""` 由构造函数安装，本方法必须拒绝（`RouteError::RootImmutable`）。
    fn insert_level(
        &self,
        path: &str,
        relative_root: RouteTarget<C>,
    ) -> Result<(), RouteError>;

    /// 在某个已存在层级下登记一条精确 route。
    ///
    /// - 与既有 route「同路径模式 + 方法有交集」时必须返回 [`RouteError::Conflict`]；
    /// - route 的路径必须严格长于所属层级前缀。
    fn insert_route(
        &self,
        path: &str,
        methods: MethodSet,
        target: RouteTarget<C>,
    ) -> Result<RouteId, RouteError>;

    /// 撤销一条 route；新请求立即看不到它，in-flight 请求继续持有 target 的 `Arc`。
    fn remove_route(&self, id: RouteId) -> Result<(), RouteError>;
}
```

设计要点：

- **`&self` 而不是 `&mut self`**：层级与 route 可被 `Arc` 共享并在运行期增删；同步由
  实现负责（默认实现内部用 `RwLock`）。
- **固定错误类型 `RouteError`**：让 `dyn TrRouter<C>` 可用，错误汇报统一。
- **对象安全**：没有泛型方法、没有关联类型，`Arc<dyn TrRouter<C>>` 可用。
- **`Arc<R>` 可直接接入**：提供
  `impl<C, R: TrRouter<C> + ?Sized> TrRouter<C> for Arc<R>` 的转发实现。

### 3.2 `TrRouteTarget<C>`：对象安全的目标句柄

```rust
/// 一个可以被路由到的目标。对象安全：服务器只需要 `dyn` 形式。
pub trait TrRouteTarget<C: TrConfig>: Send + Sync {
    /// 处理一次已经完成路由的请求。
    ///
    /// target 拥有两个 channel 半边，**负责写回复与收尾**（与旧 `TrReqHandler` 的
    /// 契约相同：写回复 → 半关闭 tx → 读完 rx → 释放 rx）。
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, C>) -> RouteTargetFuture<'f>;
}

/// 类型擦除后的 target 句柄。
pub type RouteTarget<C> = Arc<dyn TrRouteTarget<C>>;

/// target 的 future：必须装箱，才能与具体类型无关。
pub type RouteTargetFuture<'f> =
    Pin<Box<dyn Future<Output = Result<(), RouteTargetError>> + Send + 'f>>;
```

擦除层要求 `C: 'static`；`RouteTargetFuture` 要求 `Send`，因此非 `Send` 的旧 handler
不能直接接入（适配器约束见下文）。

`RouteRequest`（拥有本次请求的全部输入与 channel 半边）：

```rust
/// 一次已经完成路由的请求。

    params_: RouteParams,

    headers_: &'f mut Headers,

    /// 本次请求的取消令牌；见 3.2.1。**不得假定它永不取消**。

    tx_: ChannelTx<C>,
    rx_: ChannelRx<C>,
}

    pub fn location(&self) -> &'f str;

    pub fn matched_prefix(&self) -> &'f str;

    /// 标准收尾：先半关闭 tx，再读到对端关闭；内部使用本次请求的取消令牌。
    pub fn close_async(self) -> impl TrMayCancel<'f, MayCancelOutput = usize> + 'f
    where
        Self: 'f;

    /// 建议新增：写一条状态回复（status + UTF-8 message）；内部使用请求取消令牌。
    pub fn reply_status_async<'a>(
        &'a mut self,
        status: Status,
        message: &str,
    ) -> impl TrMayCancel<'a, MayCancelOutput = Result<(), RouteTargetError>> + 'a;
}

impl<'f, C: TrConfig> RouteRequest<'f, C> {

        matched: RouteMatch<C>,

    pub params: RouteParams,
    pub fallback: Option<FallbackInfo>,
    pub headers: &'f mut Headers,
    /// 请求级取消令牌；target 自己写回复 / 收尾时必须使用它。

    pub tx: ChannelTx<C>,
```

#### 3.2.1 `RequestCancel`：请求级取消令牌

```rust
/// 一次请求的取消令牌，由分发层在路由时产生。
///
/// **它不是 `NonCancellableToken`**：当前「按规则定时取消」的机制尚未实现，但契约上
/// 它可能因超时、服务关闭、资源 drain 等原因被取消。target 必须：
///
/// 1. 把 `req.cancel().child_token()` 传给所有可取消的异步调用
///    （`write_response_prefix_async`、`read_body_async`、长流读写……）；
/// 2. 在取消路径上完成必要的收尾，而不是假定自己一定会正常跑完；
/// 3. 不得在实现里写「令牌一定不会取消」这类假设。
#[derive(Clone)]
pub struct RequestCancel { /* 对象安全的擦除句柄 */ }

impl TrCancellationToken for RequestCancel {
    type Cancellation = RequestCancelFuture; // Pin<Box<dyn Future<Output = ()> + Send>>
    type ChildToken = RequestCancel;
    fn is_cancelled(&self) -> bool;
    fn can_be_cancelled(&self) -> bool;
    fn child_token(&self) -> Self;
    fn cancellation(self) -> Self::Cancellation;
}
```

产生位置：分发层（当前 `MptpServer`，未来可由 router 的超时策略接管）为每个被分发的
请求产生 `RequestCancel`。v1 可能只是从 serve 令牌派生一个 child（甚至暂时不可取消），
但**类型与契约按可取消设计**；具体产生机制与类型擦除见 11.2。

#### 与旧 `TrReqHandler` 的适配

```rust
/// 把 `TrReqHandler` 适配成 `TrRouteTarget`。
pub struct ReqHandlerTarget<H> { handler_: H }

impl<H> ReqHandlerTarget<H> {
    pub fn new(handler: H) -> Self;
}

impl<C, H> TrRouteTarget<C> for ReqHandlerTarget<H>
where
    C: TrConfig + 'static,
    H: TrReqHandler<C> + Send + Sync + 'static,
    H::Err: 'static,
    // `TrReqHandler::HandleAsync` 只有 `TrMayCancel` 约束，没有 `Send`；
    // 装进 `RouteTargetFuture` 必须显式要求 future 是 Send。
    for<'f> H::HandleAsync<'f>: Send + 'f,
{
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, C>) -> RouteTargetFuture<'f> {
        Box::pin(async move {
            let cancel = req.cancel().child_token();
            let parts = req.into_parts();
            self.handler_
                .handle_async(parts.method, parts.location, parts.headers, parts.tx, parts.rx)
                .may_cancel_with(cancel)
                .await
                .map_err(RouteTargetError::from_handler)
        })
    }
}
```

旧 handler 拿到的是「被 `RequestCancel` 包裹之后的可取消 future」；即使 handler 内部
没有显式处理令牌，取消也会在 await 边界生效。

### 3.4 `MethodSet` 与七种访问方法

`AccessMethod` 的线上取值是位标志，但 `Head` 是 `0`，不能直接当掩码用。`MethodSet` 是
独立的小类型：

```rust
/// 一组访问方法。内部用 7 bit 表示七种方法，`Head` 有自己的显式位。
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub struct MethodSet(/* u8 bitmask */);

impl MethodSet {
    pub const NONE: MethodSet;
    pub const ALL: MethodSet;
    pub const HEAD: MethodSet;
    pub const VIEW: MethodSet;
    pub const POST: MethodSet;
    pub const DROP: MethodSet;
    pub const PUSH: MethodSet;
    pub const PULL: MethodSet;
    pub const CALL: MethodSet;

    pub const fn just(method: AccessMethod) -> MethodSet;
    pub const fn contains(self, method: AccessMethod) -> bool;
    pub const fn intersects(self, other: MethodSet) -> bool;
    pub const fn union(self, other: MethodSet) -> MethodSet;
}

impl core::ops::BitOr for MethodSet { /* ... */ }
```

绑定语义：

- `intersects` 用于冲突检测：同一路径模式两次 route 绑定只要有交集就报 `Conflict`；
- 匹配时用 `contains(method)` 判断该 route 能否服务本次方法；
- 协议规定 `Head` 对任意资源总是可用，但**框架不自动合成 HEAD route**：资源暴露时
  应当显式绑定一个 `Head` target（通常与 `View` 共用数据、但不写 body），或用一个同时
  覆盖 `View | Head` 的 target 按 `method` 分支。路由层只按 `MethodSet` 如实匹配。

### 3.5 `RouterCtx` / `RouteBuilder` / `RouteHandle`

```rust
/// 一个层级的作用域入口。
///
/// 轻量、可克隆、可跨任务持有；服务实现者可把它存进自己的字段，在运行期继续绑定资源。
/// 手写 `Clone`（而不是 `#[derive(Clone)]`），避免给配置类型 `C` 加 `C: Clone` 约束。
pub struct RouterCtx<C: TrConfig> {
    router_: Arc<dyn TrRouter<C>>,
    /// 本层级的绝对前缀；根级为空串。不含首尾 `/`。
    prefix_: Arc<str>,
}

impl<C: TrConfig> RouterCtx<C> {
    /// 根级作用域；应用侧持有它，用来装配整个树。
    pub fn root(router: Arc<dyn TrRouter<C>>) -> Self;

    /// 本层级的前缀（I4）。
    pub fn prefix(&self) -> &str;

    /// 挂载一个子层级，并给出该层级的**相对根 handler**（必填）。
    pub fn scope(
        &self,
        rel: &str,
        relative_root: impl TrRouteTarget<C> + 'static,
    ) -> Result<RouterCtx<C>, RouteError>;

    /// 用框架默认根 handler 作为相对根，挂载一个子层级。
    pub fn scope_default(&self, rel: &str) -> Result<RouterCtx<C>, RouteError>;

    /// 在当前层级之下登记一条精确 route；`rel` 不合法时立即返回错误。
    pub fn route(&self, rel: &str) -> Result<RouteBuilder<'_, C>, RouteError>;
}

/// 一条待登记的精确 route。
pub struct RouteBuilder<'a, C: TrConfig> {
    ctx_: &'a RouterCtx<C>,
    abs_path_: Arc<str>,
}

impl<'a, C: TrConfig> RouteBuilder<'a, C> {
    /// 绑定一组访问方法到同一个 target。
    pub fn on(
        self,
        methods: MethodSet,
        target: impl TrRouteTarget<C> + 'static,
    ) -> Result<RouteHandle<C>, RouteError>;

    /// 方法糖：每个方法一个 target。与 salvo 的 `.get(...)` 等价的七种形式。
    pub fn head(self, target: impl TrRouteTarget<C> + 'static) -> Result<RouteHandle<C>, RouteError>;
    pub fn view(self, target: impl TrRouteTarget<C> + 'static) -> Result<RouteHandle<C>, RouteError>;
    pub fn post(self, target: impl TrRouteTarget<C> + 'static) -> Result<RouteHandle<C>, RouteError>;
    pub fn drop(self, target: impl TrRouteTarget<C> + 'static) -> Result<RouteHandle<C>, RouteError>;
    pub fn push(self, target: impl TrRouteTarget<C> + 'static) -> Result<RouteHandle<C>, RouteError>;
    pub fn pull(self, target: impl TrRouteTarget<C> + 'static) -> Result<RouteHandle<C>, RouteError>;
    pub fn call(self, target: impl TrRouteTarget<C> + 'static) -> Result<RouteHandle<C>, RouteError>;
}

/// 一条已登记 route 的撤销句柄。
pub struct RouteHandle<C: TrConfig> {
    router_: Arc<dyn TrRouter<C>>,
    id_: RouteId,
}

impl<C: TrConfig> RouteHandle<C> {
    pub fn id(&self) -> RouteId;
    /// 撤销该 route；新请求立即不可见，in-flight 请求不受影响。
    pub fn remove(self) -> Result<(), RouteError>;
}
```

要点：

- `RouterCtx` 只存 `Arc<dyn TrRouter<C>>` 与 `Arc<str>`；除配置类型 `C` 外没有其他类型
  参数，可以直接出现在 service 实现的字段或 `RpcServiceCtx` 里；
- `scope` 与 `route` 分别对应「挂载层级」与「登记精确 route」，两者都要求相对路径且
  严格更长；
- 层级根 handler 不占用 route 命名空间：`scope("x", root)` 之后仍然可以在 `x` 之下
  登记精确 route；
- `RouteHandle` 不实现 Drop 自动撤销；是否提供 RAII `RouteGuard` 见 11.6；
- 层级本身的卸载 API 暂未提供（见 11.17）。

### 3.6 默认实现 `RadixRouter<C>`（matchit 参考）

#### 3.6.1 与 matchit 的关系

matchit 与本文的 route 语义基本一致：整条路径精确匹配、静态 > 参数 > catch-all、
冲突检测、参数解析。差别在于：

| 维度 | matchit 0.9.x | 本设计 |
| --- | --- | --- |
| 匹配范围 | 整条路径精确匹配 | route 精确匹配；额外有「层级相对根兜底」（matchit 没有） |
| 方法 | 完全不认识 method | `MethodSet` 是 route 绑定的一部分 |
| 层级 / 根 | 无 | 显式层级 + 每层相对根 + 绝对根 |
| 运行期变更 | `insert/remove/merge` 都要 `&mut self`，无内部锁 | `&self` + 内部同步，任意时刻可增删 |
| target 所有权 | `Match.value` 是 `&T` / `&mut T`，借用 router | `Arc<dyn TrRouteTarget>`，可脱离锁跨 `await` |
| 参数所有权 | 零拷贝（key 借路由、value 借 path） | 先拥有所有权，优化见 11.16 |
| 内省 | 无路由枚举 | 至少返回 `RouteId`；层级列表待定 |
| 其他 | 参数列表无固定上限（超过 3 个走堆分配） | 同样无固定上限；自己校验，不 `panic` |

仓库当前 `matchit` 不在 `Cargo.lock` 与本地缓存中，`vendor/` 为空；而仓库内已有可复用
的段式 trie（`rpc_router_trie/src/trie_.rs`、`rpc_demo/src/trie_.rs`）。因此本设计的
结论是：

> **不把 matchit 作为依赖，而是把它的精确匹配、路径语法、优先级与冲突错误形状作为
> 蓝本，在 `mptp_smux`（或后续独立 crate）内实现 `RadixRouter`。** 用户可以注入自己的
> `TrRouter` 实现，而不是被默认实现绑死。

#### 3.6.2 数据结构草案

```text
RadixRouter<C>
  └─ RwLock<Table<C>>
       Table { root: Level<C> }
         Level {
           /// 本层级的绝对前缀。
           prefix: Box<str>,
           /// 本层级的相对根 handler；根级即绝对根 handler。
           relative_root: RouteTarget<C>,
           /// 本层级直接登记的精确 route。
           routes: RouteTrie<C>,
           /// 直接子层级（按前缀段索引）。
           children: BTreeMap<Box<str>, Level<C>>,
         }
       RouteNode<C> {
         /// 精确 route 的方法槽位；每槽一个 target。
         bindings: [Option<Binding<C>>; 7],
         /// 参数子节点（同层最多一个）与 catch-all 子节点（只能末尾）。
         param_child: Option<Box<RouteNode<C>>>,
         catch_all_child: Option<Box<RouteNode<C>>>,
         static_children: BTreeMap<Box<str>, RouteNode<C>>,
         param_name: Option<Arc<str>>,
       }
```

- 层级与 route 分开存：层级根不参与精确匹配，只作为兜底；
- `match_route` 先做精确 route 匹配（静态 > 参数 > catch-all，失败回溯）；未命中时沿
  层级前缀找「最深进入层级」，取它的 `relative_root`；
- 读锁内完成匹配与 `target.clone()` / 参数拷贝，**锁绝不跨 `await`**；
- `insert_level` / `insert_route` / `remove_route` 持写锁；冲突按 3.3 的错误返回；
- 根级在 `RadixRouter::new(absolute_root)` 时安装，`insert_level("")` 返回
  `RootImmutable`。

### 3.7 两类根 handler 与默认实现

根 handler 就是普通的 `TrRouteTarget`，区别只在挂载位置：

- **绝对根 handler**：根级的相对根，构造 `RadixRouter::new` 时安装；处理「没有进入任何
  更深层级」的请求；
- **相对根 handler**：每个子层级挂载时安装；处理「进入该层级但没有 route 命中（或方法
  不支持）」的请求，且只在它是最深进入层级时被调用。

框架建议提供默认实现：

```rust
/// 默认根 handler：没有方法诊断给 404；route 方法不支持时给 405 + Allow。
pub struct DefaultRootHandler;

impl<C: TrConfig> TrRouteTarget<C> for DefaultRootHandler {
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, C>) -> RouteTargetFuture<'f> {
        Box::pin(async move {
            match req.fallback() {
                Some(FallbackInfo::MethodNotAllowed { allowed, .. }) => {
                    // 405 + Allow（编码方式见 11.3）
                }
                None => {
                    // 404（HEAD 是否带 body 由协议约定）
                }
            }
            req.close_async().await;    // 内部使用请求取消令牌
            Ok(())
        })
    }
}
```

应用可以给不同层级安装不同语义的根 handler：例如 interface 层级返回结构化 404、
service 层级对非 `Call` 返回 405、绝对根对旧路径返回 301/302/303 + `Location`。

### 3.8 `MptpServer` 的接缝

```rust
pub struct MptpServer<C, R>
where
    C: TrConfig,
    R: TrRouter<C>,
{
    router_: R,
    _use_c_: PhantomData<fn() -> C>,
}

impl<C, R> MptpServer<C, R>
where
    C: TrConfig,
    R: TrRouter<C>,
{
    pub fn new(router: R) -> Self;
    pub fn router(&self) -> &R;

    pub fn serve_channel_async<'f>(&'f self, tx: ChannelTx<C>, rx: ChannelRx<C>) -> ...
    where C: 'f, R: 'f;

    pub fn serve_listener_async<'f>(&'f self, binding: &'f mut DockBinding<C>, reserve: usize) -> ...
    where C: 'f, R: 'f, ChannelHandle<C>: TrChannelHalf<MuxCfg<C>>;
}
```

`serve_channel_async_` 的核心变化：

```text
解码前缀
  → 产生 RequestCancel（v1：从 serve 令牌派生；未来由 router 超时策略接管）
  → router.match_route(method, location)
      → Found(m)   → target.handle_route(RouteRequest::from_match(m, ...))
      → Unmatched  → 协议级 404 + 记录警告（实现缺根级的兜底）
```

`MptpServer` 对 router 的契约要求（文档性，不做类型强制）：根级必须有绝对根 handler，
每个挂载层级必须有相对根 handler；默认实现 `RadixRouter` 在构造 / `scope` 时强制了
这一点。

### 4.1 应用装配：绝对根 + 子层级相对根 + 动态资源

```rust

// 绝对根 handler：只处理「没有进入任何更深层级」的请求。
struct AppRoot;

impl TrRouteTarget<SrvCfg> for AppRoot {
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, SrvCfg>) -> RouteTargetFuture<'f> {
        Box::pin(async move {
            let mut parts = req.into_parts();
            let cancel = parts.cancel.child_token();
            let mut resp_headers = Headers::new();
            let status = match parts.fallback {
                Some(FallbackInfo::MethodNotAllowed { .. }) => Status::MethodNotAllowed,
                None if parts.location.starts_with("old/") => {
                    resp_headers.set_text(StdHeaderKey::Location, "/api/v1");
                    Status::MovedPermanently
                }
                None => Status::NotFound,
            };
            let prefix = ResponsePrefix::with_headers(status, Some(resp_headers));
            write_response_prefix_async(&prefix, &mut parts.tx)
                .may_cancel_with(cancel.child_token())
                .await?;
            // 收尾同样使用请求取消令牌，不假定它不会取消。
            close_channel_async(parts.tx, &mut parts.rx).await;
            Ok(())
        })
    }
}

// interface 层级的相对根：处理 /api/v1 之下没有命中 route 的请求。

        Box::pin(async move {
            // 这里可以返回结构化 404，或根据 matched_prefix / remaining 做重定向。
            let _ = req.matched_prefix();
            let _ = req.remaining();
            // 省略写回复细节；实际实现同样应使用 req.cancel()。
            req.close_async().await?;
            Ok(())
        })
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // 绝对根 handler 在构造时安装，不可覆盖。
    let router = Arc::new(RadixRouter::<SrvCfg>::new(AppRoot));
    // 根级作用域：应用侧长期持有，供装配期与运行期使用。
    let app = RouterCtx::root(router.clone());

    // 1) 挂载 interface 层级；相对根 handler 必填。
    let api_v1 = app.scope("api/v1", InterfaceRoot)?;

    // 2) 普通精确 route（旧 TrReqHandler 经 ReqHandlerTarget 适配）。
    app.route("echo")?.on(MethodSet::ALL, ReqHandlerTarget::new(EchoHandler))?;

    // 3) 运行期动态资源：精确 route + 方法糖；资源只是「handle + 绑定」。
    let feed = Arc::new(TelemetryFeed::new());
    let feeds = api_v1.scope("feeds", DefaultRootHandler)?;
    let view_guard = feeds
        .route("telemetry/{id}")?
        .view(TelemetryViewTarget::new(feed.clone()))?;
    let pull_guard = feeds
        .route("telemetry/{id}")?
        .pull(TelemetryPullTarget::new(feed.clone()))?;
    let head_guard = feeds
        .route("telemetry/{id}")?
        .head(TelemetryHeadTarget::new(feed.clone()))?;

    let mut binding = /* ... 绑定 dock ... */;
    let server = MptpServer::<SrvCfg, _>::new(router.clone());
    let serve = server
        .serve_listener_async(&mut binding, 8)
        .may_cancel_with(/* 示例：真实取消源由应用提供 */ NonCancellableToken::new());

    // 运行期下线资源：撤销 route；in-flight 请求继续持有 target 的 Arc。

    pull_guard.remove()?;
    head_guard.remove()?;
```

### 4.2 service 开发者：存下本层级作用域，运行期追加资源

`add_service` 会把 service 挂载成一个**独立层级**，其相对根 handler 是 service 的
调度器；构造闭包收到的 `RpcServiceCtx` 里的 `RouterCtx` 前缀已经是
`<interface>/<service>`。服务实现可以把它存起来，在运行期继续登记更长路径：

```rust
pub struct WorkspaceServiceImpl {
    store_: Arc<Store>,
    /// 本 service 的层级作用域，前缀 = api/v1/workspace。
    routes_: RouterCtx<SrvCfg>,
}

impl WorkspaceServiceImpl {
    pub fn new(cx: &RpcServiceCtx<SrvCfg>, store: Arc<Store>) -> Self {
        WorkspaceServiceImpl {
            store_: store,
            routes_: cx.routes().clone(),
        }
    }

    /// 运行期挂一个报表资源到本 service 之下。
    ///
    /// 资源 = `report` handle + 若干精确 route；不需要实现任何资源 trait。
    pub fn expose_report(
        &self,
        id: ReportId,
        report: Arc<Report>,
    ) -> Result<Vec<RouteHandle<SrvCfg>>, RouteError> {
        let mut handles = Vec::new();
        handles.push(
            self.routes_
                .route(&format!("reports/{id}"))?
                .view(ReportViewTarget::new(report.clone()))?,
        );
        handles.push(
            self.routes_
                .route(&format!("reports/{id}"))?
                .pull(ReportPullTarget::new(report))?,
        );
        Ok(handles)
    }
}
```

服务实现者**拿不到**比 `api/v1/workspace` 更短的作用域，因此无法注册到 service 之外，
也无法覆盖 interface / 绝对根规则；这是 I3 的直接体现。

### 4.3 运行期添加 / 删除资源

```rust
// 应用在任意时刻、任意任务里都可以绑定（RouterCtx 是 Clone + Send + Sync 的句柄）。
let feeds = app.scope("feeds", DefaultRootHandler)?;   // 层级挂载
let guard = feeds
    .route(&format!("telemetry/{feed_name}"))?        // 精确 route
    .on(MethodSet::VIEW | MethodSet::PULL, TelemetryTarget::new(feed_handle.clone()))?;

// 资源下线：撤销 route。
guard.remove()?;
// 之后的新请求不再命中它；正在读流的连接持有 Arc<Target>，会自然读到结束或断开。
```

删除语义要点：

- `remove` 只影响**新的匹配**，不等待、不打断 in-flight 请求；
- 资源的业务删除（`DROP`）与路由撤销（`remove`）是两件事：前者是业务操作，后者是
  路由可见性；框架不强制绑定；
- 资源没有框架级生命周期：应用持有 handle（如 `Arc<Report>`）与 `RouteHandle`，两者
  一起决定资源是否存在；需要「撤销时优雅结束长流」时由资源的 target 自己处理。

## 5. 现状与差距（2026-11-07）

### 5.1 现状事实

**`mptp_smux::serving`**

- `TrPathHandler`（`const PATH`）、`TrPathRouter`（单一 `Handler` + `match_path(&self, &str)
  -> Option<&Handler>`）、`TrPathRouterMut`（**全仓无实现、无调用**）；
- 内置 `Router<C, R: TrRouteValues>` 用 `tlist` 类型级列表做「最长前缀 → handler」，
  装配期消费式构建；`Router::match_path` 恒等返回 `Some(self)`，真正的匹配发生在
  `handle_async` 内部；
- `RouterCtx<C>` / `RpcServiceCtx` 都是 ZST 占位：`Router::route` 自己 `new()` 一个
  `RouterCtx`，`RpcRouter::new` 接收后丢弃（`_ctx`），`add_service` 自己 `new()` 一个
  `RpcServiceCtx`——**从 ctx 到 service 构造闭包的链路是断的**；
- `MptpServer<C, R>` 的约束是 `R: TrPathRouter` 且 `R::Handler: TrReqHandler<C>`；
  `serve_*` 只拿 `&self`；未命中返回 `ServeError::NotFound`，**channel 被丢弃、不写 404**；
- `serve_listener_async_` 内联 `await` 每条 channel 的 handler，串行 accept；错误直接
  `?` 上抛终止监听循环；取消令牌实际未启用（两个 demo 都传 `NonCancellableToken`）。

**`rpc_core_v1::serving`**

- 内联链：`RpcRouter<I, S>` 用 `tlist` 在 interface 前缀下按 `SERVICE_PATH` 做最长前缀，
  只接受 `Call`（否则 405），未命中写 404；`add_service` 消费式构建；
- 队列链：`TrRpcRouter` / `RpcRouterHandler` / `RpcJob` / `ServiceRoute` /
  `TrRpcServiceRoute`，`rpc_router_trie` 提供独立 trie 实现；**当前无运行期使用者**；
- 两处各有一份 `path_prefix_len_`（`mptp_smux` 与 `rpc_core_v1`），语义相同、代码重复。

**调用点**

- 本仓内运行期只有两个 demo 使用 router，且各自带一份本地 `Router<T>`：
  `mptp_smux_v1_demo`（路径 → `DemoHandler`）与 `rpc_demo`（空前缀 → 手写 queue 版
  `RpcRouter`）；
- 仓库内的 `Router::call` / `add_service` 仅见于单测、doctest 与编译期断言；
- 仓库外的 `mptp_cs_smoke`（同级目录、独立 workspace，path 依赖本仓的 `mptp_smux` /
  `rpc_core_v1`）仍使用 `Router::call + RpcRouter::add_service` 装配，11 条 RPC 的 e2e
  是迁移时的回归基准。

### 5.2 能力矩阵（今天 → 目标）

| # | 能力 | 今天 | 目标 |
| --- | --- | --- | --- |
| 1 | 可注入 router 实现 | ⚠️ 有缝，但受单一 `Handler` / 借用返回 / 无方法参数限制，且内置实现恒等返回自身 | ✅ `TrRouter` + `Arc<dyn>` |
| 2 | 运行期增删层级 / route | ❌ | ✅ `insert_level` / `insert_route` / `remove_route` + `RouterCtx` |
| 3 | 每层知道自己的前缀 | ❌（`RouterCtx` 是 ZST） | ✅ `RouterCtx::prefix()` / `matched_prefix` / `remaining` |
| 4 | 只能向下追加、不能覆盖 | ❌ | ✅ 层级/route 只能向下 + 冲突检测 + 无 replace + 精确 route 优先 |
| 5 | 方法参与路由 | ❌（顶层只透传） | ✅ `MethodSet` 参与匹配 |
| 6 | 七种方法可用 | ⚠️（单 handler 可自己处理任意 method，但缺框架级方法匹配与回复 helper） | ✅ 方法糖 + 按方法绑定 target；资源不抽 trait |
| 7 | 统一 404 / 405 / redirect | ⚠️ RPC 层自己写；MPTP 层直接丢 channel | ✅ 每层相对根 + 绝对根；兜底只到最深进入层级 |
| 8 | 两类根 handler 必存且不可覆盖 | ❌ | ✅ `RadixRouter::new(absolute_root)` + `scope(rel, relative_root)` |
| 9 | 路径参数 | ❌ | ✅ `{name}` / `{*rest}`（matchit 语法） |
| 10 | 冲突检测 | ❌（重复前缀静默并存） | ✅ `RouteError::Conflict` |
| 11 | 请求取消与定时策略 | ❌（令牌实际未启用） | ⚠️ `RequestCancel` 契约先定；超时规则与并发接入见 7.2 / 11.2，仍是 P3 |
| 12 | 静态零装箱 | ✅ | ❌ 放弃：统一表必须类型擦除 |

### 5.3 主要取舍

1. **静态零装箱 → 每请求一次 `Arc` + boxed future**：统一到运行期表后这是必然代价。
   单个请求路径上只有一次 `Arc` clone 与一次装箱，通常可接受；若将来有实测热点，再评估
   `Small`-future 或静态 fast-path，但不作为本轮设计目标。
2. **`tlist` 路由机器删除**：`RouteValues` / `TrRouteValues` / `TrPathRouterList` 这些
   `#[doc(hidden)]` 但公开导出的类型会随旧 `Router` 一起删除。
3. **`TrReqHandler` 保留**：它是「单 handler 行为契约」，与 router 解耦；新设计通过
   `ReqHandlerTarget` 继续使用它，避免所有 handler 重写。
4. **RPC 队列链**：`rpc_router_trie` 独立 crate 与其他队列类型当前无运行期使用者；
   统一 router 落地后，队列 / 背压应表达为 **target 内部实现**（一个 target 自己持有
   有界队列与 sender），而不是第二个 router。去留见 11.8。
5. **route 语义从「前缀 + 剩余路径」改为「精确匹配」**：旧 MPTP router 的 handler 可以
   吃掉任意后缀；新设计里需要整棵子树时改用「层级 + 相对根 handler」，这既表达力更强，
   也让 404/405 有明确的层级归属。
6. **资源不再是框架 trait**：资源 = handle + 一组 route 绑定；方法集合、生命周期、长流
   都由应用自己的 target 决定，框架只提供 `RouteHandle`。

## 6. RPC 层收敛方案

### 6.1 层级映射

统一 router 落地后，RPC 的两级命名空间直接映射为两个**层级**：

| RPC 概念 | 在统一 router 中 |
| --- | --- |
| interface（`I::PATH`） | 一个层级 `I::PATH`，相对根 handler 由 `rpc_interface` 安装 |
| service（`SERVICE_PATH`） | `I::PATH/SERVICE_PATH` 下的一个层级，相对根 handler 是 `ServiceRoot` |
| service 之下的资源 | service 层级之下的精确 route（或更深层级，如需要） |
| `Call` 方法 | `ServiceRoot` 内部按 `AccessMethod::Call` 分发（不再单独注册 route） |
| 非 `Call` / 未知子路径 | 由 service 层级的相对根 `ServiceRoot` 决定 405 / 404 |

好处：interface / service 的 404 / 405 语义天然落在各自层级的相对根 handler 上，不再
需要第二个 router，也不会把下层未命中「上抛」到绝对根。

### 6.2 新增 API（`rpc_core_v1::serving`）

```rust
/// 在任意 `RouterCtx` 上挂载一个 RPC interface 层级。
pub trait TrRouterCtxRpcExt<C: TrServingConfig> {
    /// 使用默认的相对根 handler（`DefaultRootHandler`）挂载 `I::PATH` 层级。
    fn rpc_interface<I: TrRpcInterface>(
        &self,
        build: impl FnOnce(&RpcInterfaceCtx<I, C>) -> Result<(), RouteError>,
    ) -> Result<(), RouteError>;

    /// 使用自定义的相对根 handler 挂载 `I::PATH` 层级。
    fn rpc_interface_with_root<I: TrRpcInterface>(
        &self,
        interface_root: impl TrRouteTarget<C> + 'static,
        build: impl FnOnce(&RpcInterfaceCtx<I, C>) -> Result<(), RouteError>,
    ) -> Result<(), RouteError>;
}

// 实现（示意）：
// impl<C: TrServingConfig> TrRouterCtxRpcExt<C> for RouterCtx<C> { ... }

/// 一个 interface 层级的作用域，前缀 = `I::PATH`。
pub struct RpcInterfaceCtx<I: TrRpcInterface, C: TrServingConfig> {
    routes_: RouterCtx<C>,
    _interface_: PhantomData<fn() -> I>,
}

impl<I: TrRpcInterface, C: TrServingConfig> RpcInterfaceCtx<I, C> {
    pub fn routes(&self) -> &RouterCtx<C>;

    /// 挂载一个 service 层级：相对根 handler 是 `ServiceRoot`。
    ///
    /// 构造闭包收到的前缀已经是 `<I::PATH>/<SERVICE_PATH>`，服务实现可在运行期继续
    /// 登记精确 route 或挂载更深层级。
    pub fn add_service<S>(
        &self,
        make_service: impl FnOnce(&RpcServiceCtx<C>) -> S,
    ) -> Result<(), RouteError>
    where
        S: TrRpcService<I, C, Err = RpcError> + Send + Sync + 'static;
}

/// 一个 service 层级的作用域，前缀 = `<I::PATH>/<SERVICE_PATH>`。
pub struct RpcServiceCtx<C: TrServingConfig> {
    routes_: RouterCtx<C>,
}

impl<C: TrServingConfig> RpcServiceCtx<C> {
    pub fn routes(&self) -> &RouterCtx<C>;
}
```

### 6.3 `ServiceRoot`：service 层级的相对根 handler

service 不再注册成一条 route，而是挂载成一个层级；该层级的相对根 handler 就是 service
的调度器。它同时承担三件事：

1. `Call`：解码 body enum → `TrRpcService::dispatch_async` → 写回复 → 收尾；
2. 非 `Call`：回 `405 + Allow: Call`（旧 `RpcRouter` 的职责）；
3. 未知子路径上的 `Call`：由 service 自己决定 `404` 还是交给业务错误映射。

非 `Call` 请求的 `Allow` 取值规则：优先使用 `req.fallback()` 里的
`FallbackInfo::MethodNotAllowed { allowed, .. }`（说明路径命中了某个具体资源 route），
没有 fallback 时才回退为 `Allow: Call`（service 层级本身只声明 Call）。

```rust
/// 把 `TrRpcService` 适配成 service 层级的相对根 handler。
struct ServiceRoot<S, I, C> {
    service_: S,
    _interface_: PhantomData<fn() -> I>,
    _config_: PhantomData<fn() -> C>,
}

impl<S, I, C> TrRouteTarget<C> for ServiceRoot<S, I, C>
where
    C: TrServingConfig + 'static,
    I: TrRpcInterface,
    S: TrRpcService<I, C, Err = RpcError> + Send + Sync + 'static,
{
    fn handle_route<'f>(&'f self, req: RouteRequest<'f, C>) -> RouteTargetFuture<'f> {
        Box::pin(async move {
            let cancel = req.cancel().child_token();
            match req.method() {
                AccessMethod::Call => {
                    let parts = req.into_parts();
                    let mut ctx =
                        RpcCallCtx::<C>::new(parts.location, &*parts.headers, parts.tx, parts.rx);
                    let result = self
                        .service_
                        .dispatch_async(&mut ctx)
                        .may_cancel_with(cancel);
                    ctx.close_async().await;
                    result.map_err(|err| RouteTargetError::Internal(err.to_string()))
                }
                _ => {
                    // 405 + Allow；allowed 优先来自 fallback，否则默认 Call。
                    let allowed = match req.fallback() {
                        Some(FallbackInfo::MethodNotAllowed { allowed, .. }) => allowed,
                        None => MethodSet::just(AccessMethod::Call),
                    };
                    let parts = req.into_parts();
                    let _ = (allowed, parts.cancel);  // 真实实现应把它传进写回复
                    todo!("写 405 + Allow 并收尾")
                }
            }
        })
    }
}
```

## 7. 资源、七种方法与并发（router 之外的部分）

router 只做「层级 + 精确 route + 方法集合 → target」。资源不是一个框架类型，而是应用侧
「**handle + 一组 route 绑定**」的运行时组合。

### 7.1 七种访问方法与 target

| 方法 | 典型 target | 成功 | 常见失败 | body / 流 |
| --- | --- | --- | --- | --- |
| `Head` | 元信息 target | `200` | `404` | **不写 body** |
| `View` | 读取 target | `200` | `404` / `406` | 回复体；可选 suffix |
| `Post` | 创建 / 上传 target | `201` + `Location`（新建）或 `200` | `400` / `405` / `Status::new(409)` | 请求体 |
| `Drop` | 删除 target | `204`（`Status::new(204)`）或 `200` | `404` / `Status::new(409)` | 无 |
| `Push` | 客户端推流 target | `200` / `Status::new(202)` | `404` / `405` | 请求 suffix 流 |
| `Pull` | 服务端拉流 target | `200` + 持续写 | `404` / `405` | 回复 suffix 流 |
| `Call` | RPC service 层级 | `200` + 编码结果 | `4xx` / `5xx` | 现有 RPC 链不变 |

约定：

- 每种方法可以有自己的 target（`route(path)?.view(..).pull(..)`），也可以一个 target
  通过 `req.method()` 分支处理多个方法（`on(MethodSet::VIEW | MethodSet::HEAD, ..)`）；
- 协议规定 `Head` 对任意资源总是可用，但框架不自动合成：暴露资源时应显式绑定 `Head`
  target（通常复用 `View` 的数据但不写 body）；
- `Status` 缺少 `204` / `202` / `409` 常量，但 `Status::new(...)` 可用（见第 9 节）；
- 方法语义不进入 router：router 只按 `MethodSet` 选 target，target 决定状态码、
  `Allow`、`Location` 与流。

### 7.2 serving 层还需要什么

1. **请求级取消（`RequestCancel`）**：v1 只建立契约与占位实现；「按规则定时取消」
   （超时、每请求预算等）需要 serving / router 的策略层实现。实现之前，target 也必须
   按可能取消来写。
2. **并发接入**：`serve_listener_async_` 目前内联 `await` handler，`Pull` 长流会饿死
   后续 channel。需要注入 spawner（`TrChannelSpawner`）或让 listener 并发驱动每条
   channel（P3）。
3. **单 channel 错误隔离**：某条 channel 失败不应终止 accept 循环。
4. **优雅关闭**：`ServeHandle`：停止 accept → 向层级 / in-flight 发取消 → 等待超时 →
   强制 reset。
5. **`Allow` 头**：405 的标准表达。见 11.3；在新标准键获批前，用用户自定义字符串键。
6. **观测**：每 route / 每层级计数、活跃流、拒绝原因；放在 target / server 生命周期
   钩子，不引入中间件链。

### 7.3 资源 = handle + route 绑定（不抽 trait）

用户修正后的资源定义：

- **handle**：应用自己的业务对象（通常 `Arc<T>`），框架不认识它的类型；
- **route 绑定**：为该 handle 注册的一组精确 route（路径 + 方法集合 + target），每个
  target 通常持有 handle 的克隆；
- 资源的「存在」= handle 被持有 + 至少一条 route 绑定存在；
- 资源不需要、也不应该实现一个「七种方法齐全」的 trait；绝大多数资源只提供其中几种。

示例：

```rust
// 业务类型，不是框架 trait 的实现。
struct TelemetryFeed { /* ... */ }

// 资源出现：
let feed = Arc::new(TelemetryFeed::new());
let feeds = app.scope("feeds", DefaultRootHandler)?;   // 资源命名空间的相对根
let view = feeds
    .route("telemetry/{id}")?
    .view(TelemetryViewTarget::new(feed.clone()))?;
let pull = feeds
    .route("telemetry/{id}")?
    .pull(TelemetryPullTarget::new(feed.clone()))?;
let head = feeds
    .route("telemetry/{id}")?
    .head(TelemetryHeadTarget::new(feed.clone()))?;

// 资源消失：撤销 route；最后一个 Arc 释放后 handle 自然析构。
view.remove()?;
pull.remove()?;
head.remove()?;
```

生命周期与长流：

- 删除 route 只影响**新的匹配**，in-flight target 持有 `Arc` 继续运行；
- 需要「撤销时让长流优雅退出」时，由 target 自己持有资源级 drain 令牌 / 关闭信号，
  框架不提供统一资源抽象；
- 如果应用需要「一组 route 一起撤销」，可以自己用 `Vec<RouteHandle<C>>` 或一个普通的
  分组结构管理，框架不强制类型。

## 10. 测试与验收建议

### 10.1 单元测试

- 路径规范化：首尾 `/`、空段、参数语法、catch-all 位置；
- 匹配优先级：静态 > 参数 > catch-all；冲突插入报错；同路径不同方法共存；
- 精确 route 优先：已注册 route 命中时，层级相对根不被调用；新挂载层级不改变既有
  route 的命中结果；
- 两类根 handler：没有进入更深层级 → 绝对根；进入层级但没有 route 命中 → 该层级相对根，
  且**不会**上抛到祖先层级 / 绝对根；
- 方法不支持：route 路径命中但方法不在集合内 → 最深进入层级的相对根，携带
  `FallbackInfo::MethodNotAllowed`；
- 根 handler 不可覆盖：`insert_level("")` 返回 `RootImmutable`；
- 作用域：`route("")` / `scope("")` / 绝对路径 / `..` 被拒绝；两者都只能变长；
- 运行期增删：并发 `insert_level` / `insert_route` / `remove_route` / `match` 无数据
  竞争；`remove` 后新请求不可见、in-flight target 仍然有效；
- `MethodSet`：位运算、`contains`、`intersects`；
- `RequestCancel`：target 拿到的是可取消令牌；适配器/长流 target 必须把
  `child_token()` 传进 await；实现中不得断言令牌是 `NonCancellableToken`；
- `ReqHandlerTarget`：旧 handler 经适配器行为不变；
- 自定义 `TrRouter`：一个最小实现能接入 `MptpServer`（编译期 + 运行期各一条）。

### 10.2 集成 / e2e

- 装配两个 demo 后，原有客户端脚本行为不变；
- `mptp_cs_smoke` 的 11 条 RPC（`ApiV1` / `ApiV2`）回归通过；
- 服务运行中插入资源 → 客户端 `VIEW` 成功；删除 → 新请求落到 fallback / 根 handler；
- 两类根 handler 的 404 / 405 / redirect 输出可被客户端识别；
- interface / service 层级：非 `Call` 请求由 service 层级的相对根返回 405 + `Allow`；
  未知顶层路径由绝对根返回 404；
- 两条 `PULL` + 一条 `CALL` 并发（P3 之后）。

### 10.3 约束

- 测试使用中英双语文档注释（`AGENTS.md` 第 2 条）；
- 单元测试 ≤1 分钟、全量 ≤5 分钟（第 12 条）；
- 库代码不 `unwrap` / `expect`；
- 新公开项有 `///` 文档与可编译示例。

## 11. 开放问题

1. **是否引入 matchit 依赖？**
   本稿建议**不引入**：matchit 的 route 精确匹配语义已与本设计对齐，但缺少方法维度、
   层级 / 根 handler、运行期并发增删与 `Arc` target；且当前环境离线依赖受限。默认实现
   按它的设计自研 trie；可复用 `rpc_router_trie` 的段式 trie 代码。
2. **`RequestCancel` 的产生位置与类型擦除**
   契约已定：每个被分发的请求都带 `RequestCancel`，**可能取消**，handler 必须按可取消
   编写。未定的是实现细节：
   (a) 产生位置：由 `MptpServer` 从 serve 令牌派生，还是在 `TrRouter` 上增加「按规则
       产生请求取消令牌」的策略方法（超时、每请求预算、层级配额等）？
   (b) 类型擦除：`RequestCancel` 需要在内部从任意 `K: TrCancellationToken` 构造；是要求
       `K: Clone + 'static` 后包装，还是定义对象安全的 `TrErasedCancel` 再实现
       `TrCancellationToken`？
   (c) 超时规则与默认值：v1 可以先只做「serve 令牌 child、不超时」，但不得改变 handler
       侧「令牌可能取消」的契约。
3. **`Allow` 头**
   新增 `StdHeaderKey::Allow`（建议编号 `0xD7`：`0xD0`–`0xD6` 已被 `Server` / `Location` /
   `Last_Modified` / `Set_Cookie` / `ETag` / `Cache_Ctrl` / `Expires` 占用），还是先用
   用户自定义字符串键？若新增，需要协议两端同意，并决定方法名的编码格式。
4. **路径参数是否 P0 就支持？**
   本稿倾向支持（默认实现本来就按 matchit 设计）；若想缩小首版范围，可先只支持静态段 +
   catch-all，参数留到 P1。
5. **两类根 handler 的安装位置**
   本稿把**绝对根**放在 router 构造（`RadixRouter::new(absolute_root)`），把**相对根**
   放在 `RouterCtx::scope(rel, relative_root)`；备选是让 `MptpServer::new` 同时接收
   绝对根 / 默认相对根。前者让「不可覆盖」自然成立，后者让自定义 router 的契约更简单。
   需要确认。
6. **`RouteHandle` 是否提供 RAII `RouteGuard`？**
   显式 `remove` 对「资源 DROP 与路由撤销解耦」更可控；RAII 能防止忘记撤销。可同时提供，
   但 guard 与 `Arc` 生命周期要写清楚。
7. **静态零装箱是否保留可选 fast-path？**
   与「所有规则运行期可增删」冲突；本稿建议放弃，等真实性能数据再评估。
8. **队列链 / `rpc_router_trie` 去留**
   改成 target 内部实现（推荐）还是保留为独立可选 crate？注意 3.6.1 说「可复用其段式
   trie 代码」只是代码级借鉴，不等于保留该 crate；两者结论可以不同（代码可搬进
   `RadixRouter`，crate 本身可弃用）。
9. **`RouterCtx` 是否也承载应用状态？**
   目前只承载路由表句柄 + 前缀；会话 / 连接上下文是否需要经由它注入，还是留在 target
   的构造闭包里？后者更简单，前者能统一传递。
10. **in-flight 与 drain**
    删除 route 不打断 in-flight；由于资源不是框架类型，drain / grace period / 强制 reset
    由资源自己的 target 实现（框架可提供辅助工具）。是否需要框架级默认值或协议约定，
    需要确认。
11. **路由内省**
    是否需要 `routes()` / 计数 / 列出当前绑定（调试、admin、观测）？默认实现第一版只返回
    `RouteId`，列表能力可后续加。
12. **归一化边界**
    尾斜杠等价（本稿选择等价）、连续斜杠、percent-decode、大小写：哪些归 router，哪些
    归调用方？需要一次协议层确认，避免两端不一致。
13. **相对根 handler 是否允许「显式转发」给上层**
    本稿规定兜底只到最深进入层级，不允许框架自动上抛。如果某层希望「自己没命中就交给
    上一层」，应当在自己的相对根 handler 内显式转发（重定向或内部调用）。是否需要框架
    提供标准的「转发 / 链式根 handler」辅助类型，需要确认。
14. **作用域绕过与路径 newtype 封口**
    `insert_route` 是公开 trait 方法，拿到 `Arc<dyn TrRouter>` 的代码可以绕过 `RouterCtx`
    直接插绝对路径。是否引入只能由 `RouterCtx` 构造的 `ScopedPath` newtype，把「只能向下」
    从纪律升级为类型约束？
15. **`FallbackInfo.allowed` 是否取并集**
    本稿取「路径精确命中的那条 route」的方法集合（同一路径可能按方法拆成多条 route，
    实现时需要合并这些 route 的方法）。是否需要把路径上所有可命中 route 的方法并集起来，
    还是只报当前这条？需要协议/客户端行为确认。
16. **参数零拷贝优化**
    第一版 `RouteParams` 拥有所有权（拷贝参数名与值）。是否在 P2 改为 matchit 式零拷贝
    （参数名借路由表、值借 location）？后者需要 `RouteMatch` 带生命周期参数，会扩散到
    `RouteOutcome` / `RouteRequest`，建议等接口稳定后再做。
17. **层级的卸载 API**
    当前只提供 route 的 `RouteHandle::remove`；层级挂载后没有卸载入口。是否需要
    `LevelHandle` / `RouterCtx::unmount`（级联撤销该层级的 route 与子层级）？动态 service
    下线可能需要它。
18. **`insert_level` 与既有 route 的交互**
    本稿允许在既有 route 的命名空间上挂载层级，并规定「route 精确匹配优先、层级不遮挡
    route」。是否需要在挂载时对「已有更长 route」给出警告 / 冲突，还是保持静默允许并
    由 route-first 语义保证不覆盖？

## 12. 被取代的初稿方案（决策记录）

| 初稿方案 | 被取代原因 |
| --- | --- |
| 两层 router：MPTP 顶层 + RPC 层 | RPC 的路径匹配与 MPTP 层语义相同，只是前缀嵌套；两层会重复实现最长前缀、404/405，且两份实现会漂移 |
| 静态 `tlist` router 保留、动态表并行 | 用户要求「不再支持仅静态的路由规则」；双入口会把零装箱变成永久兼容负担 |
| 旧的三层拆分：`TrRouteMatcher` / `TrRouteTable` / `TrRouteTarget`（名字 `TrRouteTarget` 保留、语义重定义） | 注入面只需要一个 `TrRouter`；匹配与注册共用一张表，拆分增加装配复杂度 |
| `PathOnly` / `MptpServer::with_table` | 没有需要适配的旧入口，直接切换更干净 |
| 资源放置 A/B/C 模型 | 资源就是挂载在某个作用域下的 target，不存在「资源属于哪个 router」的独立问题 |
| `ResourceHandler` 统一写 404 / 405 | 方法与兜底语义收敛到「最深进入层级的相对根 → 绝对根」；资源只是 handle + route 绑定，target 只写业务回复 |
| 静态路径零装箱是硬目标 | 统一运行期表的必要代价；改为「每请求一次擦除」，性能数据出来后再定优化 |
| 「空前缀绑定 + 任意祖先回退」的兜底 | 用户修正：改为「绝对根 + 每层相对根，兜底只到最深进入层级」，下层未命中不得上抛给唯一绝对根 |
| route 作为「前缀 + 剩余路径」 | 用户修正：route 改为精确匹配；需要整棵子树时挂载层级并给相对根 handler |
| target 内部一律传 `NonCancellableToken` | 用户修正：`RouteRequest` 携带可取消的 `RequestCancel`；定时取消机制未实现不等于可假定不可取消 |
| `TrResource` / `ResourceTarget` 资源抽象 | 用户修正：资源不是 trait，而是应用持有的 handle + 一组 route 绑定的运行时概念 |

## 13. 附：给 service 开发者的三句话

1. **今天**：router 是「路径前缀 → 一个 handler」的静态表；你拿到的 ctx 只是占位，
   运行期不能注册任何东西。
2. **将来**：你拿到的是一个**作用域**（知道自己的前缀），只能在这个作用域之下追加更长
   路径；更短路径、父级规则、根 handler 都不归你管，也改不了。
3. **现在能做的准备**：把业务资源的「方法处理」「路径注册」「生命周期」分开写；资源就是
   你持有的 handle + 你注册的 route，不需要等框架提供某种资源 trait。只要不依赖具体
   router 类型，统一 router 落地时迁移成本最小。
