## 0. 摘要

### 0.1 现状一句话

当前 router 是一个**装配期定型、按路径前缀把整条 channel 交给单一 handler** 的静态分派器：

- `MptpServer<C, R>` 对 `R` 只有 `TrPathRouter` 约束（外加
  `R::Handler: TrReqHandler<C>`），因此「匹配策略」本身是可注入的；
- 内置 `Router<C, RList>` 用 `tlist` 类型级列表容纳**编译期已知**的 handler，运行期不做
  `dyn`、不做 downcast、不在请求路径上装箱 future；
- 命中之后，handler 拿到 `method / location / headers / tx / rx`，**写回复与收尾的权力都在
  handler**，router 不再插手；
- 路由表在 `MptpServer::new(router)` 之后不可变；`serve_*` 只拿 `&self`；
- 访问方法（`Head/View/Post/Drop/Push/Pull/Call`）在顶层 router **只被透传，不参与匹配**；
  RPC 层 `RpcRouter` 明确只接受 `Call`，其余一律 `405`。

### 0.2 三个构想的结论

| 构想 | 结论 | 主要缺口 |
| --- | --- | --- |
| 抽象与实现分文件 | **部分做到**：trait 已从 `server_` / `rpc_` 中抽出，但与内置实现仍挤在同一文件 | `router_.rs` 同时承担契约、类型级机器、内置策略、错误、辅助函数与测试；改任何一类都要碰同一个文件 |
| 简单实现 + 可注入实现 | **可注入已成立，但注入面太窄** | `TrPathRouter::Handler` 是单一类型；`match_path` 只借出 `&Handler`；不传 `method`；没有匹配错误；`TrPathRouterMut` 是未使用的死接口且签名有缺陷；动态异构 handler 没有对象安全的擦除层 |
| 运行期动态资源 + 标准方法语义 | **基本没有** | 路由表不可变；`&'static str` 前缀；没有资源模型；没有 `Head/View/Post/Drop/Push/Pull` 的服务端语义与 helper；`Pull` 长流会被串行 accept 循环卡住；删除资源没有 drain / 撤销 / 取消 |

### 0.3 建议路线

1. **先做文件与文档层面的分离**（零行为变更）：`router/contract_.rs` 只放契约，
   `router/static_.rs` 放现有 `Router`，`router/dispatch_.rs` 放 `tlist` 递归分派，
   `router/error_.rs` 放错误；`mod.rs` 只逐项重导出。
2. **新增平行的动态契约**，不破坏现有 `TrPathRouter`：`TrRouteMatcher`（只读匹配）+
   `TrRouteTable`（运行期增删）+ 对象安全的 `TrRouteTarget` 擦除层；旧实现通过适配器接入。
3. **把「资源语义」放在 target 侧，而不是 router 里**：新增 `TrResource` 与
   `ResourceHandler` 适配器，统一 `HEAD`、`405 + Allow`、`POST → 201 + Location`、
   `DROP`、`PULL` 的流式回复与收尾。
4. **最后改 serving 的并发模型**：注入 channel spawner、隔离单 channel 错误、提供优雅
   关闭与按资源的撤销/取消；否则动态资源一旦有长流，accept 循环就会被拖死。

## 1. 差距矩阵

图例：✅ 已具备；⚠️ 部分具备或有明显限制；❌ 不具备。

| # | 能力 | 现状 | 差距 |
| --- | --- | --- | --- |
| 1 | 契约与实现分文件 | ⚠️ | `router_.rs` 约 571 行混放七类职责；`rpc_core_v1` 侧同样 |
| 2 | 开箱可用的简单 router | ✅ | `Router<C, RList>` 够用，但只支持编译期登记 |
| 3 | 用户注入自定义匹配器 | ⚠️ | `TrPathRouter` 是注入缝；受单一 `Handler`、借用返回、无方法参数限制 |
| 4 | 运行期添加路由 / 资源 | ❌ | `Router` 消费式构建；`MptpServer` 持有 `R` 且 `serve_*` 为 `&self` |
| 5 | 运行期删除路由 / 资源 | ❌ | 没有删除 API，也没有 drain / 取消语义 |
| 6 | 方法参与路由 | ❌ | 顶层 `match_path` 不接收 `method`；内置 `Router` 的 `match_path` 恒等返回自身 |
| 7 | 非 `Call` 方法可用 | ❌ | `RpcRouter` 只接受 `Call`；普通资源方法没有服务端 helper |
| 8 | 未命中时的标准回复 | ⚠️ | RPC 层会写 `404/405`；MPTP 顶层 `RouterError::NotFound` 只返回错误，channel 被直接丢弃 |
| 9 | 资源元信息 / `HEAD` | ❌ | 没有资源抽象，也没有 `Allow` / 元数据约定 |
| 10 | `POST` 创建与 `Location` | ❌ | 没有创建语义；`StdHeaderKey::Location` 已有，但没有框架写入点 |
| 11 | `DROP` 删除与级联 | ❌ | 没有资源生命周期；删除路由与删除资源没有区分 |
| 12 | `PULL` / `PUSH` 长流 | ⚠️ | handler 可以持有 `tx/rx` 手工读写；但没有服务端 suffix helper，且串行 accept 会阻塞后续 channel |
| 13 | 并发接入 | ⚠️ | `serve_listener_async` 逐个 `await` handler；并发只能由 handler 自己 spawn |
| 14 | 优雅关闭 / 撤销 | ❌ | 没有 `ServeHandle`、没有 in-flight 跟踪、没有按资源取消 |
| 15 | 观测与鉴权 | ❌ | 没有中间件链（这是有意的）；也没有替代的 per-target 钩子 |

按依赖排序：

- **P0 的文件拆分不阻塞任何功能**，但它是后续所有改动的阅读基础；
- **P1 的动态表是 P2 / P3 的前提**：没有可共享的路由表，「运行期添加资源」无从谈起；
- **P3 的并发接入是 `Pull` 真正可用的前提**：即使路由与语义都就绪，串行 accept 仍会让
  第二条长流饿死；
- **`Allow` / `Location` 等协议细节不应阻塞 P1**，可以先在资源侧用用户自定义头验证，
  再决定是否进入标准头区段。

## 2. 分层与概念

### 2.1 调用链

```text
MptpServer<C, R>
  │  解码请求前缀（method / location / headers）
  │
  ├─ R: TrPathRouter::match_path(location) -> Option<&R::Handler>   ← 匹配策略注入缝
  │
  └─ R::Handler: TrReqHandler<C>::handle_async(method, location, headers, tx, rx)
        │
        ├─ Router<C, RList>（内置顶层 router）
        │     └─ 内部 tlist 递归：最长前缀 → 具体 handler
        │           ├─ RpcRouter<I, S>（RPC 内联 router，只接受 Call）
        │           │     └─ TrRpcService<I, C>（service 方法 dispatch）
        │           └─ 任意用户 handler
        │
        └─ RpcRouterHandler<R, C>（队列版适配器）
              └─ TrRpcRouter<C>::resolve(location) -> &Route
                    └─ ServiceRoute<C>（有界队列）→ worker
```

要点：

- **server 只认识 `TrPathRouter` 与 `TrReqHandler`**，不认识 RPC，也不认识资源；
- **顶层 router 只负责「把 channel 交给谁」**，不负责写回复；
- RPC 层是建在顶层 handler 之上的**第二个 router**，它自己再做 interface → service 的匹配；
- 队列版 `TrRpcRouter` 是第三个可替换的匹配层，但只服务于「匹配与交付分离」的旧链。

### 2.2 概念对照

| 概念 | 含义 | 今天的代码 |
| --- | --- | --- |
| route（路由项） | 一条「路径（将来还有方法）→ 目标」的映射 | `RouteValues::Cons { prefix_, handler_, .. }` |
| router（路由器） | 持有路由项并执行匹配的容器 | `Router<C, RList>` / 用户实现的 `TrPathRouter` |
| handler | 能处理一次请求的代码单元；拥有 `tx/rx` | `TrReqHandler<C>` |
| target（目标） | 被路由到的对象；将来可以是资源句柄 | 今天就等于 handler 实体 |
| resource（资源） | 有路径、有方法集合、有生命周期的对象 | **尚不存在** |
| service | RPC 层的业务分组；一个路径下由 body enum 分派多个方法 | `TrRpcService<I, C>` |
| method | 七种访问方法之一 | `AccessMethod` |

**最关键的一条区分**：route 的「目标」不必等于「一次请求的处理函数」。动态资源场景下，目标是
一个**有状态、可撤销、可被多个请求共享**的资源句柄；handler 只是这个句柄上的一次调用。

### 2.3 契约清单

| 契约 | 位置 | 职责 | 对象安全 |
| --- | --- | --- | --- |
| `TrPathHandler` | `mptp_smux/src/serving/router_.rs` | 提供 `const PATH`，供 `Router::call` 登记 | 不涉及 |
| `TrPathRouter` | 同上 | 只读匹配：路径 → `&Handler` | 否（关联类型 + 泛型生命周期） |
| `TrPathRouterMut` | 同上 | 装配期登记（**未使用**） | 否 |
| `TrReqHandler<C>` | `abs_mptp/src/serving/handler_.rs` | 一次请求的行为契约；按值拿两个半边 | 否（GAT `HandleAsync<'f>`） |
| `TrRpcRouter<C>` | `rpc_core_v1/src/serving/router_.rs` | RPC 层只读匹配 + 注册 | 否（泛型 `add_interface`） |
| `TrRpcServiceRoute<C>` | `rpc_core_v1/src/serving/route_.rs` | 命中后如何交付（队列 / 调度器） | 否 |
| `TrRpcService<I, C>` | `abs_rpc_serv` | service 如何被调度 | 否 |
| `TrResource<C>` | **不存在** | 资源方法语义 | — |

## 3. 现有设计复盘

### 3.1 单 handler，不做中间件

这是当前 router 最重要、也最容易被误解的决定。

**做法**：路由命中之后，框架只调用**那一个** handler；没有「链」，没有 `next()`，没有统一的
「回复对象」在层间传递。

**理由**（`router_.rs` 模块文档已写明）：`abs_mptp::serving::TrReqHandler` 的契约把
`tx` / `rx` 按值交给 handler，**写回复与收尾的权力在 handler 自己**。在「谁写最终回复、谁负责
半关闭、谁负责读完」没有唯一答案的前提下，硬造一条中间件链只会把语义变成框架猜谜。

**收益**：

- handler 对 channel 有完全控制权，长流、早停、错误回复都可以自己决定；
- 没有「中间件 A 写了头、中间件 B 又写了一次」这类状态机；
- 框架不需要定义统一回复类型，也不强加缓冲。

**代价**（对动态资源很关键）：

- 没有跨切面插入点：鉴权、限流、审计、指标只能写进每个 handler，或包一层 handler；
- 也没有「路由命中但 target 拒绝方法」的统一处理点——这个点现在由 RPC 层的 `RpcRouter`
  自己补，MPTP 顶层没有；
- 目标一旦被路由到，框架就不再观察它，无法在「资源被撤销」时统一取消。

> **结论**：不建议为了动态资源再引入通用中间件链；应当把横切能力放到 **target / resource
> 句柄**上（每个资源自带策略字段，或由 `ResourceHandler` 包一层），router 仍然只做匹配。

### 3.2 路径匹配语义

顶层与 RPC 层使用同一套规则，但各自实现了一份：

- **最长前缀**：登记 `/topic` 与 `/topic/chat` 时，`/topic/chat/42` 命中后者；
- **完整路径段**：`api/v1` 不命中 `api/v10`；空前缀匹配一切；
- **同长度平局**：后登记的那条在前（`tlist` 头插），所以「后登记生效」；
- **重复前缀**：内置 `Router` 不报错，直接并存，匹配时按上述规则选一条。

实现细节：

- `Router::match_path` 对任何路径都返回 `Some(self)`，真正匹配发生在
  `Router::handle_async` 内部（`TrPathRouterList::match_route`）；
- `RpcRouter` 先用 `strip_interface_prefix_` 剥掉 `I::PATH`，再用
  `path_prefix_len_` 在 service 列表里匹配；
- 两处各有一份 `path_prefix_len_`（`mptp_smux` 与 `rpc_core_v1`），语义相同但代码重复。

**这带来两个结构性问题**：

1. `TrPathRouter` 对内置 `Router` 是**恒等实现**。注入缝在类型层面成立，但在内置实现上
   没有实际约束力：`MptpServer` 永远命中 `Router`，再由 `Router` 内部决定是否 `NotFound`。
   因此「server 在把 channel 交出去之前就能知道未命中」这件事，对内置实现并不成立。
2. 匹配规则被复制到 RPC 层。将来加路径参数、方法匹配、尾段通配时，两份实现会漂移。

### 3.3 类型级列表：用类型系统换掉 `dyn`

内置 `Router` 与 `RpcRouter` 都用 `tlist` 的 `TCons` / `TNil` 记录路由项：

```text
Router<C, TCons<H1, TCons<H2, TNil>>>
             │            │
             └─ 运行期 RouteValues::Cons { prefix_, handler_: H1, tail_: ... }
```

好处：

- handler 数量没有元组长度上限；
- handler 实体按具体类型内联存放，没有 `dyn Any`、没有 downcast；
- 请求路径上没有 `Pin<Box<dyn Future>>`；递归分派用 `EitherMayCancel` 把两个分支合成一个
  可取消 future，用 `MapErrMayCancel` 做错误映射；
- `Send` / `Sync` 由实际 handler 类型自动决定，不需要手工断言。

代价：

- **路由数量与类型在编译期固定**。`route` / `call` 每调用一次，`Router<C, R>` 的类型就变一次；
  无法把它们塞进一个固定类型的字段，也无法在运行期插入一个「直到运行时才知道类型」的 handler；
- 类型错误信息随嵌套深度增长；
- `RouteValues` / `TrRouteValues` / `TrPathRouterList` 这些机器虽然 `#[doc(hidden)]`，
  仍是公开导出面的一部分；
- 运行时没有任何「列出路由」「删除路由」的反射能力。

> **结论**：`tlist` 适合「装配期已知、数量不定」的静态场景，不适合动态资源。动态场景需要
> **类型擦除后的 target 句柄**（`Arc<dyn ...>`），并接受仅在动态路径上装箱 future 的代价。

### 3.4 通道按值交付与收尾

`TrReqHandler::handle_async` 按值拿 `tx` / `rx`，模块文档要求 handler 负责收尾，标准顺序是：

```text
写回复 → 半关闭 tx（drop，排空后发 FIN）→ 读完 rx → 释放 rx
```

`close_channel_async(tx, &mut rx)` 封装了「先 `drop(tx)` 再 drain 到 EOF」。顺序不能反：
先放掉 `rx` 会发 `RESET`，把还没排空的响应抹掉。

这对长流有两面性：

- **正确**：`Pull` handler 本来就应该自己持有 `tx` 持续写，不能提前调用
  `close_channel_async`；
- **不足**：框架没有「流结束」的抽象，也没有在资源被撤销时替 handler 结束流的手段；
  handler 只能自己监听取消令牌或写失败。

### 3.5 取消

- 所有公开异步方法原则上经 `gen_may_cancel_future` 包装，返回 `impl TrMayCancel`；
- 分派 future 的组合子 `EitherMayCancel` / `MapErrMayCancel` / `ReadyMayCancel` 在
  `cancel_future_.rs`，只服务于 router 递归；
- `serve_listener_async` 给每条 channel 一个 `cancel.child_token()`；
- 取消的粒度是**一次请求 / 一条 channel**，没有「一个资源」或「一组流」的令牌。

一个需要澄清的现状：`server_.rs` 注释说「已经在处理的子流不会被中途打断」，但
`serve_listener_async_` 是**内联 `await`** `serve_channel_async_` 的。如果外层 listener future
被 drop，内联等待中的 handler future 也会被 drop，`tx` / `rx` 随之释放。只有当 handler 已经
把两个半边移交给外部 task 时，「不会被打断」才成立。这个语义应在文档与实现中明确，而不应
依赖读者猜测。

### 3.6 装配期定型

- `Router::new()` 是 `const fn`；`route` / `call` **消费 `self`** 并返回新类型；
- `RpcRouter::add_service` 同样消费 `self`；
- `MptpServer::new(router)` 把 router 按值存起来；
- `serve_channel_async` / `serve_listener_async` 都只拿 `&self`；
- `MptpServer::router()` 只返回 `&R`，没有 `&mut`，也没有「拿到共享句柄」的入口。

`RouterCtx<C>` 与 `RpcServiceCtx` 都是零大小占位，只为「以后注入应用状态时不改调用形状」
保留参数。它们目前不能承载共享注册表。

`TrPathRouterMut` 本意是装配期继续登记，但：

- **没有任何实现**，也没有被 `MptpServer` 或 `Router` 使用；
- `Handler` 是单一关联类型，无法表达异构 handler；
- `add_rule` 的闭包是 `FnOnce(&'f str) -> Self::Handler`，把 rule 的借用期带进 handler，
  与内置 `Router` 的 `&'static str` 前缀不是同一套语义；
- `match_path` 只读借出 `&Handler`，即便实现了也无法在运行期安全替换。

> 结论：`TrPathRouterMut` 目前是一个**会误导使用者的公开接口**。建议在 API 变更获批后删除，
> 或彻底重设计成第 6 节的 `TrRouteTable`，不要保留半成品。

### 3.7 两代 RPC router

`rpc_core_v1` 里有两条链，值得作为 router 演进的参照：

**内联链（当前主推）**

```text
Router::call(|ctx| RpcRouter::<ApiV1>::new(ctx).add_service::<Impl>(...))
  → RpcRouter::handle_async
      → 检查 method == Call（否则 405）
      → 剥 interface 前缀（否则 404）
      → service 最长前缀匹配（否则 404）
      → RpcCallCtx → TrRpcService::dispatch_async
      → ctx.close_async()
```

**队列链（保留给需要背压 / 自定义 worker 的使用者）**

```text
TrRpcRouter::resolve(location) -> &Route
  → RpcRouterHandler：405 / 404 / 构造 RpcJob / enqueue
  → ServiceRoute 的有界队列 → worker
```

队列链已经把「匹配」「交付」「接入 MPTP」拆成三个契约，这正是 router 模块应该学习的粒度；
但它只面向 `Call`，且交付语义绑定队列。

### 3.8 与运行期资源的根本冲突

把三个构想放在一起看，冲突点很集中：

| 冲突 | 静态 tlist 的做法 | 动态资源需要 |
| --- | --- | --- |
| 路由项何时确定 | 编译期，消费式 builder | 运行期，任意时刻 |
| 路由表可变性 | 构造后不可变，`&self` 只读 | 共享句柄 + 内部可变性 |
| target 类型 | 单一/列表内具体类型 | 类型擦除的异构句柄 |
| 匹配结果借用 | `&Handler` 借用 router | 必须交出可独立持有的句柄，不能跨 `await` 持锁 |
| 方法 | 不参与匹配 | 方法决定 target 或至少决定 405 |
| 生命周期 | 与 server 同生共死 | 可撤销、可 drain、可取消 |
| 长流 | handler 自己 spawn | 框架要能跟踪、限流、关闭 |

## 4. service 开发者今天怎么用

这一节是「现状版使用指南」。目标读者是写 service / handler 的开发者。

### 4.1 只想写一个 handler

如果所有路径都由你自己的代码分派，最省事的是**恒等 router**：

```rust
use mptp_smux::serving::TrPathRouter;

/// 假定 `MyHandler` 已实现 `TrReqHandler<SrvCfg>`。
struct AnyPath {
    handler: MyHandler,
}

impl TrPathRouter for AnyPath {
    type Handler = MyHandler;

    fn match_path<'f>(&'f self, _path: &'f str) -> Option<&'f Self::Handler> {
        // 把所有路径都交给同一个 handler；路径解析在 handler 内完成。
        Some(&self.handler)
    }
}

// MptpServer::<SrvCfg, AnyPath>::new(...)
```

`rpc_demo` 与 `mptp_smux_v1_demo` 就是这样做的：各自带一份 `Router<T>`，用空前缀把请求交给
唯一的 `RpcRouter`。这种写法适合「顶层只有一个分发器」的服务。

### 4.2 多个 RPC interface：用内置 `Router` + `RpcRouter`

这是当前推荐的 RPC 服务端装配方式（`mptp_cs_smoke/src/server.rs` 即此形状）：

```rust
use mptp_smux::serving::{MptpServer, Router};
use rpc_core_v1::serving::RpcRouter;

let router = Router::<SrvCfg, _>::new()
    .call(|ctx| {
        RpcRouter::<ApiV1>::new(ctx)
            .add_service::<WorkspaceServiceImpl>(move |_| WorkspaceServiceImpl::new_(store.clone()))
            .add_service::<SessionServiceImpl>(move |_| SessionServiceImpl::new_(store.clone()))
    })
    .call(|ctx| {
        RpcRouter::<ApiV2>::new(ctx)
            .add_service::<WorkspaceServiceImpl>(move |_| WorkspaceServiceImpl::new_(store))
    });

let server = MptpServer::<SrvCfg, _>::new(router);
```

- 每个 `.call` 按 `RpcRouter` 的 `TrPathHandler::PATH`（即 `I::PATH`）追加一条前缀；
- 路径形如 `/api/v1/workspace`、`/api/v2/session`；
- 方法级分派在 `RpcRouter` 内：只有 `Call` 被接受，业务方法由 body enum 变体决定；
- 路由数量没有元组上限，但**全部在装配期确定**。

### 4.3 注入自己的匹配策略

实现 `TrPathRouter` 即可替换匹配算法（静态表、正则、前缀树、外部配置……）。当前可用的
实现签名只有：

```rust
pub trait TrPathRouter {
    type Handler;
    fn match_path<'f>(&'f self, path: &'f str) -> Option<&'f Self::Handler>;
}
```

它适合：

- 目标类型单一（或你自己先做类型擦除）；
- 匹配结果能直接从 `&self` 借出；
- 不需要知道 `method`；
- 匹配是同步且不会失败的。

不适合：运行期增删、异构 target、需要读锁保护的表、需要按方法分派。
这些限制是第 5.2 节的主要讨论对象。

### 4.4 需要背压或自定义 worker

使用队列链：

1. 为每个 service 建立有界队列与 worker；
2. 用 `ServiceRoute::new(SERVICE_PATH, sender)` 交出注册项；
3. 用 `rpc_router_trie::RpcRouter` 沿 interface / service 两级注册；
4. `into_handler()` 交给 `MptpServer`。

这条链的匹配与交付是分开的；如果你要自己实现调度器，实现 `TrRpcServiceRoute` 即可。
但这条链同样只接受 `Call`。

### 4.5 想用非 `Call` 方法

今天没有框架级支持。可行但手工的路径：

1. 在顶层实现一个 `TrReqHandler`，让它持有你的资源表；
2. 在 `handle_async` 里按 `method` 分支；
3. 自己写回复前缀 / body / 流，并自己收尾。

这意味着 `Head/View/Post/Drop/Push/Pull` 的**状态码约定、`Allow`、`HEAD` 不写 body、
`POST` 的 `Location`、`PULL` 的持续写**都要每个 handler 重写一遍。第 6 节建议把这部分
收敛到 `ResourceHandler`。

### 4.6 常见坑

1. **handler 忘记收尾**：返回前必须写完并 `close_channel_async`（或把两个半边交给负责收尾的
   worker）。框架不会替你 `drop(tx)` / drain。
2. **先 drop `rx`**：会发 `RESET`，可能抹掉未排空的响应。
3. **以为 `NotFound` 会回 404**：MPTP 顶层 `Router` 未命中时返回 `RouterError::NotFound`，
   `MptpServer` 把它变成 `ServeError` 并结束该条处理路径；channel 被丢弃，客户端不一定收到
   一个格式良好的 404。需要 404 的话，必须在 handler 内自己写。
4. **路径写成裸字符串前缀**：内置实现按完整路径段匹配，`/api/v1` 不会命中 `/api/v10`；
   自己实现时不要用 `starts_with` 一把梭。
5. **重复前缀不会报错**：内置 `Router` 允许重复，后登记者优先；需要冲突检测就自己实现。
6. **路由表在运行期不能改**：`MptpServer` 拿走 router 后只给 `&R`；要动态能力，等第 6 节
   的契约，或自己在 handler 内维护一张 `Arc<RwLock<...>>` 表（但拿不到框架的方法级语义）。

## 5. 三个构想的差距分析

### 5.1 抽象与实现分离

#### 现状

`mptp_smux/src/serving/router_.rs` 约 571 行，至少承担七类职责：

| 区段（约） | 内容 | 类型 |
| --- | --- | --- |
| 54–85 | `TrPathHandler` / `TrPathRouter` / `TrPathRouterMut` | 公开契约 |
| 87–107 | `RouterCtx` | 装配上下文 |
| 109–147 | `RouteValues` / `TrRouteValues` | 类型级机器（`doc(hidden)`） |
| 149–241 | `Router` 与 builder | 内置实现 |
| 243–281 | `RouterError` / `map_handler_error_` / `path_prefix_len_` | 错误与辅助 |
| 283–449 | `TrPathRouterList` / 递归分派 | 分派机器（`doc(hidden)`） |
| 451–571 | 单元测试 | 测试 |

`rpc_core_v1/src/serving/router_.rs` 同样把「`TrRpcRouter` 契约」「`RpcRouterHandler` 适配器」
「404/405 拒绝与收尾」放在一起；`rpc_router_.rs` 又把「`TrRpcServiceList` 契约」「运行期
枚举」「匹配算法」「`TrReqHandler` 实现」放在一起。

#### 问题

- **读者找不到重点**：想理解「契约是什么」的人要跳过几百行类型机器；想改「匹配策略」的人
  会碰到公开 trait；想加新实现的人要和测试、辅助函数挤在同一文件。
- **变更放大**：改错误类型、改分派组合子、加一个方法，都会让同一个文件出现在 diff 里，
  评审时很难区分「契约变了」还是「实现变了」。
- **可见性混乱**：`#[doc(hidden)]` 的机器与真正的公开契约混排，导出的边界不直观。
- **测试耦合内部**：单测直接测 `path_prefix_len_` 与私有构造，拆分后需要重新安排。

#### 建议

把 `serving/router_` 改成目录（按仓库规则用 `mod.rs`，且 `mod.rs` 只做逐项导出）：

```text
mptp_smux/src/serving/
├── mod.rs
├── router/
│   ├── mod.rs          # 只逐项 pub use，不放逻辑
│   ├── contract_.rs    # 三个契约 + 匹配结果 + 错误 trait（无具体策略）
│   ├── static_.rs      # 现有 Router<C, R> 与 builder
│   ├── dispatch_.rs    # RouteValues / TrRouteValues / TrPathRouterList / 递归分派
│   ├── error_.rs       # RouterError / 错误映射
│   └── dynamic_.rs     # 将来：DynamicRouter / RouteTable / RouteGuard
├── cancel_future_.rs   # 组合子，保持不变
├── server_.rs
└── ...
```

约束：

1. `contract_.rs` **不得** import `RouteValues`、`Router`、`tlist` 或任何具体策略；
2. `static_.rs` / `dynamic_.rs` **不得**声明新的公开 trait；
3. `dispatch_.rs` 的输入输出只用契约类型，便于将来同时服务静态与动态实现；
4. `mod.rs` 逐项列出导出，不用 `*`；
5. 现有公开路径（`mptp_smux::serving::Router` 等）通过 `pub use` 保持不变。

`rpc_core_v1` 侧建议同样拆：

```text
rpc_core_v1/src/serving/
├── router/contract_.rs      # TrRpcRouter
├── router/adapter_.rs       # RpcRouterHandler + 拒绝/收尾
├── rpc_router/contract_.rs  # TrRpcServiceList
├── rpc_router/static_.rs    # RpcRouter<I, S> + add_service
└── ...
```

**验收**：纯移动 + 重导出，不改任何签名；`cargo doc` 无新增警告；原有单元测试与 doctest
全部通过；`git diff` 中公开项的路径不变。

### 5.2 默认实现与可注入实现

#### 已经成立的

- `MptpServer<C, R>` 对 `R` 只有 `TrPathRouter` 约束，因此注入是类型层面成立的；
- 两个 demo 各自实现了 `TrPathRouter`，证明「不用内置 `Router` 也能跑」；
- `Router::call` 只要求 `H: TrPathHandler`；要让结果交给 `MptpServer`，`H` 还必须实现
  `TrReqHandler<C>`。因此 handler 可以是 RPC router，也可以是别的。

#### 不够的

**(a) `Handler` 是单一类型**

`TrPathRouter` 只能有一个 `type Handler`。内置 `Router` 用 `tlist` 把异构 handler 藏进
`Router` 自身，于是 `Handler = Self`；但一个外部实现如果想同时挂 `RpcRouter<ApiV1>`、
`RpcRouter<ApiV2>` 和普通资源 handler，就必须自己造 enum 或 `Box<dyn>`，框架没有提供
任何擦除类型。

**(b) `match_path` 借出 `&Handler`，且路径与 self 共用生命周期**

```rust
fn match_path<'f>(&'f self, path: &'f str) -> Option<&'f Self::Handler>;
```

（以上是 trait 方法签名；下面用一张动态表说明它为什么不够。）

动态表通常长这样：

```rust
struct Table {
    routes: RwLock<BTreeMap<String, Arc<dyn Target>>>,
}

impl Table {
    fn match_path<'f>(&'f self, _path: &str) -> Option<&'f Arc<dyn Target>> {
        let guard = self.routes.read().unwrap();
        // 问题：`&Arc<dyn Target>` 借用自 `guard`，guard 必须在返回值存活期间一直活着；
        // 但 guard 不是 `Send`，也无法跨 `await` 持有。返回 `Arc` 克隆才能脱离 guard。
        let _ = guard;
        None
    }
}
```

要么改成返回**拥有所有权的句柄**（`Arc<dyn Target>`），要么让匹配同步完成并把 guard 留在
调用点——后者与 `Option<&Handler>` 的签名不兼容。此外，`path: &'f str` 被绑到与 `&self`
同一个 `'f`，比实际需要更严格，进一步限制了返回值的生命周期。

> 上面的 `unwrap()` 只是示意；真实实现必须处理 lock poisoned，且不能在持有 guard 时
> `await`。

**(c) 不传 `method`**

方法级分派（同一个路径，`View` 交给只读 target，`Drop` 交给管理 target；或直接按
`(path, method)` 注册）无法在匹配层表达。今天只能在 handler 内部 `match method`。

**(d) 没有匹配错误**

`match_path` 返回 `Option`，无法表达「路径命中但配置损坏」「表处于 draining，暂时拒绝」
这类需要 503 或 500 的情况。错误只能退化成 `None`（404），或塞进 handler。

**(e) 没有对象安全的 handler 契约**

`TrReqHandler<C>` 的 GAT `HandleAsync<'f>` 让它无法直接 `dyn`。要在运行期保存
`Box<dyn TrReqHandler<C>>`，必须另写一个「装箱 future」的擦除适配器。框架没有提供，文档也
没有说明应该怎么写。

**(f) `TrPathRouterMut` 是死接口**

见 3.6。它不仅没被使用，而且它的形状会让使用者以为「实现它就能动态注册」，实际上
`MptpServer` 根本不调用它。

**(g) server 拿不到共享句柄**

`MptpServer::new(router)` 之后，应用侧就只剩 `router()` 的只读借用。即便 router 内部用了
`RwLock`，应用也需要在构造前 clone 一份 `Arc`；目前 `RouterCtx` 是空的，没有官方的
「把注册表句柄同时交给 server 和应用」的通道。

#### 建议：三层契约 + 擦除层

```rust
/// 一次匹配的结果。
pub struct RouteMatch<T> {
    /// 被命中的目标。
    pub target: T,
    /// 命中的路径长度（字节）；用于把剩余路径交给 target。
    pub matched_len: usize,
}

/// 只读匹配能力：`MptpServer` 只需要这一层。
pub trait TrRouteMatcher {
    /// 目标类型；静态实现可用具体类型，动态实现用 `Arc<dyn TrRouteTarget<C>>`。
    type Target;

    /// 按方法与路径匹配。
    fn match_route(
        &self,
        method: AccessMethod,
        location: &str,
    ) -> Option<RouteMatch<Self::Target>>;
}

/// 运行期可增删的路由表：应用侧持有。
pub trait TrRouteTable: TrRouteMatcher {
    type Err: core::error::Error;

    /// 登记或替换；返回被替换的旧目标。
    fn insert(&self, path: &str, target: Self::Target) -> Result<Option<Self::Target>, Self::Err>;

    /// 撤销一条路由；返回被移除的目标。
    fn remove(&self, path: &str) -> Option<Self::Target>;
}
```

设计要点：

- **`Target` 用关联类型而不是固定 `dyn`**：静态实现可以继续零成本；动态实现把它取成
  `Arc<dyn TrRouteTarget<C>>`；
- **`match_route` 接收 `method`**：把「方法是否参与匹配」留给实现。内置静态 `Router` 可以
  忽略它（行为不变），动态实现可以按 `(path, method)` 或资源的能力集匹配；
- **返回 `RouteMatch<T>` 而不是 `&T`**：目标由值 / `Arc` 交出，不跨 `await` 持锁；
- **`insert/remove` 用 `&self`**：动态表内部用 `RwLock` / 无锁结构；静态表如果不想提供，
  可以不实现 `TrRouteTable`；
- **旧 `TrPathRouter` 保留**，通过适配器 `PathOnly<R>` 或 blanket impl 接到新 matcher；
  `MptpServer` 的约束可以逐步从 `TrPathRouter` 切到 `TrRouteMatcher`，或新增
  `MptpServer::with_matcher` 避免一次性破坏。

对象安全的目标擦除层（草案）：

```rust
/// 类型擦除后的路由目标。只用于动态表。
pub trait TrRouteTarget<C: TrConfig>: Send + Sync {
    fn handle_route<'f>(
        &'f self,
        req: RouteRequest<'f, C>,
        cancel: ErasedCancelToken, // 需要对象安全的取消令牌；见下
    ) -> Pin<Box<dyn Future<Output = Result<(), RouteError>> + Send + 'f>>
    where
        C: 'f;
}
```

注意：`abs_cancel::TrCancellationToken` 带关联类型 `ChildToken` / `Cancellation`，**不能直接
`dyn`**。动态路径要么：

1. 把取消令牌在进入擦除层之前就转换成具体类型并捕获进 boxed future（推荐，无需新契约）；
2. 或在 `mptp_smux` 里新增一个对象安全的 `TrErasedCancel`（只含 `is_cancelled` 与
   `cancellation() -> BoxFuture`）。

这是动态实现落地前必须确认的细节，不能在文档里含糊带过。

### 5.3 运行期动态资源与标准访问语义

#### 现状事实

1. **不可变**：`Router` 的 builder 消费 `self`；`MptpServer` 持有 `R`；`serve_*` 是 `&self`；
   没有 `insert` / `remove` / `Arc` 共享入口。
2. **前缀是 `'static`**：`Router::route(prefix: &'static str, ...)`；运行期拼出来的路径
   无法登记。
3. **方法不参与路由**：`TrPathRouter::match_path` 只有 `path`；内置 `Router` 只做前缀；
   `RpcRouter` 在 handler 内检查 `Call`。
4. **没有资源模型**：没有「资源」类型、没有方法集合、没有元数据、没有父子关系、没有
   创建 / 删除 / 列举语义。
5. **未命中不写回复**：顶层 `RouterError::NotFound` 只返回错误。
6. **长流被串行循环阻塞**：`serve_listener_async_` 内联 `await` handler；`Pull` handler 如果
   持续持有 `tx`，listener 就无法 accept 下一条 channel，除非 handler 自己 spawn。
7. **没有服务端 suffix helper**：客户端有 `send_req_suffix_async` / `recv_resp_suffix_async`；
   服务端只有裸 `tx/rx`，`close_channel_async` 又是「一问一答」收尾，不适合长流。
8. **不是协议缺能力**：客户端已经能收发 suffix 流；缺的是服务端的持续写 / 读 helper、
   结束语义与生命周期管理。这一区分很重要，避免把 serving 的工程问题误判成协议问题。

#### 资源挂在哪一层（关键设计选择）

用户的例子是「在**某个 service** 中添加一个可 `Pull` 的资源，并指定某个路径」。这引出一个
当前没有答案的问题：动态资源与 RPC 的 interface / service 前缀是什么关系？

今天的约束：

- 顶层 `Router` 只按前缀选一个 handler；
- `RpcRouter` 在 handler 内**只接受 `Call`**，其它方法直接 `405`；
- `TrRpcService` 的路径来自 `SERVICE_PATH`，是编译期常量，且只表达 service，不表达资源。

因此「在 service 下挂资源」不能只靠现状拼出来，需要先选一种放置模型：

| 模型 | 形状 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 全局扁平资源表 | `DynamicRouter` 直接登记 `/feeds/telemetry` | 最简单，与 RPC 解耦 | 资源不在 interface / service 的命名空间下；鉴权与配额只能按全局路径做 |
| B. interface 下最长前缀共存 | `/api/v1` → `RpcRouter<ApiV1>`；`/api/v1/feeds` → `ResourceHandler` | 复用现有 interface 前缀与最长前缀规则；客户端看到统一的 `/api/v1/...` | 需要方法感知或「更长前缀优先」来解决 `/api/v1/feeds` 与 `/api/v1/workspace` 的共存；资源要自己剥前缀 |
| C. service 内资源表 | `RpcRouter` 把非 `Call` 委托给该 service 的资源表 | 最贴近「在某个 service 中添加资源」的直觉；权限 / 配额可按 service 归属 | 要扩展 RPC service 契约或让 `RpcRouter` 持有资源表；RPC 层开始认识「资源」 |

**建议**：

1. P1/P2 先做 **B**：动态表按最长前缀选择 target；`RpcRouter` 只需被包成一个
   `TrRouteTarget`，资源 target 与它在同一张表里共存。方法匹配可以后置——先用「更长前缀
   优先」，再逐步引入 `method` 参与匹配。
2. 如果业务确实要求「资源属于某个 service」（例如按 service 做配额、审计、生命周期），
   再评估 **C**：给 `TrRpcService` 或 `RpcRouter` 增加一个资源子表；不要一开始就把
   Router 变成 service 感知的类型。
3. **A 只作为过渡**：它无法表达 service 归属，长期会导致路径命名空间失控。

这也解释了为什么「资源语义放在 target 侧」是合适的：无论 A/B/C，router 都只需要把
`(method, path)` 交给 target；「这个 target 是 RPC router 还是 resource handler」由装配者
决定。

#### 建议：资源语义放在 target 侧

Router 不应该知道「什么是资源」；它只应该知道「这个 (method, path) 交给谁」。资源语义由
一个新的适配器承担：

```text
DynamicRouter (TrRouteTable)
  └─ RouteMatch<Arc<dyn TrRouteTarget<C>>>
        └─ ResourceHandler<C, R>  （实现 TrRouteTarget）
              ├─ 方法检查：HEAD / VIEW / POST / DROP / PUSH / PULL / CALL
              ├─ 标准状态码与 Allow
              ├─ HEAD 不写 body
              ├─ POST 的 Location
              ├─ PULL / PUSH 的 suffix 流
              └─ 收尾 / 取消 / drain
                    └─ 用户实现 TrResource<C>
```

用户只写业务方法（下面是**示意签名**，`...` 代表具体的可取消 future，不是可编译代码）：

```rust
pub trait TrResource<C: TrConfig>: Send + Sync {
    /// 本资源支持的方法集合；`HEAD` 默认总是可用。
    fn allowed_methods(&self) -> MethodSet;

    /// 查看元信息。
    fn head(&self, ctx: &mut ResourceCtx<'_, C>) -> ...;

    /// 读取内容。
    fn view(&self, ctx: &mut ResourceCtx<'_, C>) -> ...;

    /// 创建 / 上传。
    fn post(&self, ctx: &mut ResourceCtx<'_, C>) -> ...;

    /// 删除。
    fn drop(&self, ctx: &mut ResourceCtx<'_, C>) -> ...;

    /// 客户端推流。
    fn push(&self, ctx: &mut ResourceCtx<'_, C>) -> ...;

    /// 服务端拉流（持续写 suffix）。
    fn pull(&self, ctx: &mut ResourceCtx<'_, C>) -> ...;
}
```

> 草案；`drop` 作为方法名与 Rust 的 `Drop` 语义容易混淆，落地时可能改成 `delete` /
> `remove`。这里保留协议名是为了对照。

`ResourceCtx` 至少应提供：

- `method` / `location` / 剩余路径 / 路径参数；
- `headers`（可读写）；
- `tx` / `rx`；
- `reply_status_async` / `reply_body_async` / `reply_stream_async` / `close_async`；
- 本次请求的取消令牌，以及资源级的 drain 令牌。

#### 标准方法语义（建议）

| 方法 | 目标 | 成功 | 常见失败 | body / 流 |
| --- | --- | --- | --- | --- |
| `Head` | 元信息 | `200`，头描述资源 | `404` | **不写 body** |
| `View` | 读内容 | `200` + 内容 | `404` / `406` | 回复体；可选 suffix |
| `Post` | 创建 / 上传 | `201` + `Location`（新建）或 `200`（替换） | `400` / `405` / `409` | 请求体 |
| `Drop` | 删除 | `204`（或 `200` + 结果） | `404` / `409` | 无 |
| `Push` | 客户端推流 | `200` / `202` | `404` / `405` | 请求 suffix 流 |
| `Pull` | 服务端拉流 | `200` + 持续写 | `404` / `405` | 回复 suffix 流 |
| `Call` | RPC 调用 | `200` + 编码结果 | `4xx` / `5xx` | 现有 RPC 链不变 |

约定：

- `HEAD` 对任何「存在」的资源总是可用，即使 `View` 不支持；`Allow` 里应包含 `HEAD`；
- 不支持的方法回 `405`，并在头里给出 `Allow`。**`Allow` 目前不是标准头键**：需要决定是
  新增 `StdHeaderKey::Allow`（`0xD0–0xFF` 区段，具体编号待定），还是先用用户自定义键；
- `POST` 若创建了新资源，`Location` 指向新路径；由资源实现决定新路径，`ResourceHandler`
  负责写头；
- `DROP` 是「删除资源」，`remove` 是「撤销路由」，两者不是同一件事：一个资源可以先被
  `DROP`（业务上删除），再由应用撤销路由；
- `PULL` 成功后，`ResourceHandler` 不应立即 `close_channel_async`；它要持有 `tx` 持续写，
  直到资源结束、客户端半关闭或收到 drain 取消；
- `PUSH` 期间服务端从 `rx` 读 suffix，直到客户端半关闭。

#### 增删与生命周期

动态表的核心不是「一个 `RwLock<BTreeMap>`」，而是**删除时的语义**：

```text
Active ── remove()/Drop ──▶ Draining ── 所有 lease 释放 / 超时 ──▶ Removed
   ▲                             │
   └────── re-insert ────────────┘（策略待定）
```

- 每次命中产生一个 `RouteLease`（持有 `Arc` target + 资源级取消令牌）；
- `remove` 立即让**新的**匹配跳过该路径，但已经发出的 lease 继续运行；
- `remove` 可以向该资源的 drain 令牌发取消；`PULL` / `PUSH` 应协作退出；
- 超过 grace period 仍未退出时，框架可以强制 `RESET`（drop `tx/rx`）；
- 重新登记同一路径：建议默认 `Err`，或返回旧值并要求调用者显式替换；不要在 draining
  期间静默覆盖；
- `RouteGuard`（RAII）可以让「应用忘记 remove」在 drop 时自动撤销；但 guard 与 `Arc` 的
  生命周期要设计清楚，避免表自身持有唯一强引用。

#### 路径参数

如果动态资源需要 `/items/{id}`，匹配结果必须携带捕获值：

```rust
pub struct RouteMatch<T> {
    pub target: T,
    pub matched_len: usize,
    pub params: SmallVec<[RouteParam; 4]>, // 草案
}
```

但这是**可以推迟**的能力：第一版动态表可以只支持「精确路径 + 前缀回退」，与现有语义一致；
路径参数作为 P2/P3 的增量，不要和动态增删绑在一起。

### 5.4 serving 层还需要什么

Router 不能单独解决长流与撤销；以下问题在 `server_.rs`：

1. **串行 accept**
   `serve_listener_async_` 在循环里 `await` `serve_channel_async_`。任何长流 handler 都会
   阻塞后续 channel。需要要么：
   - 注入 spawner（推荐）：`MptpServer` 不依赖具体 runtime，由调用者提供
     `TrChannelSpawner`；
   - 或要求长流服务自己用 `serve_channel_async` + 外部 task（现状，不友好）。
2. **单 channel 错误杀死 accept 循环**
   当前 `?` 直接向上传播。应改为：记录错误、继续 accept；只有 listener 本身失败才退出。
3. **没有优雅关闭**
   需要一个 `ServeHandle`：停止 accept → 向所有 lease 发取消 → 等待 in-flight（带超时）→
   强制 reset。
4. **`NotFound` 没有协议化**
   顶层 router 未命中时，应能写一个 `404`（无 body 或纯文本），再按序收尾；而不是把
   `ServeError` 抛给 listener。
5. **`RouterCtx` / `RpcServiceCtx` 太瘦**
   需要携带共享注册表句柄、会话/连接上下文、以及将来的资源管理器；两者目前都是 ZST，
   扩展时要注意调用形状不变。
6. **`close_channel_async` 的定位**
   它是「一问一答」的收尾；长流需要 `finish_stream_async`（半关闭 tx、等待对端、释放 rx）
   与 `abort_stream`（立即 reset）两个不同入口。不要把一个函数复用到所有场景。
7. **没有观测**
   至少需要每路由的请求计数、活跃流计数、拒绝原因；不要为了观测引入中间件链，放在
   target / server 的生命周期钩子里即可。
8. **一问一答与长流并不冲突，但会话复用未定**
   `server_.rs` 里已有「一条子流处理一个请求」的 TODO。对 `Pull` 来说，一条 channel 承载
   一次长会话恰好是合理的；真正缺的是并发接入与取消，不是「同一条 channel 上循环处理」。
   后者（keep-alive / 多请求复用）可以继续推迟。

## 6. 目标架构草案

### 6.1 分层

```text
┌──────────────────────────────────────────────────────────────┐
│ 应用（service / resource 开发者）                            │
│   Router::call(...) / DynamicRouter::insert(...)             │
│   TrResource 实现 / RpcRouter::add_service(...)              │
├──────────────────────────────────────────────────────────────┤
│ mptp_smux::serving::router                                   │
│   contract_: TrRouteMatcher / TrRouteTable / TrRouteTarget   │
│   static_:   Router<C, RList>（现有）                        │
│   dynamic_:  DynamicRouter<T> / RouteGuard（新增）           │
│   dispatch_: tlist 递归 / EitherMayCancel                    │
├──────────────────────────────────────────────────────────────┤
│ mptp_smux::serving::server                                   │
│   MptpServer：解码 → 匹配 → 交给 target → 跟踪 / 关闭        │
├──────────────────────────────────────────────────────────────┤
│ abs_mptp / abs_smux                                          │
└──────────────────────────────────────────────────────────────┘
```

### 6.2 契约草案

见 5.2 的 `TrRouteMatcher` / `TrRouteTable` / `TrRouteTarget`。补充两个决定：

- **静态路径不引入动态开销**：`Router<C, RList>` 继续用具体 handler 类型与
  `EitherMayCancel`。若把它硬接进 `TrRouteMatcher`，`Target` 只能取 `Self` 或 `&Self`：
  取 `Self` 时 `match_route(&self)` 无法交出一个 `Self` 值（既不能移动也不能复制）；取
  `&Self` 时返回值又被绑回 `&self`，与动态实现的 `Arc` 不同型。因此静态实现应保留
  **引用或轻量句柄**的路径，而不是强行统一。

  这是一个真实的张力：`match_route` 若返回 `T`（值），`Router` 无法从 `&self` 复制自身；
  若返回 `&T`，动态实现又持不了锁。可选方案：

  1. `Target = Arc<dyn ...>` 只用于动态；静态 `Router` 继续实现旧的 `TrPathRouter`，
     `MptpServer` 用两个构造函数区分（`new` 接受 `TrPathRouter`，`with_table` 接受
     `TrRouteMatcher`）；
  2. `match_route` 返回 `RouteMatch<Self::Target>`，并允许 `Target: Clone`；静态实现用
     `&Self` 或轻量 `RouterRef<'f>`，动态实现用 `Arc`；
  3. 接受统一 `Arc`，静态路径也付一次原子递增（通常可接受，但违背当前零开销目标）。

  **建议选 1**：不为动态能力破坏静态路径；两套入口共享 `MptpServer` 的内部状态机。

- **方法匹配是可选能力**：`match_route` 接收 `method`，但静态 `Router` 的实现可以忽略它。
  这样「是否按方法分派」由实现决定，而不是由框架强制。

### 6.3 静态路径保持不变

- 现有 `Router<C, RList>` 的行为、类型与公开路径不变；
- 它继续实现 `TrPathRouter`，继续支持 `MptpServer::new`；
- 新增的 `TrRouteMatcher` 通过适配器（如 `StaticMatcher<R>`）接入动态服务器入口；
- `TrPathRouterMut` 在下一个 breaking 版本删除，或标记 `#[deprecated]` 并给出替代。

### 6.4 动态路径

```rust
pub struct DynamicRouter<C: TrConfig> {
    routes: RwLock<BTreeMap<RouteKey, Arc<dyn TrRouteTarget<C>>>>,
    // 可按需加：generation / 计数 / draining 集合
}

impl<C: TrConfig> DynamicRouter<C> {
    pub fn new() -> Self;

    /// 登记或替换；返回旧目标。`RouteGuard` 在 drop 时撤销（可选）。
    pub fn insert(
        &self,
        path: &str,
        target: Arc<dyn TrRouteTarget<C>>,
    ) -> Result<Option<Arc<dyn TrRouteTarget<C>>>, RouteTableError>;

    /// 撤销；已发出的 lease 不受影响，新请求立即 404。
    pub fn remove(&self, path: &str) -> Option<Arc<dyn TrRouteTarget<C>>>;
}
```

使用形状（草案）：

```rust
let table = Arc::new(DynamicRouter::<SrvCfg>::new());

// 应用侧：运行期添加一个可 Pull 的遥测资源。
table.insert(
    "/feeds/telemetry",
    Arc::new(ResourceHandler::new(TelemetryFeed::new())),
)?;

// server 持有同一张表的句柄。
let server = MptpServer::<SrvCfg, _>::with_table(table.clone());

// 之后任意时刻：撤销（新请求 404，长流收到 drain 取消）。
table.remove("/feeds/telemetry");
```

关键不变量：

1. `insert` / `remove` 与 `match_route` 的并发安全由表内部保证；
2. 匹配路径上的锁**不得跨 `await`**：`match_route` 只把 `Arc` 交出去；
3. 表不拥有「请求生命周期」；请求由 `RouteLease` 持有；
4. `remove` 不阻塞等待长流；drain 是异步的，有超时。

### 6.5 生命周期

```text
insert ──▶ Active ──remove / guard drop──▶ Draining ──lease=0 / timeout──▶ Removed
              ▲                                 │
              └────────── re-insert ────────────┘（默认拒绝，需显式替换）
```

- `RouteLease`：命中时创建，持有 `Arc<dyn TrRouteTarget<C>>` + 资源级取消令牌；
- `Draining` 时：匹配跳过；向 lease 的令牌发取消；等待 `PULL` / `PUSH` 协作退出；
- 超时：强制 drop `tx/rx`（发 `RESET`），记录一条告警；
- `Drop` 方法（客户端语义）与 `remove`（路由撤销）解耦：业务删除不自动撤销路由，
  除非应用显式这样做。

### 6.6 方法语义

- 方法检查放在 `ResourceHandler`，不在 router；
- `HEAD` 默认由 `ResourceHandler` 基于 `allowed_methods` + 资源的 `head` 实现；
- `405` 的 `Allow` 由 `allowed_methods` 生成；
- `PULL` / `PUSH` 由 `ResourceHandler` 提供流式 helper，避免每个资源重复写收尾；
- `CALL` 继续走 `RpcRouter`，两条链可以在同一个 `DynamicRouter` 下共存。

### 6.7 文件布局

```text
mptp_smux/src/serving/
├── mod.rs
├── router/
│   ├── mod.rs
│   ├── contract_.rs
│   ├── static_.rs
│   ├── dispatch_.rs
│   ├── dynamic_.rs
│   ├── resource_.rs        # TrResource / ResourceHandler / ResourceCtx
│   └── error_.rs
├── cancel_future_.rs
├── config.rs
├── prep_ctx_.rs
└── server_.rs
```

`rpc_core_v1` 侧同样拆契约与实现；`rpc_router_trie` 保持不变，它是「可选实现 crate」的

## 7. 路线图

### P0：文档与结构（无行为变更）

- 写本文（已完成）并把稳定部分提升为 `router/mod.rs` 的 rustdoc；
- 拆分 `router_.rs` 为 `contract_` / `static_` / `dispatch_` / `error_`；
- 拆分 `rpc_core_v1` 的 `router_.rs` / `rpc_router_.rs`；
- 公开路径不变，测试全部通过。

**验收**：`cargo check` / `clippy` / `test` 通过；`cargo doc` 无新增警告；`git diff` 只包含
移动与重导出。

### P1：动态契约与擦除层

- 新增 `TrRouteMatcher` / `TrRouteTable` / `TrRouteTarget` / `RouteMatch`；
- 新增 `PathOnly<R>`（旧 `TrPathRouter` → 新 matcher 的适配器）；
- 新增 `DynamicRouter<T>`（先只支持精确路径 + 前缀回退，不做参数）；
- `MptpServer` 新增 `with_table`（不破坏 `new`）；
- 解决取消令牌的对象安全形态（见 5.2）。

**验收**：一个 e2e：服务启动后插入两条资源路由，客户端分别访问；删除一条后新请求 404；
旧连接不受影响。静态 `Router` 的性能与行为不变。

### P2：资源语义与标准方法

- 新增 `TrResource` / `ResourceCtx` / `ResourceHandler`；
- `HEAD`、`405 + Allow`、`POST → 201 + Location`、`DROP` 的默认实现；
- `VIEW` 的 body 写出 helper；
- 决定 `Allow` 是标准头还是用户键。

**验收**：同一资源上七种方法的矩阵测试；`HEAD` 不写 body；不支持的方法一定 405 且带
`Allow`；`POST` 创建后 `Location` 可被客户端跟随。

### P3：长流与生命周期

- 新增 `TrChannelSpawner`，`MptpServer` 可注入；accept 循环隔离单 channel 错误；
- `PULL` / `PUSH` 的 suffix 流 helper（写、读、结束、abort）；
- `RouteLease` / drain / grace period / 强制 reset；
- `ServeHandle` 优雅关闭；
- `NotFound` 协议化为 404。

**验收**：两条并发 `PULL` 长流 + 普通 `CALL` 不互相阻塞；删除正在 `PULL` 的资源后，客户端
在 grace period 内收到流结束或 reset，服务端不泄漏 channel；关闭服务端时 in-flight 请求
在超时内退出。

### P4：观测、鉴权、文档

- 每路由计数 / 活跃流 / 拒绝原因；
- per-target 的鉴权钩子（不是中间件链）；
- 面向 service 开发者的 `docs/router-guide.md`；
- 把本文的「现状」部分更新为「已实现」。

**非目标**（本路线明确不做）：

- 通用中间件链：与「handler 拥有回复权」的契约冲突；
- HTTP 兼容层：MPTP 的路径 / 方法 / 头是自有协议，不追求 HTTP 语义的每一个细节；
- 持久化路由表 / 跨进程服务发现：这是应用层或独立 crate 的事；
- 用 `dyn` 替换所有静态路径：静态路径的零装箱是刻意保留的优势。

## 9. 测试与验收建议

### 9.1 单元测试

- 匹配：最长前缀、完整段、重复前缀、空前缀、方法过滤、`PathOnly` 适配；
- 动态表：并发 insert / remove / match；draining 期间新请求 404；re-insert 冲突策略；
- 资源：`HEAD` 不写 body；不支持的 method 返回 405 + `Allow`；`POST` 写 `Location`；
- 生命周期：lease 计数、grace timeout、强制 reset。

### 9.2 集成 / e2e

- 服务运行中插入资源 → 客户端 `VIEW` 成功；
- 删除资源 → 新请求 404，旧长流收到结束；
- 两条 `PULL` + 一条 `CALL` 并发，互不阻塞；
- `PUSH` 客户端半关闭后服务端正确结束；
- 服务端优雅关闭：不再 accept，in-flight 在超时内完成或取消；
- 静态 `Router` 的回归：现有 `mptp_cs_smoke` 的 11 条 RPC 仍通过。

### 9.3 约束

- 单元测试设置不超过 1 分钟超时；全量测试不超过 5 分钟（按仓库 `AGENTS.md` 第 12 条）；
- 新增测试使用中英双语文档注释；
- 不在库代码里 `unwrap()` / `expect()`（测试除外）；
- 新公开项必须有 `///` 文档与可编译示例。

## 10. 开放问题

1. **方法匹配放在哪一层？**
   顶层 `match_route(method, path)` 可以按方法选 target，但会让静态 `Router` 的签名变化；
   另一种是顶层只按路径，`ResourceHandler` 内做方法检查。建议：契约接收 `method`，实现可
   忽略；资源方法检查放 `ResourceHandler`。需要确认是否接受「匹配层与方法层各检查一次」的
   可能性（避免双重 405）。
2. **`Target` 用 `Arc<dyn ...>` 还是泛型？**
   动态表必须擦除；静态表必须零成本。是否接受两套入口（`new` / `with_table`）？
3. **取消令牌的对象安全形态**
   是新增 `TrErasedCancel`，还是在进入擦除层前把具体 token 捕获进 boxed future？后者更简单，
   但要求所有动态 target 的 future 都是 `Send + 'static` 或有明确生命周期。
4. **`Allow` 头**
   新增标准键，还是先用用户自定义键？如果新增，编号定在 `0xD0–0xFF` 的哪一位？
5. **`POST` 的创建语义**
   谁分配新资源 id？`Location` 是绝对路径还是相对路径？创建失败时是否回滚？
6. **`DROP` 的级联**
   删除父资源时，子资源是 `409` 拒绝、级联删除，还是先 drain？需要协议层约定。
7. **`HEAD` 与 `VIEW` 的关系**
   `HEAD` 是否自动复用 `VIEW` 的元信息计算？如果资源只实现 `VIEW`，是否自动提供 `HEAD`？
8. **删除的 grace period**
   默认多长？是否可配置？超时后强制 `RESET` 是否会让客户端误判为网络错误？
9. **动态表的位置**
   放在 `mptp_smux` 内核，还是独立 crate（如 `mptp_router_dynamic`）？如果依赖只有
   `std::sync::RwLock`，放内核更便于使用；如果引入无锁 trie / 参数匹配，独立 crate 更合适。
10. **是否保留 `Router` 的 `tlist` 实现**
    长期看，动态表 + 资源语义会覆盖大部分场景；但静态零装箱仍有价值。建议保留，并明确
    「静态 / 动态」两种装配风格。
11. **`rpc_core_v1` 的两代 router 是否收敛**
    队列链与内联链长期并存会增加文档与测试成本；是否在动态 router 落地后，把队列链标记为
    「高级 / 可选」并停止扩展？

## 11. 附：现状能力清单

| 场景 | 今天能否做到 | 做法 |
| --- | --- | --- |
| 单 handler 服务 | ✅ | 恒等 `TrPathRouter` |
| 多 RPC interface | ✅ | `Router::call` + `RpcRouter::add_service` |
| 自定义路径匹配 | ⚠️ | 实现 `TrPathRouter`，但受单一 `Handler` / 借用返回限制 |
| 有界队列 / 自定义 worker | ✅ | `ServiceRoute` + `rpc_router_trie` |
| 运行期加路由 | ❌ | 无 API |
| 运行期删路由 | ❌ | 无 API |
| 非 `Call` 方法 | ⚠️ | 自己写 `TrReqHandler`，手工处理状态码 / body / 流 |
| `HEAD` 元信息 | ❌ | 自己写 |
| `POST` 创建 + `Location` | ❌ | 自己写 |
| `DROP` 删除 | ❌ | 自己写 |
| `PULL` 长流 | ⚠️ | handler 持有 `tx` 自己写；需自行 spawn，否则阻塞 accept |
| `PUSH` 客户端推流 | ⚠️ | handler 从 `rx` 自己读 |
| 优雅关闭 | ❌ | 只能 drop listener / 外部取消 |
| 观测 / 鉴权 | ❌ | 每个 handler 自己做 |

## 12. 写给 service 开发者的三句话

1. **今天**：把 router 当成「路径前缀 → 一个 handler」的静态表；handler 负责写回复与收尾，
   不要在 router 里找中间件。
2. **将来**：把资源当成「有方法集合和生命周期的 target」；router 只匹配，`ResourceHandler`
   负责标准语义，`MptpServer` 负责并发与关闭。
3. **现在能做的准备**：把业务资源的「方法处理」与「路径注册」分开写；资源实现不要依赖
   `Router` 的具体类型，只依赖 `TrReqHandler` / 将来的 `TrResource` 契约，这样动态
   能力落地时迁移成本最小。
