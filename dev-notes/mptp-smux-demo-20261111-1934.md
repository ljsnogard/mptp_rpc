## 0. 目的：这是 `mptp_smux` 的 API 压测场，不是太阳系模拟器

`mptp_smux_v1_demo` 重写后的第一目标不是「做一个好看的太阳系」，而是：

> **用一段真实的、多客户端、长连接、持续广播的业务，把 `mptp_smux` 当前提供的 API
> 全部用上；凡是 demo 为了实现业务而不得不写的传输层代码，都是 `mptp_smux` API 的
> 缺口，应被记录并优先补在 `mptp_smux` 里，而不是在 demo 里绕过去。**

因此本 demo 的代码取舍标准是：

- 能直接用 `mptp_smux` 的公开 API，就不自己写；
- 必须自己写的，只能是**业务层**：场景模型、行星参数、事件、帧格式、订阅注册表、
  Bevy ECS / 渲染；
- 如果发现 `mptp_smux` 缺一个原语，先在本文档的“API 缺口”一节记录，评估最小补充，
  再实施；不在 demo 里复制 `mptp_smux` 的内部逻辑。

本 demo 要展示的 `mptp_smux` 能力至少包括：

- 七种 AccessMethod 中的 `Pull` / `Call` / `Head` / `View` 的自然使用；
- `RequestBuilder` 的方法糖、`body_bytes`、`send_async`；
- `Response` 的 `status` / `headers` / `body_async` / `suffix_async`；
- 服务端 `MptpServlet` 的 `listen_async` / `accept_async` / `serve_session_async`；
- `TrServeHandler::allowed_methods` 与 `405`；
- `ServingSession::req_body_async` / `response`；
- `ResponseBuilder` 的定长体、无体、后缀流；
- 服务端持续后缀流（本次需要补的 `ResponseStream`）；
- 取消传播、错误分类、收尾次序；
- 一条连接上多个并发 session（服务端每连接一个 `MptpServlet`，客户端控制调用与订阅并发）。

## 1. 已确认的约束

| 约束 | 决定 |
| --- | --- |
| 客户端 | **Bevy** 直接渲染，不使用网页 / WASM |
| 传输 | 客户端与服务端**直接 MPTP over TCP/smux**，禁止 HTTP / WebSocket 网关 |
| 运行时 | 两端都使用 `abs_art-facade` + **compio** |
| 线程 | 每个进程**最多两个线程** |
| 打包 | Bevy 客户端按 **feature-gated binary** 设计 |
| 控件 | `bevy_egui` 滑杆 |
| 负载编解码 | **denco**（`abs_denco` / `mp_denco` / `denco_macro`） |
| 服务端连接 | **每客户端一条 MPTP 连接** |
| 场景 | 太阳 + 每个客户端新增一颗行星；摄像机锁定自己的行星；可改自身公转 / 自转速度 |
| 服务端职责 | 不渲染、不算显示效果；只维护场景参数并以 MPTP 后缀流广播 |

## 2. 为什么 Bevy 直连更适合本 demo

相比网页 + WebSocket 网关：

| 维度 | 网页 + 网关 | Bevy 直连 |
| --- | --- | --- |
| 架构层数 | 浏览器 → WS → gateway → MPTP → server | Bevy → MPTP → server |
| `mptp_smux` 暴露 | 网关把 `MptpClient` 藏在后面 | 客户端直接使用 `MptpClient` / `Response` |
| 业务类型 | Rust ↔ JSON ↔ JS 翻译 | 两端共享 Rust + denco 类型 |
| 客户端身份 | 逻辑 clientId 放消息体，需防冒充 | **连接即身份** |
| 多连接 | 一条网关连接多 session | 每客户端一条连接，服务端多连接 |
| CI | WebSocket headless | 需要额 headless smoke 客户端 |
| 构建成本 | 轻 | Bevy 较重，需要 feature gate |

结论：**演示 `mptp_smux` API 时，Bevy 直连更直接**；主要成本是 Bevy 构建与线程约束，
而不是传输层。

## 3. 总体架构

```text
┌──────────────────────────────┐        MPTP over TCP/smux        ┌──────────────────────────────┐
│ Bevy 客户端 A                │ ◀──────────────────────────────▶ │ scene-server                 │
│  - Bevy 主线程（渲染 / UI）  │      一条连接 / 一个 MptpServlet  │  - compio 单线程             │
│  - compio 网络线程           │                                  │  - 每连接一个 MptpServlet     │
│  - 摄像机跟随自己的行星      │                                  │  - SceneHub / PlanetRegistry │
└──────────────────────────────┘                                  │  - 不渲染、不算轨道位置       │
┌──────────────────────────────┐        MPTP over TCP/smux        │                              │
│ Bevy 客户端 B                │ ◀──────────────────────────────▶ │                              │
│  ...                         │                                  │                              │
└──────────────────────────────┘                                  └──────────────────────────────┘
```

### 3.1 进程与线程

| 进程 | 线程 | 职责 |
| --- | --- | --- |
| `scene-server` | **1 个 compio 线程** | TCP accept、所有连接、所有 session、场景广播 |
| `scene-client`（Bevy） | **Bevy 主线程 + 1 个 compio 网络线程** | 渲染 / UI / ECS；MPTP 连接与订阅流 |
| `scene-smoke`（headless） | **1 个 compio 线程** | e2e 用的无渲染客户端，复用同一套 `SceneClient` |

服务端只有一个 compio 线程：所有连接、`MptpServlet`、handler、`ResponseStream` 都在
同一线程上。若以后需要更多并行度，再加线程；本 demo 不超。

Bevy 客户端：

- Bevy 主线程只做 ECS / 渲染 / `bevy_egui`；
- 网络线程创建 compio runtime，持有 `MptpClient`、订阅 `Response`、控制请求；
- 两个线程之间只传普通的 `NetCommand` / `NetEvent`（不含任何 MPTP / compio 类型）。

### 3.2 为什么必须这样分线程

`buffex_compio_adapt` 的 `BuffRead` / `BuffWrite`：

- 必须在**正在运行的 compio runtime 内**构造；
- 类型是 `!Send`；
- 不能在别的线程 / 别的 runtime 上使用。

因此**整个 MPTP 栈必须固定在一条 compio 线程上**：

- 服务端：一个 compio 线程承载所有连接；
- 客户端：一个 compio 网络线程承载连接；
- Bevy 主线程不能直接碰 `BuffRead` / `BuffWrite` / `MptpSession`。

这也正好满足“最多两个线程”：Bevy 主线程 + compio 网络线程。

### 3.3 Bevy 内部线程

Bevy 自身可能创建渲染 / 任务线程。为了守住“最多两个线程”：

- `bevy` 依赖使用 `default-features = false`，不启用 `multi_threaded`；
- 不启用 `pipelined_rendering`；
- `TaskPoolPlugin` 使用单线程配置（或等价配置），关闭后台 task pool；
- 不在 demo 代码里再 `std::thread::spawn` 其他业务线程；
- 验收时用线程名 / `ps -T` 记录实际线程数；如果 Bevy 仍有内部引擎线程，
  在 README 中明确它们属于引擎，业务线程仍然只有两个。

## 4. MPTP 映射

### 4.1 方法选择

| 路径 | 方法 | 用途 |
| --- | --- | --- |
| `/scene` | `Head` | 读取场景能力 / 版本（无体），也用于展示 `Head` 的无体语义 |
| `/scene` | `View` | 一次性读取完整场景快照（有体），用于调试 / 重连后手动同步 |
| `/scene` | `Pull` | **加入 + 订阅**：长生命周期请求，服务端持续写后缀流 |
| `/scene/update` | `Call` | 修改自己的公转 / 自转速度，回复 ack |
| 其他 | 任意 | `405` + `Allow` 由 `allowed_methods()` 统一处理 |

说明：

- 主交互只自然使用 `Head` / `View` / `Pull` / `Call` 四种；
- 不为了“覆盖七种方法”硬造 `Post` / `Push` / `Drop` 的业务；如果评审要求，
  可以后续增加 `Drop /scene/leave` 或 `Push /scene/camera`，但默认不做；
- `Pull` 按协议语义就是“服务端持续提供数据，成功时服务端必然有后缀流”，最适合订阅。

### 4.2 加入 + 订阅：`Pull /scene`

客户端：

```text
Pull /scene
请求体: JoinRequest { display_name, color_hint? }
```

服务端 `SceneHandler`：

1. 读取 `JoinRequest`；
2. 用当前连接的 `connection_id` 创建行星；
3. 写回复前缀（无回复体）；
4. 打开后缀流；
5. 第一帧发送 `Welcome`：
   - `client_id` / `planet_id`
   - 当前全部行星
   - `epoch_ms`
   - `scene_version`
6. 之后持续写场景事件帧。

客户端：

```text
client.pull("/scene")
      .body_bytes(join_bytes)
      .send_async()
      .await
→ Response::status/headers
→ Response::suffix_async()
→ 循环 read_frame
```

### 4.3 修改自身行星：`Call /scene/update`

```text
Call /scene/update
请求体: UpdateRequest { orbit_speed, spin_speed }
回复体: UpdateAck { version }
```

服务端：

1. 从 `SceneHandler` 的 `own_planet` 取当前连接的行星；
2. 校验范围；
3. 更新 `PlanetRegistry`；
4. `scene_version += 1`；
5. 广播 `PlanetUpdated`；
6. 用 `ResponseBuilder::sized_async` 写 ack。

**不**在请求体里传 `client_id`：直连方案中连接即身份，避免冒充。

### 4.4 快照 / 健康检查

- `Head /scene`：
  - 无请求体 / 无回复体；
  - 回复头里带 `scene_version` 或自定义能力头；
  - 用于展示 `Head` 不写体。
- `View /scene`：
  - 无请求体；
  - 回复体是完整 `SceneSnapshot`（denco）；
  - 用于调试、重连或手工同步。

### 4.5 离开

- Bevy 客户端退出 → MPTP 连接断开；
- 服务端 `Pull` 流写入失败 / 读到 EOF；
- `SceneHandler` 删除自己的行星；
- `SceneHub` 广播 `PlanetRemoved`；
- 其他客户端看到行星消失。

## 5. 服务端设计

### 5.1 compio accept 循环

`scene-server` 只有一个 compio 线程：

```text
compio Runtime
  └─ TcpListener accept loop
       ├─ 为每个 TcpStream 创建 BuffRead / BuffWrite（必须在 runtime 内）
       ├─ 建立 MuxConnection（smux_v1）
       ├─ bind dock（例如 1）
       ├─ 分配 ConnectionId
       ├─ 创建 SceneHandler { hub, registry, own_planet }
       ├─ 创建 MptpServlet<SceneCfg, SceneHandler>
       └─ spawn 本地任务：listen_async + accept_async + serve_session_async
```

所有连接、session、handler 都在同一线程；`compio::runtime::spawn` 不要求 `Send`，
正好承载 `!Send` 的 compio 适配器与 `MptpSession`。

### 5.2 每连接一个 `SceneHandler`

```rust
struct SceneHandler {
    connection_id: ClientId,
    hub: Rc<RefCell<SceneHub>>,
    registry: Rc<RefCell<PlanetRegistry>>,
    own_planet: Cell<Option<PlanetId>>,
}
```

- `connection_id` 在 accept 时分配；
- `own_planet` 在 `Pull` 加入时设置；
- `Call /scene/update` 只操作 `own_planet`；
- 连接断开 / 订阅流结束时清理自己的行星。

`TrServeHandler` 实现：

```rust
impl TrServeHandler<SceneCfg> for SceneHandler {
    type Err = SceneError;

    fn allowed_methods(&self) -> MethodSet {
        MethodSet::HEAD | MethodSet::VIEW | MethodSet::PULL | MethodSet::CALL
    }

    async fn handle_async(&self, method, session) {
        match method {
            Head => ...
            View => ...
            Pull => ...
            Call => ...
            _ => 405 由框架处理，不会进入这里
        }
    }
}
```

未知路径在 handler 内写 `404`；`405` 由 `allowed_methods()` 和框架统一处理。

### 5.3 场景广播：单线程内不需要锁

因为所有连接都在同一个 compio 线程，`SceneHub` / `PlanetRegistry` 不需要 `Mutex`：

```rust
struct SceneHub {
    // 每个订阅一个 flume sender；帧已经编码为 Arc<[u8]>
    subscribers: RefCell<Vec<(SubscriptionId, flume::Sender<Arc<[u8]>>)>>,
}

struct PlanetRegistry {
    planets: BTreeMap<PlanetId, Planet>,
    next_planet: u64,
    version: u64,
}
```

广播流程：

1. 更新 registry；
2. `version += 1`；
3. 用 denco 编码一次 `SceneEvent`；
4. 加上长度前缀，得到一帧 `Arc<[u8]>`；
5. 对每个 subscriber `try_send`：
   - 成功：其订阅任务会被唤醒；
   - 满 / 已关闭：移除该 subscriber，关闭它的流（慢客户端策略）。

使用 `flume` 的理由：

- 已有依赖链里就有 `flume`（`smux_v1` 使用）；
- `recv_async` 可在 compio 线程上等待；
- bounded / `try_send` 的慢客户端策略简单；
- 不需要引入 tokio。

### 5.4 `Pull` handler 与 `ResponseStream`

这是 demo 唯一需要 `mptp_smux` 补 API 的地方。

当前 `ResponseBodyWriter::suffix_async` 接受有限 `TrBuffRead`，写到 EOF 就结束；广播需要
**无限 / 可追加**的后缀流。推荐先给 `mptp_smux` 加：

```rust
impl<C: serving::config::TrConfig> ResponseBuilder<'_, C> {
    pub fn suffix_stream_async(self) -> ResponseSuffixStreamAsync<'_, C>;
}

pub struct ResponseStream<'a, C> { ... }

impl<'a, C> ResponseStream<'a, C> {
    pub async fn write_chunk_async(&mut self, bytes: &[u8]) -> Result<(), ServeError>;
    pub async fn finish_async(self) -> Result<(), ServeError>;
}
```

`Pull` handler 的形状：

```rust
async fn handle_pull_(session: &mut ServingSession<SceneCfg>) -> Result<(), ServeError> {
    let join = decode_body_(session.req_body_async().await?).await?;
    let welcome = handler.join_(join)?;

    let mut stream = session
        .response(Status::Ok)
        .suffix_stream_async()
        .await?;

    stream.write_chunk_async(&encode_frame_(&SceneEvent::Welcome(welcome))?).await?;

    let (tx, rx) = flume::bounded(K_SUB_QUEUE);
    handler.hub.add_subscriber(tx);

    while let Ok(frame) = rx.recv_async().await {
        stream.write_chunk_async(&frame).await?;
    }

    stream.finish_async().await?;
    handler.leave_();
    Result::Ok(())
}
```

业务侧只看到：

- `req_body_async` 读入；
- `response(...).suffix_stream_async` 开流；
- `write_chunk_async` 写帧；
- `finish_async` 收尾。

不需要 `take_parts`，不需要碰 `ChannelTx` / `mptp_wire` 写循环。

### 5.5 慢客户端策略

- 每个订阅一个 bounded `flume`（例如 64 帧）；
- 广播用 `try_send`，不 await；
- 满 / 断开：移除订阅，关闭该 `ResponseStream`；
- 客户端重连后通过 `Welcome` 拿新快照；
- 不阻塞其他客户端。

这是应用层策略，不塞进 `mptp_smux`。

## 6. 客户端设计（Bevy + compio）

### 6.1 线程模型

```text
Bevy 主线程
  ├─ 每帧 drain event_rx（flume::Receiver<NetEvent>）
  ├─ 更新 ECS / 渲染 / bevy_egui
  └─ 控件变化时 cmd_tx.send(NetCommand::Update { ... })
             │
             ▼
compio 网络线程
  ├─ 创建 compio Runtime / LocalScope
  ├─ 建立 MptpClient
  ├─ 发起 Pull /scene（join + subscribe）
  ├─ 循环读后缀帧 → event_tx.send(NetEvent)
  ├─ 处理 NetCommand::Update → Call /scene/update
  └─ 退出时关闭连接
```

跨线程只传：

```rust
enum NetCommand {
    Update { orbit_speed: f32, spin_speed: f32 },
    Shutdown,
}

enum NetEvent {
    Connected { client_id, planet_id, epoch_ms, planets, version },
    PlanetAdded(Planet),
    PlanetUpdated(Planet),
    PlanetRemoved(PlanetId),
    Ack { version },
    Error(String),
    Disconnected,
}
```

`NetEvent` / `NetCommand` 不含任何 `MptpSession` / `Response` / `ChannelTx` / compio 类型，
因此可以安全跨线程。

### 6.2 网络线程

- 创建 compio runtime；
- 在 runtime 内取 `abs_art_facade::CompioRuntime::current()` / `local_scope()`；
- 建立 smux 连接与 `MptpClient`；
- `Pull /scene`：
  - 发送 `JoinRequest`；
  - 读回复前缀；
  - 读第一帧 `Welcome`；
  - 循环 `read_frame`，解码为 `SceneEvent`，转成 `NetEvent` 发给 Bevy；
- 控制命令：
  - 收到 `Update` 时发 `Call /scene/update`；
  - 读 ack body；
  - 发 `NetEvent::Ack`（可选，主要靠广播更新 UI）；
- 退出：
  - `Shutdown` → 取消订阅 / drop `Response` / 关闭连接。

订阅 `Pull` 和 `Call` 控制请求可以并发；`MptpClient` 共享连接，控制调用开新 session。
网络线程可以用 `futures::join!` / 本地 `compio::runtime::spawn` 组织。

### 6.3 Bevy 插件

```text
MptpNetPlugin
  - 启动网络线程
  - 资源：NetHandle { cmd_tx, event_rx }

ScenePlugin
  - 资源：SceneState { my_planet, planets, epoch, version }
  - 系统：
      drain_net_events
      apply_scene_events
      send_update_commands
      update_orbits
      follow_my_planet
      controls_ui
```

`drain_net_events` 每帧 `try_recv`，把事件写入 Bevy 的 `EventWriter` 或直接更新资源。

### 6.4 Bevy 场景

- 太阳：自发光球 + `PointLight`；
- 行星：球体 + 颜色 + 轨道环（`Gizmos` 画圆即可）；
- `PlanetVisual` 组件保存轨道参数；
- `MyPlanet` 标记自己的行星；
- `CameraFollow` 组件 / 资源指向自己的行星实体；
- 每帧：

```text
elapsed = now - epoch
angle = orbit_phase + orbit_speed * elapsed
planet_pos = (cos(angle) * orbit_radius, 0, sin(angle) * orbit_radius)
planet_rotation = spin_phase + spin_speed * elapsed
camera_pos = planet_pos + camera_offset
camera.look_at(planet_pos)
```

因此：

- 自己的摄像机跟随自己的行星；
- 其他行星按相同参数计算位置，自然可见；
- 服务端完全不参与位置计算。

### 6.5 `bevy_egui` 控件

- 面板显示：
  - 自己的 `client_id` / `planet_id`；
  - 当前公转 / 自转速度；
  - 其他行星数量。
- 两个滑杆：
  - 公转速度 `orbit_speed`；
  - 自转速度 `spin_speed`。
- 值变化时：
  - 本地立即更新 `PlanetVisual`（视觉预览）；
  - 发送 `NetCommand::Update`；
  - 服务端广播的 `PlanetUpdated` 到达后以服务端值为准（版本号 / 时间戳可防止旧帧覆盖新值）。

## 7. 数据与 denco 编解码

### 7.1 类型

```rust
struct JoinRequest { display_name: String, color_hint: Option<u32> }
struct UpdateRequest { orbit_speed: f32, spin_speed: f32 }
struct UpdateAck { version: u64 }

struct Planet {
    id: PlanetId,
    owner: ClientId,
    name: String,
    color: u32,
    orbit_radius: f32,
    orbit_phase: f32,
    orbit_speed: f32,
    spin_phase: f32,
    spin_speed: f32,
}

enum SceneEvent {
    Welcome(Welcome),
    PlanetAdded(Planet),
    PlanetUpdated(Planet),
    PlanetRemoved(PlanetId),
    Heartbeat { server_time_ms: u64, version: u64 },
}
```

全部使用 `abs_denco` 的 `TrEncodable` / `TrDecodable` 派生，复用项目现有 `mp_denco`
MessagePack 编解码器。

### 7.2 控制体

- 请求体：`RequestBuilder::body_bytes(&encoded)` 自动写 `Body_Size`；
- 回复体：`ResponseBuilder::sized_async(&mut encoded, len)` 自动写 `Body_Size`；
- `Call /scene/update` 的 ack body 用 denco 编码。

### 7.3 后缀帧

后缀流是裸字节，没有 MPTP 帧边界；demo 自己定义：

```text
frame = u32-be length + denco(SceneEvent)
```

- 服务端编码一次为 `Arc<[u8]>`；
- `ResponseStream::write_chunk_async(&frame)`；
- 客户端 `read_frame`：
  - 读 4 字节长度；
  - 读 `len` 字节；
  - denco 解码为 `SceneEvent`。
- `read_frame` 是 demo 的 `frames_.rs`，不放进 `mptp_smux`；`mptp_smux` 只提供字节流。

如果发现 `abs_buff` 的段接口让 `read_frame` 变得异常繁琐，可以在 demo 写一个小的
`read_exact` 辅助，但不要把帧协议塞回 `mptp_smux`。

## 8. `mptp_smux` API 使用矩阵

| demo 需求 | 使用的 `mptp_smux` API | 说明 |
| --- | --- | --- |
| 连接 | `MptpClient::new(shared_conn)` | compio 网络线程内 |
| 加入 / 订阅 | `MptpClient::pull("/scene")` + `RequestBuilder::body_bytes` + `send_async` | 长生命周期 |
| 读取 Welcome / 事件 | `Response::suffix_async` + demo `read_frame` | 客户端流式读 |
| 修改速度 | `MptpClient::invoke("/scene/update")` + `body_bytes` + `send_async` | 短请求 |
| 读取 ack | `Response::body_async` | denco 解码 |
| 健康检查 | `MptpClient::head("/scene")` | 展示无体回复 |
| 快照 | `MptpClient::view("/scene")` | 展示有体回复 |
| 服务端监听 | `MptpServlet::listen_async` | 每连接一个 servlet |
| 并发 session | `MptpServlet::accept_async` + `serve_session_async` + compio spawn | 每 session 一个任务 |
| 读请求体 | `ServingSession::req_body_async` | join / update |
| 写 ack | `ServingSession::response(...).sized_async` | 定长体 |
| 写快照 | `ResponseBuilder::sized_async` | View |
| 无体回复 | `ResponseBuilder::no_body_async` | Head / 405 |
| 服务端持续推送 | **`ResponseBuilder::suffix_stream_async` + `ResponseStream`**（本次补） | 订阅流 |
| 405 | `TrServeHandler::allowed_methods` + `MethodSet` | 统一处理 |
| 404 | handler 内 `session.response(Status::NotFound).no_body_async` | 业务层 |
| 取消 | `.may_cancel_with(token)` | 退出 / 超时 |
| 收尾 | `ResponseStream::finish_async` / `ServingSession::finish_async` | 半关闭 + 读尽 |
| 错误分类 | `ServeError` / `ClientError` | 取消 / 传输 / 协议 / 状态 |

## 9. 发现的 API 不足

### 9.1 主缺口：可追加的服务端后缀流

**现象**：`ResponseBodyWriter::suffix_async` 只接受有限 `TrBuffRead`，写至 EOF 结束；
广播需要“写 Welcome → 等事件 → 写事件 → 继续等”。

**如果不补**：

- 只能用 `ServingSession::take_parts()`；
- 自己调 `mptp_wire::write_response_prefix_async`；
- 自己写 `ChannelTx` 的段循环；
- 自己 `close_channel_async`；
- demo 会多出 100～200 行传输层代码。

**建议**：在 `mptp_smux` 增加：

```rust
ResponseBuilder::suffix_stream_async() -> ResponseStream
ResponseStream::write_chunk_async(&[u8])
ResponseStream::finish_async()
```

可选后续：

```rust
ResponseBodyWriter::into_suffix_stream_async()
```

用于“先写回复体，再开持续后缀流”的场景。

### 9.2 其他观察（不一定要补）

| 观察 | 结论 |
| --- | --- |
| `MptpServlet` 每连接一个，多连接 accept 没有框架 helper | 应用层职责；demo 自己写 accept 循环，不补 |
| handler 拿不到连接 id | 应用层在 accept 时注入 `SceneHandler`，不补 |
| 没有广播 / 订阅注册表 | 应用层 `SceneHub`，不补 |
| 没有帧长度 / 业务编解码 | 应用层 denco + `frames_`，不补 |
| 没有慢客户端策略 | 应用层 bounded channel，不补 |
| 没有断线重连 | 应用层；demo 用重连/重启 |
| `Response` 没有 `read_frame` | 应用层 `frames_`，不补 |
| `ResponseBodyWriter::suffix_async` 是有限源 | 由 9.1 的 `ResponseStream` 补 |

**原则**：只有“业务无论怎么写都会重复实现的传输原语”才补进 `mptp_smux`；广播策略、
路由、帧格式、重连都属于应用。

## 14. 风险

| 风险 | 处理 |
| --- | --- |
| Bevy 编译慢、依赖大 | feature-gated binary，默认 workspace 不编译 Bevy |
| Bevy 内部线程超过两个 | 关闭 `multi_threaded` / `pipelined_rendering`；单线程 task pool；验收记录实际线程 |
| compio 适配器 `!Send` | 所有 MPTP 固定在一个 compio 线程；跨线程只传普通事件 |
| 单 compio 线程被慢客户端拖住 | bounded flume + `try_send`；满则关闭该订阅 |
| `ResponseStream` 是新 API | 先补 `mptp_smux` 并测试，再写 demo |
| denco 编解码与 Bevy 线程 | 编解码全部在网络线程；Bevy 只收普通结构体 |
| Bevy GPU 环境 | 手工验收；CI 只做 `cargo check` / headless smoke |
| 服务端多连接 accept | 应用层 accept 循环；不塞进 `mptp_smux` |
| 旧 demo 脚本 | 重写 `justfile`，旧 echo/sum e2e 不再作为主验证 |

## 16. 英文摘要

This note plans the rewrite of `mptp_smux_v1_demo` as a native Bevy solar-system demo.
Clients connect to the scene server directly over MPTP/smux, with no HTTP or WebSocket
gateway. Both sides use `abs_art-facade` with compio; each process keeps at most two
business threads: Bevy main + one compio network thread on the client, and one compio
thread on the server. The Bevy client is a feature-gated binary and uses `bevy_egui`
sliders; payloads use denco. The server accepts one MPTP connection per client and
broadcasts scene events through per-connection `Pull` suffix streams.

The demo's primary goal is to exercise `mptp_smux` and expose API gaps. The main gap is
an appendable server-side suffix stream: `ResponseBodyWriter::suffix_async` writes a
finite source to EOF, while broadcast needs `Welcome -> wait -> event -> write -> ...`.
The note proposes a minimal `ResponseStream` addition. Everything else — scene model,
denco framing, subscription hub, Bevy ECS, slow-client policy, multi-connection accept —
belongs to the demo/application layer.
