## 0. 目的：这是 `mptp_smux` 的 API 压测场

`mptp_smux_v1_demo` 重写后的第一目标不是太阳系模拟器，而是：

> **用真实的「目录发现 + 选择性订阅 + 取消 / 重新订阅 + 无限后缀流」业务，把
> `mptp_smux` 当前提供的 API 全部用上；凡是 demo 为了实现业务而不得不写的传输层代码，
> 都是 `mptp_smux` 的 API 缺口，应记录并补在 `mptp_smux`，而不是在 demo 里绕过。**

因此本 demo 的取舍标准：

- 能直接用 `mptp_smux` 公开 API，就不自己写；
- 必须自己写的只能是业务层：场景目录、行星参数、事件、denco 编解码、订阅注册表、
  Bevy ECS / 渲染；
- 发现缺 API 时，先在一个**最小集成测试**里复现，评估最小补充，再实施；
- 不在 demo 中复制 `mptp_smux` 的会话 / 后缀 / 收尾逻辑。

| 约束 | 决定 |
| --- | --- |
| 客户端 | **Bevy** 直接渲染，不使用网页 / WASM |

| 实施顺序 | **先集成测试，后 Bevy 游戏** |

## 2. 核心模型：目录 + 每行星数据流

### 2.1 URI / 资源

| 资源 | 方法 | 语义 |
| --- | --- | --- |
| `/scene/join` | `Call` | 当前连接创建自己的行星，返回 `PlanetDescriptor` |
| `/scene/update` | `Call` | 修改自己行星的公转 / 自转速度，返回 ack |
| `/scene/planets` | `View` | 列出当前所有行星数据流（目录），不订阅 |
| `/scene/planets` | `Head` | 只返回行星数量 / 目录版本（无体） |
| `/scene/planets/{id}` | `Pull` | 订阅该行星的数据流；服务端持续写后缀流 |
| 其他 | 任意 | 未知路径 `404`；方法不允许 `405` |

**关键点**：行星存在 ≠ 客户端已订阅。客户端可以先 `View` 看到所有行星，再按 URI
选择订阅其中一部分。

### 2.2 目录

`View /scene/planets` 返回：

```rust
struct PlanetDirectory {
    directory_version: u64,
    planets: Vec<PlanetDescriptor>,
}

struct PlanetDescriptor {
    id: PlanetId,
    owner: ClientId,
    name: String,
    color: u32,
    stream_uri: String,   // "/scene/planets/{id}"
    version: u64,         // 该行星状态版本
}
```

目录只描述「有哪些流」，不建立订阅。

### 2.3 行星数据流

`Pull /scene/planets/{id}`：

- 回复前缀无回复体；
- 后缀流中按顺序发送 denco 编码的 `PlanetEvent`：
  - `Snapshot { planet, version }`：订阅起点；
  - `Updated { planet, version }`：参数变化；
  - `Removed { planet_id, version }`：行星被删除，随后流结束；
  - `Heartbeat { server_time_ms, version }`：可选。
- 流一直保持到客户端关闭 / 取消订阅；
- 服务端不要求客户端读取速度匹配；慢客户端策略在应用层（bounded queue）。

### 2.4 加入

`Call /scene/join`：

- 每个连接只允许一次；
- 服务端创建该连接的行星；
- 返回 `PlanetDescriptor`，客户端从中拿到自己的 `planet_id` 和 `stream_uri`；
- 目录版本递增。

### 2.5 订阅 / 退订 / 重新订阅

- **订阅**：`Pull` 某个 `stream_uri`，读到 `Snapshot` 后更新本地场景；
- **退订**：客户端丢弃该 `Pull` 的 `Response` / 取消其任务；服务端在流写入失败或读到
  EOF 时移除订阅者；
- **重新订阅**：再次 `Pull` 同一 URI；服务端先发新的 `Snapshot`，客户端以快照覆盖本地
  旧状态；
- 同一连接可以同时持有多个 `Pull` 会话（每个被订阅行星一个）；
- 不同连接、不同订阅之间互不影响。

### 2.6 客户端选择策略

为了满足「两个客户端能互相看到」，demo 的默认策略可以是：

1. 启动后 `Call /scene/join` 拿到自己的行星；
2. `View /scene/planets` 列出所有行星；
3. 默认订阅全部（包括自己）；
4. UI 提供每个行星的勾选框：
   - 取消勾选 → 丢弃对应 `Pull` 会话（退订）；
   - 重新勾选 → 新开 `Pull`（重新订阅，拿新快照）。

这样既满足「默认互看」，也完整演示选择性订阅。

目录变化（新客户端加入）时，客户端可以：

- 周期性 `View /scene/planets`（例如 1 Hz）做 diff；或
- 订阅中的行星事件带 `directory_version`，变化时重新 `View`。

本规划默认**低频轮询 `View` + Removed 事件触发刷新**，简单可靠。

## 3. chunk 语义：无限流 + 对象序列化

### 3.1 这里的 chunk 不是 `Body_Transfer: chunked`

必须明确：

- MPTP 后缀流在协议上是**裸字节**：没有长度声明、没有 2 字节块帧；
- 本规划说的 **chunk** 是 `mptp_smux` 的**写入单位**，不是 `Body_Transfer: chunked`
  的线上帧；
- 不改变 `mptp_wire` 的线上格式；
- 如果将来要把 chunk 边界写进线上格式，那是协议变更，需单独讨论，不在本 demo 范围。

### 3.2 对象 → 一个或多个 chunk

每个要发送的对象：

1. 用 denco 序列化成字节；
2. 通过 `SuffixStream::write_chunk_async(&bytes)` 写入；
3. 对象可以一次写完，也可以拆成多个 chunk 分多次写；
4. 接收端把后缀流当作连续的 denco 值序列，**逐值解码**；
5. denco / MessagePack 的值是自描述的，因此不需要再加长度前缀。

例如：

```text
chunk 1: PlanetEvent::Snapshot 的前半段字节
chunk 2: PlanetEvent::Snapshot 的后半段字节
chunk 3: PlanetEvent::Updated 的完整字节
chunk 4: PlanetEvent::Updated 的完整字节
...
```

接收端第一次解码会等 chunk 1 + chunk 2 到齐；之后每遇到一个新值就解出一个事件。

### 3.3 无限长

- `SuffixStream` 没有「总长度」概念；
- 只要不 `finish`、不关闭会话，就可以一直写；
- 结束由客户端退订 / 连接关闭 / 服务端删除行星触发；
- 因此同一套 API 既支持少量事件，也支持持续数小时的更新流。

### 3.4 需要的 `mptp_smux` API

```rust
impl<C: serving::config::TrConfig> ResponseBuilder<'_, C> {
    /// 写回复前缀（无回复体），返回可无限追加 chunk 的后缀流句柄。
    pub fn suffix_stream_async(self) -> SuffixStreamAsync<'_, C>;
}

pub struct SuffixStream<'a, C> {
    // 借用 ServingSession
}

impl<'a, C> SuffixStream<'a, C> {
    /// 追加一个 chunk；不关闭写端。
    pub async fn write_chunk_async(&mut self, chunk: &[u8]) -> Result<(), ServeError>;

    /// 可选：把一个有限读源的内容连续写成 chunks。
    pub async fn write_chunks_async<R>(&mut self, src: &mut R) -> Result<(), ServeError>
    where
        R: TrBuffRead<u8> + TrConsumerState;

    /// 半关闭写端、读尽对端、结束会话。
    pub async fn finish_async(self) -> Result<(), ServeError>;
}
```

要点：

- `write_chunk_async` 可以调用任意多次；
- 不定义对象边界、不定义长度前缀、不做 denco；
- `Head` / `Drop` 的回复不能开后缀流；
- 取消沿用 `.may_cancel_with(token)`；
- `finish_async` 复用现有「半关闭写端 → 读尽对端」收尾。

这是本次规划发现的**唯一需要先补进 `mptp_smux` 的公共原语**。

### 3.5 `Push` 方向的未来缺口

当前 demo 的业务只需要服务端 → 客户端的 `Pull` 后缀流：

- 服务端写：`SuffixStream`；
- 客户端读：`Response::suffix_async` + denco 逐值解码。

如果未来要支持**无限长 `Push`**（客户端持续向服务端写后缀流），当前客户端
`RequestBuilder::suffix` 仍是有限源语义，届时需要一个对称的
`RequestSuffixWriter` / `PushStream`。本 demo 不实现，但记录为已知缺口。

## 4. 总体架构

```text
┌──────────────────────────────┐        MPTP over TCP/smux        ┌──────────────────────────────┐
│ Bevy 客户端 A                │ ◀──────────────────────────────▶ │ scene-server                 │
│  - Bevy 主线程（渲染 / UI）  │      一条连接 / 一个 MptpServlet  │  - compio 单线程             │
│  - compio 网络线程           │                                  │  - 每连接一个 MptpServlet     │
│  - 订阅 0..N 个行星流        │                                  │  - PlanetRegistry / per-planet│
│  - 摄像机锁自己的行星        │                                  │    stream hub                │
└──────────────────────────────┘                                  │  - 不渲染、不算位置           │
┌──────────────────────────────┐        MPTP over TCP/smux        │                              │
│ Bevy 客户端 B                │ ◀──────────────────────────────▶ │                              │
│  - 可只订阅 A 的行星         │                                  │                              │
└──────────────────────────────┘                                  └──────────────────────────────┘
```

### 4.1 线程模型

| 进程 | 线程 | 职责 |
| --- | --- | --- |
| `scene-server` | **1 个 compio 线程** | accept、所有连接、所有 session、目录与行星流 |
| `scene-client`（Bevy） | **Bevy 主线程 + 1 个 compio 网络线程** | 渲染 / UI / ECS；MPTP 连接与订阅 |
| `scene-smoke`（headless） | **1 个 compio 线程** | 无渲染 e2e 客户端 |

`buffex_compio_adapt` 的 `BuffRead` / `BuffWrite`：

- 必须在正在运行的 compio runtime 内构造；
- 类型 `!Send`；
- 不能跨线程 / 跨 runtime 移动。

因此**整个 MPTP 栈固定在一条 compio 线程上**：

- 服务端一个 compio 线程承载所有连接；
- 客户端一个 compio 网络线程承载连接、所有 `Pull` 订阅、控制请求；
- Bevy 主线程只通过 channel 收发普通数据。

Bevy 内部线程按上一版约定处理：关闭 `multi_threaded` / `pipelined_rendering`，
单线程 task pool，不额外 spawn 业务线程；引擎内部线程单独记录。

## 5. 服务端设计

### 5.1 compio accept

```text
compio Runtime（单线程）
  └─ TcpListener accept
       ├─ 为每个连接创建 BuffRead / BuffWrite
       ├─ 建立 MuxConnection
       ├─ bind dock
       ├─ 分配 ConnectionId
       ├─ 创建 SceneHandler { hub, registry, own_planet }
       ├─ 创建 MptpServlet<SceneCfg, SceneHandler>
       └─ spawn 本地任务：
            listen_async → accept_async → serve_session_async
```

所有连接、所有 session 都在同一线程；`compio::runtime::spawn` 不要求 `Send`，
正好承载 `!Send` 的适配器与 `MptpSession`。

### 5.2 每连接一个 `SceneHandler`

```rust
struct SceneHandler {
    connection_id: ClientId,
    hub: Rc<RefCell<SceneHub>>,
    registry: Rc<RefCell<PlanetRegistry>>,
    own_planet: Cell<Option<PlanetId>>,
}
```

`TrServeHandler`：

```rust
impl TrServeHandler<SceneCfg> for SceneHandler {
    type Err = SceneError;

    fn allowed_methods(&self) -> MethodSet {
        MethodSet::HEAD | MethodSet::VIEW | MethodSet::PULL | MethodSet::CALL
    }

    async fn handle_async(&self, method, session) {
        match (method, session.location()) {
            (Call, "/scene/join")   => join_,
            (Call, "/scene/update") => update_,
            (View, "/scene/planets") => list_,
            (Head, "/scene/planets") => head_,
            (Pull, uri) if planet_uri_(uri) => pull_,
            (_, _) => not_found_,
        }
    }
}
```

- `405` 由框架的 `allowed_methods` 处理；
- 未知路径在 handler 内写 `404`；
- `join` 每个连接一次；
- `update` 只操作 `own_planet`；
- `Pull` 解析 `/scene/planets/{id}`，未知 id 写 `404`。

### 5.3 目录与 per-planet hub

```rust
struct PlanetRegistry {
    planets: BTreeMap<PlanetId, Planet>,
    directory_version: u64,
}

struct SceneHub {
    // 每个行星一组订阅者；帧已编码为 Arc<[u8]>
    streams: BTreeMap<PlanetId, Vec<(SubId, flume::Sender<Arc<[u8]>>)>>,
}
```

单线程，因此：

- 不需要 `Mutex` / `RwLock`；
- `Rc<RefCell<...>>` 足够；
- 广播时只短暂借用，不跨 `await` 持有 `RefCell` 借用。

### 5.4 目录 `View`

`View /scene/planets`：

1. 读 registry；
2. 生成 `PlanetDirectory`（所有行星，包括无人订阅的）；
3. 用 denco 编码；
4. `session.response(Status::Ok).sized_async(&mut bytes, len)` 写回复体。

目录只读，不建立订阅。

### 5.5 `Pull` 行星流

```rust
async fn pull_(handler: &SceneHandler, session: &mut ServingSession<SceneCfg>) -> Result<(), ServeError> {
    let planet_id = parse_planet_uri_(session.location())?;
    let snapshot = handler.registry.borrow().snapshot_(planet_id)?;

    let (tx, rx) = flume::bounded(K_SUB_QUEUE);
    handler.hub.borrow_mut().add_(planet_id, tx);

    let mut stream = session
        .response(Status::Ok)
        .suffix_stream_async()
        .await?;

    // 第一个 chunk：Snapshot
    stream.write_chunk_async(&encode_chunk_(&PlanetEvent::Snapshot(snapshot))?).await?;

    while let Ok(frame) = rx.recv_async().await {
        stream.write_chunk_async(&frame).await?;
    }

    stream.finish_async().await?;
    handler.hub.borrow_mut().remove_(planet_id, sub_id);
    Result::Ok(())
}

// 注意：write_chunk_async / finish_async 的错误路径也必须先移除订阅者，
// 否则客户端断开后订阅表会泄漏。实现时用 guard 或把 cleanup 放在统一的
// 出口，不要只在成功路径 remove。
```

注意：

- `Snapshot` 是一个 denco 对象，可能由多个 chunk 写入；
- 之后的每个 `Updated` / `Removed` 也是独立 denco 对象；
- 客户端按 denco 值逐个解码，不需要长度前缀；
- 慢客户端由 bounded `flume` 控制；
- `Pull` 结束（客户端退订）时移除订阅者。

### 5.6 更新 / 离开

`Call /scene/update`：

1. 校验 `own_planet`；
2. 更新 registry 与版本；
3. 编码 `Updated`；
4. 只向该行星的订阅者广播；
5. 写 ack。

连接断开：

1. 从 registry 删除自己的行星；
2. 向该行星订阅者广播 `Removed` 并关闭其流；
3. `directory_version += 1`。

## 6. 客户端设计

### 6.1 网络线程

```text
compio 网络线程
  ├─ 建立 MptpClient
  ├─ Call /scene/join → PlanetDescriptor
  ├─ View /scene/planets → PlanetDirectory
  ├─ 对每个选中的 planet URI 发起 Pull（多个 Response）
  ├─ 每个 Pull 一个读取任务：denco 解码 PlanetEvent → NetEvent
  ├─ 处理 NetCommand::Subscribe / Unsubscribe / Update
  └─ 退出时关闭所有 Pull 与连接
```

- 同一连接上多个 `Pull` 会话并发；
- `MptpClient` 共享；
- 控制 `Call` 与订阅 `Pull` 并发；
- 所有 MPTP / denco / compio 操作都在这个线程；
- 与 Bevy 主线程只传 `NetCommand` / `NetEvent`。

### 6.2 命令 / 事件

```rust
enum NetCommand {
    Subscribe { planet_id: PlanetId, uri: String },
    Unsubscribe { planet_id: PlanetId },
    UpdateSelf { orbit_speed: f32, spin_speed: f32 },
    RefreshDirectory,
    Shutdown,
}

enum NetEvent {
    Joined { descriptor: PlanetDescriptor },
    Directory { directory: PlanetDirectory },
    PlanetEvent { planet_id: PlanetId, event: PlanetEvent },
    SubscriptionClosed { planet_id: PlanetId, reason: String },
    Error(String),
    Disconnected,
}
```

### 6.3 Bevy 端

- `MptpNetPlugin`：启动网络线程；资源 `NetHandle { cmd_tx, event_rx }`；
- `ScenePlugin`：
  - `SceneState { my_planet, directory, planets, subscriptions, epoch, version }`；
  - 系统：
    - `drain_net_events`
    - `refresh_directory`（低频 `View`）
    - `apply_planet_events`
    - `follow_my_planet`
    - `update_orbits`
    - `subscription_ui`（`bevy_egui` 勾选框 + 速度滑杆）
    - `send_commands`

### 6.4 订阅 UI

- 面板列出目录中的行星：
  - 名称 / owner / 是否已订阅；
  - 勾选框 → Subscribe / Unsubscribe；
- 自己的行星默认订阅，且不可退订（摄像机需要）；
- 其他行星可勾选 / 取消；
- 取消后：
  - 丢弃对应 `Pull` 任务；
  - 从本地场景移除或标记为未订阅（建议移除，避免显示过期数据）；
- 重新勾选：
  - 新开 `Pull`；
  - 收到 `Snapshot` 后重新加入场景。

### 6.5 摄像机与轨道

- 自己的摄像机跟随自己的行星；
- 其他行星按相同的轨道公式本地计算；
- 未订阅的行星不显示；
- 服务端只发参数 / 事件，不发位置。

## 7. denco 编解码

- 所有控制体、回复体、行星事件都用 denco MessagePack；
- 每个 `PlanetEvent` 序列化成一个**自描述值**；
- 后缀流是连续值序列，客户端用 `MpDecoder` 逐个解码；
- chunk 拆分不影响解码；
- 不引入长度前缀（denco 自描述）；
- 如果将来需要非 denco 编码或显式对象边界，可以在应用层加帧；`mptp_smux` 不参与。

---

## 8. `mptp_smux` API 使用矩阵

| 需求 | API |
| --- | --- |
| 加入 | `MptpClient::invoke("/scene/join")` + `body_bytes` + `send_async` |
| 目录 | `MptpClient::view("/scene/planets")` + `Response::body_async` |
| 数量 / 版本 | `MptpClient::head("/scene/planets")` + `Response::headers` |
| 订阅 | `MptpClient::pull(stream_uri)` + `Response::suffix_async` |
| 读事件 | `Response::suffix_async` + denco 逐值解码 |
| 更新 | `MptpClient::invoke("/scene/update")` + `body_bytes` + `send_async` |
| 退订 | 丢弃 `Response` / 取消任务 |
| 服务端监听 | `MptpServlet::listen_async` |
| 多 session | `accept_async` + `serve_session_async` + compio spawn |
| 读请求体 | `ServingSession::req_body_async` |
| 写目录 / ack | `ResponseBuilder::sized_async` |
| 无体回复 | `ResponseBuilder::no_body_async` |
| 持续行星流 | **`ResponseBuilder::suffix_stream_async` + `SuffixStream::write_chunk_async`（本次补）** |
| 405 | `TrServeHandler::allowed_methods` + `MethodSet` |
| 404 | handler 内写 `Status::NotFound` |
| 取消 | `.may_cancel_with(token)` |
| 收尾 | `SuffixStream::finish_async` / `ServingSession::finish_async` |
| 错误分类 | `ClientError` / `ServeError` |

## 9. API 缺口

### 9.1 主缺口：无限 chunk 后缀流

- 当前 `ResponseBodyWriter::suffix_async` 只接受有限源，写至 EOF 结束；
- 行星数据流是无限序列，需要多次 `write_chunk_async`；
- 不补的话，demo 只能用 `take_parts` + 裸 `ChannelTx` + `mptp_wire` 写循环，
  这会把传输层代码塞进业务。

**建议补**：

```rust
ResponseBuilder::suffix_stream_async() -> SuffixStream
SuffixStream::write_chunk_async(&[u8])
SuffixStream::write_chunks_async<R>(&mut R)   // 可选
SuffixStream::finish_async()
```

### 9.2 未来缺口：客户端无限 `Push`

- 本 demo 不需要；
- 若未来支持客户端持续 `Push`，需要对称的 `RequestSuffixWriter`；
- 不在本次实现。

### 9.3 不属于 `mptp_smux` 的

- 目录 / 路由 / URI 解析；
- 每行星订阅表；
- 慢客户端策略；
- denco 编解码 / 对象边界；
- 多连接 accept；
- Bevy / compio 线程桥接；
- 重连 / 目录刷新。

这些全部放 demo / 应用层。

## 14. 风险与未决

| 风险 | 处理 |
| --- | --- |
| `SuffixStream` 是新 API | 先补 `mptp_smux` 并写传输测试，再写夹具 |
| 每行星多个并发 `Pull` 会话 | 测试覆盖；客户端按 planet 管理任务 |
| 单 compio 线程被慢订阅拖住 | bounded flume + `try_send`；满则关闭订阅 |
| 目录刷新频率 | 默认 1 Hz `View` + Removed 触发刷新；可调 |
| Bevy 内部线程 | 关闭多线程 feature；验收记录 |
| denco 逐值解码跨 chunk | 用 `object_split_across_chunks_` 测试覆盖 |
| 订阅退订的竞态 | 客户端丢弃 `Response`；服务端流写失败 / EOF 清理；测试覆盖 |
| 未来 Push 无限流 | 记录为后续 `RequestSuffixWriter` 缺口，不在本 demo |

未决：

1. `View` 目录是否包含 `owner` / `stream_uri` 的完整信息？本规划默认包含。
2. 目录刷新是否由服务端主动推 `DirectoryChanged`？本规划默认客户端低频 `View`；
   如果测试发现轮询不优雅，再评估是否增加目录流。
3. 退订后本地场景是删除还是灰显？默认删除；重新订阅后按 Snapshot 恢复。
4. 是否需要在 `Pull` 请求体里带订阅选项（如 `include_heartbeat`）？默认无请求体。
5. `Head /scene/planets` 的头键使用标准头还是 demo 自定义头？默认 demo 自定义头。

## 15. 英文摘要

This revision changes the Bevy solar-system demo from one global `/scene` broadcast
stream to a **directory + per-planet stream** model. Clients `View /scene/planets` to
discover all planet stream URIs, then `Pull /scene/planets/{id}` to subscribe to the
ones they choose; dropping the `Pull` session unsubscribes, and a new `Pull`
resubscribes with a fresh snapshot. The suffix stream is chunk-based at the API level:
each denco-serialized object is written as one or more `write_chunk_async` calls and
decoded as a sequence of self-describing values; the wire suffix remains raw bytes and
is infinite until unsubscribed.

The note now puts integration tests first: a Bevy-free `SceneFixture`/`SceneTestClient`
exercises directory listing, join, selective subscription, unsubscribe/resubscribe,
chunk splitting, infinite streams, multi-client isolation, 404/405 and cleanup before
the game code is written. The one required `mptp_smux` addition remains an appendable
`SuffixStream`; everything else stays in the demo/application layer.
