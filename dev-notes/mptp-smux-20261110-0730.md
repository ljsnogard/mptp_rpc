## 0. 结论摘要

1. `mptp_smux` 是 **MPTP 协议在 `smux_v1` 这个多流传输层上的具体实现**，关系类似
   HTTP over TCP。它既不是 MPTP 协议本身（协议形状在 `abs_mptp`），也不是 RPC 框架
   （RPC 语义在 `rpc_core_v1` / `abs_rpc_serv`）。
2. MPTP 对传输层的核心要求是「可靠的、有序的、双向的、支持半关闭的、可并行的多条子流」。
   按这个条件，QUIC 是合法候选；因此 `mptp_smux` 与想象中的 `mptp_quic` 必须共享
   **MPTP 报文语义**，只把「子流怎么开、内存怎么给、连接怎么建」留给各自传输层。
3. 两端对等：同一条 `smux_v1` 连接的两端都可以同时发请求和接请求。`mptp_smux` 因此同时
   提供客户端与服务端；重构目标是把它们拆成 `client` / `server` feature，默认全开。
4. `mptp_smux` 应该负责：smux 绑定、子流生命周期、ring 内存注入、前缀线格式、按头表搬运
   体 / 后缀、半关闭与收尾、取消传播、客户端会话与服务端 accept 循环。
5. `mptp_smux` 绝对不应该负责：RPC service 语义、业务体编解码、应用路由策略、运行时选择、
   socket/TLS/连接池、协议常量本身，以及「为了同时支持 QUIC 而抽象所有传输层」的大一统
   接口。
6. 当前已经超出理想职责、但暂时仍在承担的部分：
   - 内置 `serving::Router`（路径前缀 → handler）——路由是应用策略，不是 MPTP 线格式；
   - 具体前缀线格式与 `RequestPrefix` / `ResponsePrefix` / `Headers` 类型——它们目前住在
     `mptp_smux`，导致 RPC 层直接依赖具体传输 crate，未来 `mptp_quic` 无法复用；
   - `K_DEFAULT_SERVING_DOCK`——当前文档称其为「协议常量」，但协议综述并未把 dock 写进
     线格式；它究竟是协议约定还是 smux 绑定的参考默认值，需要先核对，再决定是否上移；
   - `x_deps` 的大量转出——便利，但不是职责；
   - `abs_mptp_smux` 与 `mptp_smux` 的配置 / ring 准备代码重复，且前者当前没有使用者。
7. 当前缺少：`client` / `server` feature、服务端并发接入（spawner / 每子流任务）、优雅关闭
   句柄、稳定的错误源、no_std 事实与 Cargo 元数据的一致性。

## 1. 定位

```text
┌───────────────────────────────────────────────────────────┐
│ 应用 / RPC：业务类型、序列化、service、路由、handler        │
├───────────────────────────────────────────────────────────┤
│ MPTP：前缀、头表、体边界、后缀流、一次请求的会话顺序        │
│       abs_mptp（协议形状） + 具体线格式（当前在 mptp_smux） │
├───────────────────────────────────────────────────────────┤
│ 多流传输：open / accept / read / write / half-close / reset │
│       smux_v1（当前） / QUIC（候选）                        │
├───────────────────────────────────────────────────────────┤
│ 字节流载体：TCP / UDS / ...                                 │
└───────────────────────────────────────────────────────────┘
```

MPTP 协议综述已经明确：MPTP 只定义一条**字节流通道**上的一次请求 / 回复如何表示；
通道建立、复用、可靠传输与流控由下层负责；服务端路由策略、RPC 方法到业务函数的映射
不属于 MPTP。这个边界是本文判断「应该 / 不应该」的第一依据。

`mptp_smux` 的「smux」不是协议的一部分，而是实现选择：它把 `abs_mptp` 的抽象落到
`abs_smux` / `smux_v1` 的 dock、channel、ring 与 accept 循环上。

## 2. 与 `mptp_quic` 的共通点

### 2.1 MPTP 对传输层的要求

一条能承载 MPTP 的传输必须提供：

1. **可靠**：字节不丢失、不重复、不损坏；
2. **有序**：每个方向保持写入顺序；
3. **双向**：一条子流上双方都能独立读写；
4. **半关闭**：发送方可以只关闭写方向，接收方读到 EOF 后仍能继续写；
5. **多条并行子流**：一条连接上可同时存在多条互不阻塞的通道；
6. **按字节流处理**：MPTP 的所有边界由前缀与体帧自行界定，不依赖消息边界。

`smux_v1` 满足这些条件；QUIC 的双向 stream 也满足。二者都不满足「消息边界」这一条，
所以 MPTP 不能假设下层替它保留消息边界。

### 2.2 应该共通的部分

| 层次 | 共通内容 | 归属 |
| --- | --- | --- |
| MPTP 语义 | access method、status、标准头、`Body_Size` / `Body_Transfer`、后缀流语义 | `abs_mptp` |
| MPTP 线格式 | 请求 / 回复前缀的 MessagePack 字节序列、头表编码 | 应独立于具体传输（见 §4.3） |
| 会话状态 | 前缀 → 请求体 → 回复前缀 → 回复体 → 后缀 → 半关闭 | 协议形状在 `abs_mptp`，具体 IO 由传输实现 |
| 角色模型 | 两端都既可发起也可响应；client / server 是「一次请求的方向」而不是「连接的属性」 | 协议契约 |
| 取消 / 错误分类 | 取消、传输错误、协议错误、应用拒绝 | 协议契约 + 各传输绑定 |
| handler 契约 | `TrReqHandler`（服务端收到一次请求后做什么） | `abs_mptp::serving` |

### 2.3 必然不同的部分

| 关注点 | `mptp_smux` | 假想的 `mptp_quic` |
| --- | --- | --- |
| 子流标识 | dock（本端 / 远端） | stream ID |
| 开子流 | `bind_async` + `open_channel_async` + `accept_async` | QUIC stream open / accept |
| 接子流 | `listen_async` + `income_async` + `accept_async` | QUIC accept |
| ring 内存 | 调用者注入两块 ring，`TrPrepFactory` 生产准备器 | QUIC 自己的 send / recv buffer 模型 |
| 半关闭 / reset | smux_v1 的 FIN / RESET | QUIC 的 FIN / RESET_STREAM |
| 连接对象 | `abs_smux` 的 connection / binding | QUIC connection |
| 流控 | smux_v1 的窗口 | QUIC 的 stream / connection flow control |

### 2.4 直接推论

- `mptp_smux` 与 `mptp_quic` 应是**兄弟绑定**，不是父子关系；
- 二者共享的 MPTP 线格式与会话契约不能依赖 `mptp_smux` 的具体类型；
- 具体传输绑定可以各自定义 `TrConfig`、ring 准备、dock / stream 类型；
- 不应该为了「以后可能有 QUIC」就在 `mptp_smux` 里造一个万能 `TrTransport`，把所有传输
  的差异塞进同一个 trait；共用部分应该先收敛到 `abs_mptp` / 独立的 wire crate，
  transport-specific 的部分各自保留。

## 3. 当前实践审计

### 3.1 谁在使用 `mptp_smux`

| 使用者 | 使用的部分 | 希望它做什么 |
| --- | --- | --- |
| `abs_rpc_serv` | `serving::config::TrConfig`、`x_deps` 中的协议类型 | 为 RPC service 抽象提供 `Headers` / `ChannelTx` / `ChannelRx` / `Status` 等类型 |
| `rpc_core_v1` | `MptpClient` / `MptpSession`、`MptpServer`、`Router`、`messaging::{RequestPrefix, ResponsePrefix, Headers, write_*}`、`client::config`、`serving::config`、`prep` 工厂 | 完成一次 RPC 的客户端请求、服务端解码 / 回复 / 收尾、interface 前缀分派 |
| `rpc_svc_macro` | 通过 `rpc_core_v1` 间接使用；文档示例使用 `mptp_smux::serving::Router` / `RouterCtx` | 生成代码只依赖 core；装配期由用户组织 router |
| `mptp_smux_v1_demo` | `MptpClient`、`MptpServer`、`messaging` 四个前缀读写入口、`TrPrepFactory`、`TrPathRouter` | 在真实 TCP 上验证 mptp_smux 的端到端行为；自己提供 Router |
| `rpc_demo` | `MptpClient`、`MptpServer`、`messaging`、`TrPathRouter` | 手写 queue 版 RPC demo；自己提供 Router/RpcRouter |
| `mptp_cs_smoke`（仓库外） | `MptpClient`、`MptpServer`、`Router`、`RpcRouter` 及配置 / 工厂 | 真实 UDS + compio 的 11 条 RPC 回归 |
| `abs_mptp_smux` | **无使用者** | 名义上是「MPTP over SMUX 的抽象」，实际与 `mptp_smux` 的 config / ring 准备重复 |

### 3.2 它们真正需要的稳定面

从调用点看，上层实际依赖的是：

1. **线格式类型与读写入口**：`RequestPrefix` / `ResponsePrefix` / `Headers`、
   `read_*_prefix_async` / `write_*_prefix_async`；
2. **一次请求的会话对象**：发请求体、发后缀、读回复前缀、读回复体 / 后缀；
3. **客户端连接对象**：`MptpClient::new`、`request_async` / `request_to_dock_async`；
4. **服务端 accept 循环**：`MptpServer::new`、`serve_listener_async` / `serve_channel_async`；
5. **ring 内存注入**：`TrPrepFactory` / `ClientPrepCtx` / `ServingPrepCtx` / `RingBuffs`；
6. **取消传播**：所有 await 点都要接受调用方令牌；
7. **收尾**：`close_channel_async` 的「先半关闭写端，再读到 EOF」次序。

它们**不**需要 `mptp_smux` 提供业务类型、RPC 方法、service 注册或业务错误映射。

### 3.3 层间耦合的现状

- `abs_rpc_serv` 是一个抽象契约 crate，却直接依赖具体的 `mptp_smux`，只为拿
  `serving::config::TrConfig` 与几个协议类型。理想依赖应是 `abs_mptp`（或未来的
  `abs_mptp_smux` 抽象），而不是具体实现。
- `rpc_core_v1` 的 `ClientProxy` 字段是具体 `MptpClient<C>`，`RpcCallCtx` 直接持有
  `mptp_smux` 的 `ChannelTx` / `ChannelRx`，`TrRpcClientConfig` / `TrServingConfig`
  也以 `mptp_smux` 的 `TrConfig` 为父 trait。这使 RPC 层无法换到 `mptp_quic`。
- `abs_mptp` 只定义前缀「形状」，具体的 `RequestPrefix` / `ResponsePrefix` 类型与
  MessagePack 编码在 `mptp_smux::messaging`；如果 `mptp_quic` 出现，它会需要同一份线格式，
  但现在没有一个不依赖 `mptp_smux` 的共享点。

## 4. 职责边界

### 4.1 `mptp_smux` 应该做什么

1. **smux 绑定**：把 MPTP 的「开一条通道 / 接一条通道 / 读写 / 半关闭」落到
   `abs_smux` 的 bind / open / listen / income / accept / ring 接口上；
2. **子流生命周期**：一次请求一条通道；请求前缀、请求体、请求后缀、回复前缀、回复体、
   回复后缀、半关闭与收尾的次序；
3. **ring 内存注入**：按配置声明的工厂，为每条子流现场生产新的 ring 内存；
4. **前缀线格式的参考实现**：按 MPTP 规定编码 / 解码请求与回复前缀，且读前缀时不越过
   体的第一个字节；
5. **体 / 后缀搬运**：按头表声明的 `Body_Size` / `Body_Transfer` 选择定长 / 分块 / 无体，
   后缀按裸字节流处理；
6. **客户端与服务端角色实现**：`MptpClient` / `MptpSession` 与 `MptpServer` 的 accept
   循环；两者共享同一份 MPTP 语义；
7. **取消传播与错误分类**：把调用方令牌传到每个 await 点，区分取消、传输错误、协议错误、
   handler 错误；
8. **两端配置分离**：客户端与服务端各自声明连接类型、ring 来源、默认 dock；它们可以
   跑在两个进程、各自升级。

### 4.2 `mptp_smux` 绝对不应该做什么

1. **不实现 RPC 语义**：service trait、`#[rpc]` 宏、RPC 状态码到业务错误的映射、方法名到
   handler 的映射，都属于 `abs_rpc_serv` / `rpc_core_v1`；
2. **不实现业务体编解码**：MessagePack / JSON / 自定义业务类型的序列化不属于本 crate；
   本 crate 只按头表搬运字节；
3. **不决定应用路由策略**：路径如何匹配、是否分层、是否运行期增删，是应用 / router crate
   的事。`TrPathRouter` 可以作为一个**可选接缝**保留，但内置 `Router` 不应成为 MPTP 的
   必备部分；
4. **不选择运行时 / 不替调用者 spawn**：tokio / compio / smol、线程数、任务模型由应用
   决定；当前 `serve_listener_async` 逐条 inline await 只是实现限制，不是契约；
5. **不管理 socket / TLS / 连接池 / 重连**：连接从哪里来由调用者提供；
6. **不把实现默认值冒充协议常量**：如果 `K_DEFAULT_SERVING_DOCK` 确为协议约定，它应住在
   `abs_mptp::spec`，本 crate 只做本端 dock 类型翻译；如果它只是 smux 参考实现的默认值，
   就应留在本 crate，但必须改掉「协议常量」的措辞；
7. **不把「一条通道复用多次请求」偷偷加进来**：当前 MPTP 没有请求 ID / 多路复用帧；
   一条通道一次请求是协议约束，不是实现偷懒；
8. **不抽象所有传输**：不要为了 QUIC 造一个把 dock、stream、ring 全部抹平的万能 trait；
   共通部分应上移到协议 / wire 层。

### 4.3 已经越界但暂时保留的部分

| 现状 | 问题 | 建议 |
| --- | --- | --- |
| `serving::Router` / `TrPathRouter` | 路由是应用策略，不是 MPTP 线格式；外部 `mptp_cs_smoke` 仍在用 | 保留 `TrPathRouter` 接缝；把内置 `Router` 放到 `router` feature 或独立 crate，至少与 `server` feature 解耦 |
| `messaging` 具体线格式 | `RequestPrefix` / `ResponsePrefix` / `Headers` 被 `abs_rpc_serv`、`rpc_core_v1` 直接依赖，`mptp_quic` 无法复用 | 抽到共享 wire crate，或至少让 `abs_mptp` 拥有具体类型，`mptp_smux` 只做 IO |
| `K_DEFAULT_SERVING_DOCK` | 文档称其为协议常量，但协议综述未定义 dock；归属未核 | 确认协议地位后再决定上移 `abs_mptp::spec`，或改称「smux 参考默认值」并留在本 crate |
| `x_deps` | 大量上游 crate 转出，形成隐式 API 面 | 明确标注不稳定；下游优先用具体模块 / `preludes` |
| `abs_mptp_smux` | 与 `mptp_smux` 的 config / ring 准备重复，当前无使用者 | 二选一：删除；或让 `mptp_smux` 依赖它并删掉重复定义 |

## 5. 缺口

1. **feature 未拆分**：当前 `client` 与 `server` 总是同时编译；只想要客户端的使用者也被
   迫拉入服务端、`Router`、`matchit_route`、`tlist`。
2. **服务端并发**：`serve_listener_async` 在 accept 循环里直接 await 一条子流的 handler；
   长 `Pull` / 慢 handler 会阻塞后续 accept。缺少 spawner 或每子流任务注入。
3. **优雅关闭**：只有取消令牌；没有 `ServeHandle` / drain / 等待 in-flight 结束的句柄。
4. **错误源**：大量 `ServeError::* (String)` / `ClientError::* (String)` 丢掉了底层错误
   类型，调用者无法区分「连接断了」与「协议错」。
5. **no_std 事实不一致**：Cargo `categories = ["no-std"]`，但 crate 没有 `#![no_std]`，
   且使用 `String` / `format!` / std prelude；`abs_mptp_smux` 才是 no_std 的抽象层。
   要么补 `std` feature 并明确「默认 std」，要么真的支持 no_std。
6. **线格式 / RPC 层耦合**：见 §3.3；这是 `mptp_quic` 的最大障碍。
7. **`abs_mptp_smux` 定位未定**：是未来 mptp_smux/mptp_quic 的共同抽象，还是废弃实验？

## 6. `client` / `server` feature 目标

### 6.1 建议的 feature 表

| feature | 提供 | 说明 |
| --- | --- | --- |
| `default` | `client` + `server` | 保持当前「两端对等」的开箱行为 |
| `client` | `client` 模块、`client::config::TrConfig`、`ClientPrepCtx`、`MptpClient` / `MptpSession` | 只发请求时使用 |
| `server` | `serving` 模块、`serving::config::TrConfig`、`ServingPrepCtx`、`MptpServer`、`TrPathRouter`；第一阶段仍含内置 `Router` | 只接请求时使用 |
| `router`（第二阶段） | 内置 `serving::Router` + `matchit_route` / `tlist` 依赖 | 第二阶段从 `server` 拆出；只有需要默认前缀路由时开启 |
| `messaging` | 不设 feature，始终编译 | 前缀线格式类型与读写入口是两端共享面 |

依赖调整：

- `matchit_route` / `tlist` 变为 optional，只在 `router`（或 `server` 若保留内置 Router）
  时启用；
- `abs_denco` / `mp_denco` / `denco_macro` 仍由 `messaging` 使用，两端都需要；
- `futures` / `thiserror` 为公共依赖；
- `tokio` 仍只作为 dev-dependency。

### 6.2 下游怎么声明

```toml
# 只做客户端
mptp_smux = { path = "../mptp_smux", default-features = false, features = ["client"] }

# 只做服务端（第一阶段仍带内置 Router）
mptp_smux = { path = "../mptp_smux", default-features = false, features = ["server"] }

# 两端对等（第二阶段可再显式启用 router）
mptp_smux = { path = "../mptp_smux", features = ["client", "server", "router"] }
```

预期下游：

| crate | features |
| --- | --- |
| `abs_rpc_serv` | `server`（只需要 serving 契约与协议类型） |
| `rpc_core_v1` | `client` + `server`（RPC 两端都要） |
| `mptp_smux_v1_demo` | `client` + `server` |
| `rpc_demo` | `client` + `server` |
| `mptp_cs_smoke` | `client` + `server` |

### 6.3 验收条件

- `cargo check -p mptp_smux --no-default-features`：只剩 `messaging`（+ 公共 ring 契约）；
- `--features client`：无 `serving` 模块、无 `matchit_route` / `tlist` 依赖；
- `--features server`：无 `client` 模块；
- `--all-features`：当前全量行为不变；
- 各下游按上表声明后，`cargo test --workspace` 与两个 demo 的 e2e 不变。

## 8. 开放问题

1. **线格式归属**：新建 `mptp_wire`，还是把 `RequestPrefix` / `ResponsePrefix` /
   `Headers` 与 MessagePack codec 移进 `abs_mptp`？后者会让 `abs_mptp` 依赖 `mp_denco`，
   需要确认 `abs_mptp` 的「只定义形状、不规定编码」定位是否要调整。
2. **Router 去留**：`TrPathRouter` 接缝保留；内置 `Router` 是 feature 化、移到独立 crate，
   还是直接删除？外部 `mptp_cs_smoke` 需要迁移。
3. **`abs_mptp_smux` 去留**：删除，还是让 `mptp_smux` 依赖它并把重复的 config / ring
   准备搬过去？
4. **并发模型**：`serve_listener_async` 是否接受一个 spawner/handler 注入？默认串行还是
   默认并发？这会改变 `ServeError` 与关闭语义。
5. **no_std**：`mptp_smux` 目标是否 no_std + alloc？如果是，`std` feature 与
   `abs_mptp_smux` 的关系需要先定。
6. **错误类型**：是否保留底层错误 source，而不是 `String`？
7. **会话复用**：协议当前一条通道一次请求；是否明确「不打算支持」并写进 README，
   避免以后误加？

## 9. 建议的重构顺序

1. 先拆分 `client` / `server` feature，保持行为不变；这是最小、可验证的一步；
2. 把内置 `Router` 从 `server` 默认依赖中拆出（`router` feature 或独立 crate）；
3. 决定线格式归属，解除 `abs_rpc_serv` / `rpc_core_v1` 对 `mptp_smux` 的直接依赖；
4. 再讨论并发 / 关闭 / no_std 等行为变化；
5. 最后清理 `abs_mptp_smux` 与 `x_deps`。

## 10. 对 README 的约束

- README 必须区分「当前状态」与「重构目标」，不能把尚未实现的 feature 写成已实现；
- 「应该 / 不应该」用明确条目写，避免只描述模块；
- 例子可以指向 `mptp_smux_v1_demo` / `rpc_demo`，不要复制一整套配置；
- 与 `mptp_quic` 的共通点要写成契约，而不是「以后可能」的口号；
- 不把 `Router` 写成 MPTP 的必备部分。

## 11. 英文摘要

`mptp_smux` is the concrete MPTP binding over `smux_v1`, analogous to HTTP over
TCP. It must own the smux-specific channel lifecycle, ring-memory injection, prefix
wire IO, body/suffix transport and cancellation propagation, while leaving RPC
semantics, business body codecs, routing policy, runtime selection and connection
management outside. The planned `client` / `server` features make the peer-to-peer
roles independently selectable. A future `mptp_quic` should share the MPTP wire
format and session contracts, not depend on `mptp_smux`; today the concrete prefix
types and the built-in router are the main couplings that block that split.
